# 22.9 — Hierarchical & Partial-Order Planning

Hierarchical planning chooses useful abstractions before choosing every primitive action. Partial-order planning keeps only the before/after constraints that are logically needed, so independent actions can remain unordered until a causal dependency or a threat forces a decision.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build hierarchical task networks and partial-order planning one idea at a time. Run each cell in order and read the printed intermediate values — every piece of planning logic is spelled out so nothing is a black box. This walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

```python
import numpy as np  # arrays and simple counting for planning experiments.
import matplotlib.pyplot as plt  # all walkthrough and example visualizations.
from itertools import permutations  # enumerate linearizations of tiny partial orders.
from math import factorial  # count flat search branches and total permutations.
np.random.seed(0)  # make any random tie-breaking reproducible.

def draw_dag(nodes, edges, pos, title, edge_labels=None, node_colors=None):  # Draw a small planning DAG with Matplotlib only.
    edge_labels = edge_labels or {}  # Optional labels such as causal-link conditions.
    node_colors = node_colors or {}  # Optional per-node colors for emphasis.
    plt.figure(figsize=(6, 3.6))  # Keep diagrams readable in notebook cells.
    for a, b in edges:  # Draw every ordering or causal edge as an arrow.
        x1, y1 = pos[a]  # Producer/source coordinates.
        x2, y2 = pos[b]  # Consumer/target coordinates.
        plt.annotate("", xy=(x2, y2), xytext=(x1, y1), arrowprops=dict(arrowstyle="->", lw=1.8, color="black"))  # Arrow means a must happen before b.
        if (a, b) in edge_labels:  # Place edge text halfway along the arrow.
            plt.text((x1 + x2) / 2, (y1 + y2) / 2 + 0.08, edge_labels[(a, b)], ha="center", fontsize=9)  # Label causal condition.
    for n in nodes:  # Draw labeled action/task nodes.
        x, y = pos[n]  # Node position.
        plt.scatter([x], [y], s=900, color=node_colors.get(n, "white"), edgecolor="black", zorder=3)  # Circular node.
        plt.text(x, y, n, ha="center", va="center", fontsize=9, zorder=4)  # Node label.
    plt.title(title)  # Explain the diagram.
    plt.axis("off")  # Hide numeric axes; this is a graph.

def topological_orders(nodes, edges):  # Enumerate valid total orders for tiny partial-order plans.
    edge_set = set(edges)  # Store constraints for quick checking.
    orders = []  # Collect legal linearizations.
    for order in permutations(nodes):  # Try every tiny permutation.
        idx = {name: k for k, name in enumerate(order)}  # Position of each action in the order.
        if all(idx[a] < idx[b] for a, b in edge_set):  # Check every before-after constraint.
            orders.append(order)  # Keep only legal schedules.
    return orders  # Return all valid linearizations.
```

### 1. HTN methods replace one abstract task with smaller tasks

A Hierarchical Task Network method is a recipe: when the planner sees an abstract task such as `Travel`, it may replace it with subtasks such as `Pack`, `Drive`, and `Park`. The important modeling choice is that the method library controls which refinements are even considered.

```python
methods_w = {"Travel": ["Pack", "Drive", "Park"]}  # One HTN method maps an abstract task to three executable subtasks.
root_w = "Travel"  # The abstract task at the top of the hierarchy.
subtasks_w = methods_w[root_w]  # Apply the method to refine the task.
print(f"{root_w} -> {subtasks_w}")  # Inspect the symbolic decomposition.
print("primitive step count:", len(subtasks_w))  # Count the executable leaves.
assert len(subtasks_w) == 3  # Match the lesson's Travel -> three primitive steps.

nodes_w = [root_w] + subtasks_w  # Include abstract and primitive tasks in one diagram.
edges_w = [(root_w, s) for s in subtasks_w]  # Tree edges mean decomposition, not temporal order.
pos_w = {root_w: (1.5, 1.2), "Pack": (0, 0), "Drive": (1.5, 0), "Park": (3, 0)}  # Layout as a task tree.
draw_dag(nodes_w, edges_w, pos_w, "1: HTN task-decomposition tree", node_colors={root_w: "lightyellow"})  # Visualize the hierarchy.
plt.show()  # Display the planning visualization.
```
▶ What you'll see: one abstract task fans out into three primitive leaves.

*Why it's done this way:* hierarchy turns a hard flat action choice into a smaller method choice, so abstraction prunes irrelevant primitive sequences before search begins.

### 2. Hierarchy reduces branching by making useful commitments

Flat planning at depth three with six primitive choices per level has $6^3=216$ candidate sequences. If an HTN first chooses between two methods and then makes three internal choices, it explores only $2\cdot3=6$ combinations in this toy comparison.

```python
flat_choices_w = 6  # Flat planner's primitive branching factor.
depth_w = 3  # Number of primitive decisions.
flat_count_w = flat_choices_w ** depth_w  # Flat depth-three sequence count.
htn_methods_w = 2  # Number of high-level method choices.
internal_choices_w = 3  # Choices left after selecting a method.
htn_count_w = htn_methods_w * internal_choices_w  # Hierarchical search count.
reduction_w = flat_count_w / htn_count_w  # How many fewer candidates HTN considers.
print("flat candidates:", flat_count_w)  # 216.
print("HTN candidates:", htn_count_w)  # 6.
print("reduction factor:", reduction_w)  # 36.
assert flat_count_w == 216 and htn_count_w == 6 and reduction_w == 36  # Verify lesson arithmetic.

plt.figure(figsize=(5, 3))  # Compare the two search spaces.
plt.bar(["flat 6^3", "HTN 2·3"], [flat_count_w, htn_count_w], color=["crimson", "seagreen"])  # Show candidate counts.
plt.ylabel("candidate refinements")  # Count scale.
plt.title("2: hierarchy shrinks the branching burden")  # Explain plot.
plt.show()  # Display the relevant branching comparison.
```
▶ What you'll see: the flat bar is 36 times taller than the HTN bar.

*Why it's done this way:* an HTN method is useful only if it removes large regions of primitive search while still preserving the plans the domain designer believes matter.

### 3. Partial-order plans keep only necessary before-after constraints

A partial-order plan is a set of steps plus constraints $a\prec b$. With `Buy`, `Cook`, and `SetTable`, the only causal requirement might be `Buy ≺ Cook`; `SetTable` is intentionally left floating.

```python
steps_w = ["Buy", "Cook", "SetTable"]  # Three actions in the tiny plan.
constraints_w = [("Buy", "Cook")]  # Only one necessary ordering constraint.
orders_w = topological_orders(steps_w, constraints_w)  # Enumerate total schedules consistent with the partial order.
print("valid linearizations:", orders_w)  # Inspect all legal total orders.
print("count:", len(orders_w), "of", factorial(len(steps_w)))  # Three of six permutations.
assert len(orders_w) == 3  # Match the lesson's 6/2 = 3 result.

pos_w = {"Buy": (0, 0.5), "Cook": (2, 0.5), "SetTable": (1, -0.6)}  # Put independent SetTable below the chain.
draw_dag(steps_w, constraints_w, pos_w, "3: partial-order plan, SetTable floats")  # Visualize the one required edge.
plt.show()  # Display the planning visualization.
```
▶ What you'll see: only Buy points to Cook; SetTable has no forced position.

*Why it's done this way:* delayed commitment preserves flexibility, because the planner does not choose among equivalent total orders until some later constraint actually requires it.

### 4. Causal links explain why an ordering exists

A causal link records that one step achieves a condition needed by another step. If `Buy` achieves `have_food` and `Cook` requires `have_food`, then the link `Buy --have_food--> Cook` justifies the ordering `Buy ≺ Cook`.

```python
producer_w = "Buy"  # Step that makes a condition true.
consumer_w = "Cook"  # Step that needs the condition.
condition_w = "have_food"  # The fluent protected by the causal link.
causal_link_w = (producer_w, condition_w, consumer_w)  # Store producer, condition, consumer.
ordering_w = (producer_w, consumer_w)  # The implied before-after constraint.
print("causal link:", causal_link_w)  # Inspect the protected fact.
print("implied ordering:", ordering_w)  # Inspect the temporal consequence.
assert causal_link_w[0] == ordering_w[0] and causal_link_w[2] == ordering_w[1]  # Producer precedes consumer.

pos_w = {"Start": (-1, 0.5), "Buy": (0.5, 0.5), "Cook": (2, 0.5), "Finish": (3.5, 0.5)}  # Linear causal chain layout.
nodes_w = ["Start", "Buy", "Cook", "Finish"]  # Include start and finish sentinels.
edges_w = [("Start", "Buy"), ("Buy", "Cook"), ("Cook", "Finish")]  # Ordering edges.
labels_w = {("Buy", "Cook"): condition_w}  # Label the causal edge.
draw_dag(nodes_w, edges_w, pos_w, "4: causal link protects a needed condition", labels_w)  # Visualize the link.
plt.show()  # Display the planning visualization.
```
▶ What you'll see: the Buy→Cook edge is labeled with the condition it protects.

*Why it's done this way:* causal links make a plan explainable: every precondition should be supported by a specific earlier action, not by hope.

### 5. Threats force promotion or demotion

A threat is a step that could occur between a producer and consumer while deleting the protected condition. If `EatSnack` deletes `have_food`, it cannot float between `Buy` and `Cook`; the planner must demote it before `Buy` or promote it after `Cook`.

```python
link_w = ("Buy", "have_food", "Cook")  # Protected causal link.
threat_w = "EatSnack"  # A step that consumes or deletes the food.
deletes_w = {"EatSnack": {"have_food"}}  # Delete effects by action.
is_threat_w = link_w[1] in deletes_w.get(threat_w, set())  # Check whether the threat deletes the protected condition.
resolutions_w = [(threat_w, link_w[0]), (link_w[2], threat_w)]  # Demotion or promotion orderings.
print("is threat:", is_threat_w)  # Confirm the threat test.
print("resolutions:", resolutions_w)  # Show demotion and promotion.
assert is_threat_w and len(resolutions_w) == 2  # Verify both standard repairs exist.

nodes_w = ["Buy", "Cook", threat_w]  # Actions in the threatened plan.
pos_w = {"Buy": (0, 0.5), "Cook": (2, 0.5), threat_w: (1, -0.6)}  # Threat sits between them visually.
edges_w = [("Buy", "Cook"), (threat_w, "Buy"), ("Cook", threat_w)]  # Include both alternative repairs as dashed-looking labels via text.
labels_w = {("Buy", "Cook"): "have_food", (threat_w, "Buy"): "demote", ("Cook", threat_w): "promote"}  # Explain edges.
draw_dag(nodes_w, edges_w, pos_w, "5: threat repair by demotion or promotion", labels_w, {threat_w: "mistyrose"})  # Visualize repair options.
plt.show()  # Display the planning visualization.
```
▶ What you'll see: the threatening node is separated from the protected interval by added orderings.

*Why it's done this way:* POP stays flexible until a threat appears, then adds the weakest ordering constraint that protects the causal link.

### 6. Bad method libraries can hide valid plans

HTN planning is only as complete as its method library. If the library has a `Travel` method for driving but no method for taking a train, then every train-based valid plan is invisible to the planner.

```python
all_real_methods_w = {"Travel": ["drive_method", "train_method"]}  # What the world might allow.
library_w = {"Travel": ["drive_method"]}  # What the HTN planner actually knows.
missing_w = set(all_real_methods_w["Travel"]) - set(library_w["Travel"])  # Methods hidden from search.
print("known methods:", library_w["Travel"])  # Inspect available decompositions.
print("missing methods:", sorted(missing_w))  # Inspect absent decompositions.
assert missing_w == {"train_method"}  # The library hides the train option.

plt.figure(figsize=(5, 3))  # Compare real and encoded method coverage.
plt.bar(["real methods", "library methods"], [len(all_real_methods_w["Travel"]), len(library_w["Travel"])], color=["gray", "seagreen"])  # Count methods.
plt.ylabel("method count")  # Count axis.
plt.title("6: HTN completeness depends on the method library")  # Explain the pitfall.
plt.show()  # Display the method-coverage visualization.
```
▶ What you'll see: the planner's library is a strict subset of the real options.

*Why it's done this way:* hierarchy is a powerful bias, but every bias excludes something; missing methods can make a valid plan unreachable.

### 7. Overconstraining destroys useful flexibility

Adding unnecessary orderings converts a flexible partial-order plan into one arbitrary total order. For `Buy`, `Cook`, and `SetTable`, the single required edge gives three legal schedules, but adding `Buy ≺ SetTable` and `SetTable ≺ Cook` leaves only one.

```python
steps_w = ["Buy", "Cook", "SetTable"]  # Same tiny plan as before.
minimal_w = [("Buy", "Cook")]  # Only causal ordering.
overconstrained_w = [("Buy", "SetTable"), ("SetTable", "Cook"), ("Buy", "Cook")]  # Extra unnecessary chain.
minimal_orders_w = topological_orders(steps_w, minimal_w)  # Flexible linearizations.
tight_orders_w = topological_orders(steps_w, overconstrained_w)  # Overconstrained linearizations.
print("minimal count:", len(minimal_orders_w), minimal_orders_w)  # Three valid orders.
print("overconstrained count:", len(tight_orders_w), tight_orders_w)  # One valid order.
assert len(minimal_orders_w) == 3 and len(tight_orders_w) == 1  # Verify flexibility loss.

plt.figure(figsize=(5, 3))  # Show lost schedule flexibility.
plt.bar(["minimal POP", "overconstrained"], [len(minimal_orders_w), len(tight_orders_w)], color=["seagreen", "crimson"])  # Compare linearization counts.
plt.ylabel("valid total orders")  # Count axis.
plt.title("7: unnecessary constraints reduce flexibility")  # Explain plot.
plt.show()  # Display the relevant flexibility count.
```
▶ What you'll see: the legal schedule count drops from three to one.

*Why it's done this way:* a partial-order planner should add constraints because logic requires them, not because one arbitrary sequence happens to be easy to imagine.

### ✍️ Toy 5 · Threats need promotion or demotion

If a step can delete a protected condition, the planner must order it outside the protected interval.

```python
import numpy as np

t5_rng = np.random.default_rng(0)
t5_link = ("WashCup", "cup_clean", "PourTea")
t5_threat = "UseDirtySpoon"
t5_deletes = {t5_threat: frozenset(["cup_clean"])}
t5_is_threat = t5_link[1] in t5_deletes[t5_threat]  # -> True
t5_demote = (t5_threat, t5_link[0])  # -> ('UseDirtySpoon', 'WashCup')
t5_promote = (t5_link[2], t5_threat)  # -> ('PourTea', 'UseDirtySpoon')
t5_repairs = [t5_demote, t5_promote]
print("is threat?:", t5_is_threat)  # -> True
print("demotion repair:", t5_demote)  # -> ('UseDirtySpoon', 'WashCup')
print("promotion repair:", t5_promote)  # -> ('PourTea', 'UseDirtySpoon')
assert t5_is_threat and t5_repairs == [("UseDirtySpoon", "WashCup"), ("PourTea", "UseDirtySpoon")]

plt.figure(figsize=(5.8, 3))
t5_pos = {"WashCup": (0, 0.5), "PourTea": (2.2, 0.5), "UseDirtySpoon": (1.1, -0.7)}

plt.axis("off")
plt.title("Toy 5 · repairs keep the threat outside")
plt.show()
```

### ✍️ Toy 7 · Extra orderings collapse flexibility

Adding unnecessary constraints can turn a flexible partial-order plan into one arbitrary chain.

```python
import numpy as np

t7_rng = np.random.default_rng(0)
t7_orders_all = [("BuyFlowers", "WriteCard", "DeliverGift"), ("BuyFlowers", "DeliverGift", "WriteCard"), ("WriteCard", "BuyFlowers", "DeliverGift"), ("WriteCard", "DeliverGift", "BuyFlowers"), ("DeliverGift", "BuyFlowers", "WriteCard"), ("DeliverGift", "WriteCard", "BuyFlowers")]
t7_minimal = [t7_order for t7_order in t7_orders_all if t7_order.index("BuyFlowers") < t7_order.index("DeliverGift")]  # -> 3 orders
t7_tight = [t7_order for t7_order in t7_orders_all if t7_order.index("BuyFlowers") < t7_order.index("WriteCard") < t7_order.index("DeliverGift")]  # -> 1 order
t7_counts = np.array([len(t7_minimal), len(t7_tight)])  # -> [3 1]
print("minimal schedules:", t7_minimal)  # -> [('BuyFlowers', 'WriteCard', 'DeliverGift'), ('BuyFlowers', 'DeliverGift', 'WriteCard'), ('WriteCard', 'BuyFlowers', 'DeliverGift')]
print("tight schedules:", t7_tight)  # -> [('BuyFlowers', 'WriteCard', 'DeliverGift')]
print("schedule counts:", t7_counts.tolist())  # -> [3, 1]
assert t7_counts.tolist() == [3, 1]

plt.figure(figsize=(4.8, 3))
plt.bar(["minimal", "overconstrained"], t7_counts, color=["seagreen", "crimson"])
plt.ylabel("valid total orders")
plt.title("Toy 7 · unnecessary orderings remove schedules")
```

## 🛠️ Setup

```python
import numpy as np  # Use NumPy for arrays, masks, and small numerical checks.
import matplotlib.pyplot as plt  # Use Matplotlib for all HTN and POP visualizations.
from itertools import permutations  # Enumerate tiny topological orders without external graph libraries.
from math import factorial  # Count total permutations and flat search candidates.
np.random.seed(0)  # Keep examples reproducible.

def draw_plan(nodes, edges, pos, title, labels=None, colors=None):  # Draw a tiny directed planning graph.
    labels = labels or {}  # Optional labels for causal links or repair choices.
    colors = colors or {}  # Optional node colors for highlighting.
    plt.figure(figsize=(6, 3.6))  # Create a readable notebook figure.
    for a, b in edges:  # Draw each directed edge.
        x1, y1 = pos[a]  # Source coordinates.
        x2, y2 = pos[b]  # Target coordinates.
        plt.annotate("", xy=(x2, y2), xytext=(x1, y1), arrowprops=dict(arrowstyle="->", lw=1.7, color="black"))  # Edge arrow.
        if (a, b) in labels:  # Add a label when the edge has semantic meaning.
            plt.text((x1 + x2) / 2, (y1 + y2) / 2 + 0.08, labels[(a, b)], ha="center", fontsize=9)  # Edge text.
    for n in nodes:  # Draw nodes after edges so they sit on top.
        x, y = pos[n]  # Node coordinates.
        plt.scatter([x], [y], s=850, color=colors.get(n, "white"), edgecolor="black", zorder=3)  # Node marker.
        plt.text(x, y, n, ha="center", va="center", fontsize=9, zorder=4)  # Node label.
    plt.title(title)  # Figure title.
    plt.axis("off")  # Hide axes because positions are schematic.

def legal_orders(nodes, edges):  # Return all topological orders for a tiny DAG.
    orders = []  # Storage for legal linearizations.
    for order in permutations(nodes):  # Brute-force all permutations because lesson examples are tiny.
        index = {name: k for k, name in enumerate(order)}  # Map each node to its position.
        if all(index[a] < index[b] for a, b in edges):  # Enforce every ordering constraint.
            orders.append(order)  # Keep legal schedules.
    return orders  # Return valid total orders.

def has_cycle(nodes, edges):  # Detect whether ordering constraints are inconsistent.
    for order in permutations(nodes):  # Try tiny candidate topological orders.
        index = {name: k for k, name in enumerate(order)}  # Position map.
        if all(index[a] < index[b] for a, b in edges):  # A legal order means no cycle.
            return False  # Constraints are consistent.
    return True  # No legal order exists, so a cycle blocks the plan.

def htn_decompose(task, methods):  # Recursively decompose one HTN task using the first available method.
    if task not in methods:  # Primitive tasks have no decomposition method.
        return [task]  # Return the primitive leaf.
    leaves = []  # Storage for primitive tasks.
    for subtask in methods[task]:  # Expand subtasks in method order.
        leaves.extend(htn_decompose(subtask, methods))  # Recursively refine each subtask.
    return leaves  # Return all primitive leaves.

def pop_plan(actions, initial_state, goal):  # A tiny POP constructor for independent goal literals.
    steps = ["Start", "Finish"]  # Sentinel steps.
    edges = [("Start", "Finish")]  # Start must precede Finish.
    links = []  # Causal links from producers to Finish.
    for need in sorted(goal):  # Support each goal literal.
        producer = None  # Track an action that can add the needed literal.
        for name, spec in actions.items():  # Search action definitions.
            if need in spec["add"]:  # This action can support the goal.
                producer = name  # Choose the first support action.
                break  # Stop searching.
        assert producer is not None or need in initial_state  # Every goal must be supported.
        if producer is not None:  # If an action supports the goal.
            if producer not in steps:  # Add producer once.
                steps.append(producer)  # Insert action into partial plan.
                edges.append(("Start", producer))  # Action occurs after Start.
            edges.append((producer, "Finish"))  # Producer must precede Finish.
            links.append((producer, need, "Finish"))  # Record causal link.
    return steps, edges, links  # Return tiny partial-order plan.
```

#### A2. Add threat detection to the POP planner

**Goal.** Scan causal links for deleting actions and repair them, because an apparently supported plan may still be invalid if a threat can slip between producer and consumer. We build it in 4 steps.

```python
steps_a2 = ["Buy", "Cook", "EatSnack"]  # Existing actions.
links_a2 = [("Buy", "have_food", "Cook")]  # Protected causal link.
edges_a2 = [("Buy", "Cook")]  # Current ordering constraints.
deletes_a2 = {"EatSnack": {"have_food"}, "Buy": set(), "Cook": set()}  # Delete effects.
threats_a2 = []  # Store detected threats.
for producer_a2, cond_a2, consumer_a2 in links_a2:  # Check each causal link.
    for step_a2 in steps_a2:  # Check each action.
        if step_a2 not in (producer_a2, consumer_a2) and cond_a2 in deletes_a2.get(step_a2, set()):  # Threat test.
            threats_a2.append((step_a2, producer_a2, cond_a2, consumer_a2))  # Record threat.
print("threats:", threats_a2)  # Inspect detected threat tuples.
assert threats_a2 == [("EatSnack", "Buy", "have_food", "Cook")]  # Verify threat detection.
```
▶ What you'll see: EatSnack is detected as threatening Buy's support for Cook.

```python
repairs_a2 = []  # Store repair edges.
for threat_a2, producer_a2, cond_a2, consumer_a2 in threats_a2:  # Repair each threat.
    promote_a2 = (consumer_a2, threat_a2)  # Promotion edge.
    candidate_edges_a2 = edges_a2 + [promote_a2]  # Try promotion first.
    if not has_cycle(steps_a2, candidate_edges_a2):  # Keep it if consistent.
        repairs_a2.append(promote_a2)  # Accept promotion.
edges_repaired_a2 = edges_a2 + repairs_a2  # Final repaired edge set.
print("repairs:", repairs_a2)  # Inspect added orderings.
assert repairs_a2 == [("Cook", "EatSnack")]  # Promotion is valid here.
```

