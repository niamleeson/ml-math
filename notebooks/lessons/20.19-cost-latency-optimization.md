# 20.19 — Cost & Latency Optimization

Cost and latency optimization turns a trained model into a production decision: serve the cheapest path that still meets quality and tail-latency promises. In this lesson, we build the arithmetic from scratch with NumPy so every engineering knob — batching, caching, autoscaling, spot capacity, Pareto search, and cascades — is visible as a small equation rather than hidden infrastructure magic.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build cost and latency optimization one idea at a time. Run each cell in order and read the printed intermediate values — the goal is to make every production tradeoff inspectable. This walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

```python
import numpy as np  # arrays, percentiles, and small simulations.
import matplotlib.pyplot as plt  # all walkthrough visualizations.
np.random.seed(0)  # reproducibility for synthetic workloads.
```

### 1. Tail latency is the product promise

Production ML is judged by users, not by averages. If most requests are fast but a few are painfully slow, the mean can look healthy while the product feels broken. We therefore inspect percentiles: p50 is the median user, while p95 asks what latency 95% of users beat and 5% exceed.

```python
latencies_w = np.array([58, 61, 64, 66, 69, 72, 74, 77, 81, 88, 96, 120, 180], dtype=float)  # synthetic request latencies in ms.
p50_w = float(np.percentile(latencies_w, 50))  # median latency.
p95_w = float(np.percentile(latencies_w, 95))  # tail latency target.
print("p50 ms:", round(p50_w, 1), "p95 ms:", round(p95_w, 1), "tail / median:", round(p95_w / p50_w, 2))
assert round(p50_w, 1) == 74.0 and round(p95_w, 1) == 144.0
```
▶ What you'll see: the p95 is almost 2× the median even in this tiny workload.

```python
plt.figure(figsize=(5, 3))
plt.plot(np.sort(latencies_w), marker="o", color="teal")
plt.axhline(p50_w, linestyle="--", color="gray", label="p50")
plt.axhline(p95_w, linestyle="--", color="crimson", label="p95")
plt.title("1: sorted request latencies")
plt.xlabel("request after sorting")
plt.ylabel("latency (ms)")
plt.legend()
plt.show()
```
▶ What you'll see: the right edge bends upward; that bend, not the center, drives p95 pain.

*Why it's done this way:* percentiles convert a distribution into user promises. The p95 is an order statistic: it asks where the slowest 5% begin. Optimizing only the mean can hide a small slow subgroup, while p95 explicitly prices that subgroup into the objective.

### 2. Roofline: compute-bound versus memory-bound

A model server cannot run faster than its hardware limits. The roofline model says throughput is the smaller of compute peak and memory bandwidth times arithmetic intensity. Arithmetic intensity is FLOPs per byte moved; low intensity workloads wait on memory, high intensity workloads wait on math units.

```python
peak_tflops_w = 120.0  # accelerator peak compute.
bandwidth_tb_s_w = 1.6  # memory bandwidth.
intensity_w = np.array([2, 8, 32, 128], dtype=float)  # FLOPs per byte.
roof_tflops_w = np.minimum(peak_tflops_w, bandwidth_tb_s_w * intensity_w)  # roofline throughput.
print("intensity:", intensity_w)
print("roof TFLOP/s:", np.round(roof_tflops_w, 1))
assert np.allclose(roof_tflops_w, [3.2, 12.8, 51.2, 120.0])
```
▶ What you'll see: low-intensity kernels are far below peak compute because memory bandwidth is the ceiling.

```python
plot_intensity_w = np.logspace(0, 3, 100)
plot_roof_w = np.minimum(peak_tflops_w, bandwidth_tb_s_w * plot_intensity_w)
plt.figure(figsize=(5, 3.4))
plt.loglog(plot_intensity_w, plot_roof_w, color="navy")
plt.scatter(intensity_w, roof_tflops_w, color="orange", zorder=3)
plt.axhline(peak_tflops_w, linestyle="--", color="gray", label="compute peak")
plt.title("2: roofline throughput bound")
plt.xlabel("arithmetic intensity (FLOPs / byte)")
plt.ylabel("achievable TFLOP/s")
plt.legend()
plt.show()
```
▶ What you'll see: the slanted memory-bound region rises with intensity, then flattens at the compute peak.

*Why it's done this way:* runtime is constrained by two resources. If each byte creates few FLOPs, bytes arrive too slowly and bandwidth dominates. If each byte is reused enough, math units saturate and compute peak dominates. The minimum of the two bounds is the best possible throughput before software overhead.

### 3. Batching lowers compute cost but adds queueing

Batching shares fixed overhead and accelerates matrix kernels, so compute per request can fall as batch size grows. But requests must wait for the batch to form. End-to-end latency is not just compute; it is queue wait plus batched compute.

```python
batch_sizes_w = np.array([1, 2, 4, 8, 16], dtype=float)
fixed_ms_w = 12.0  # launch and framework overhead per batch.
per_item_ms_w = 4.0  # incremental compute per request inside a batch.
compute_per_request_w = fixed_ms_w / batch_sizes_w + per_item_ms_w
print("compute/request ms:", np.round(compute_per_request_w, 2))
assert round(float(compute_per_request_w[3]), 2) == 5.5
```
▶ What you'll see: batch 8 amortizes fixed overhead to 5.5 ms per request.

```python
arrival_gap_ms_w = 3.0  # average time between incoming requests.
queue_wait_w = arrival_gap_ms_w * (batch_sizes_w - 1) / 2  # average wait for the batch to fill.
end_to_end_w = queue_wait_w + compute_per_request_w
print("queue wait ms:", np.round(queue_wait_w, 2))
print("end-to-end ms:", np.round(end_to_end_w, 2))
assert round(float(end_to_end_w[2]), 2) == 11.5
```
▶ What you'll see: larger batches keep lowering compute, but waiting eventually dominates.

```python
plt.figure(figsize=(5, 3))
plt.plot(batch_sizes_w, compute_per_request_w, marker="o", label="compute/request")
plt.plot(batch_sizes_w, end_to_end_w, marker="s", label="compute + wait")
plt.title("3: batching economics")
plt.xlabel("batch size")
plt.ylabel("latency (ms)")
plt.legend()
plt.show()
```
▶ What you'll see: the compute curve falls, while the end-to-end curve has a sweet spot.

*Why it's done this way:* batching divides fixed cost by batch size, which is why throughput improves. Queueing grows roughly with half the fill time, because an average request arrives halfway through the batch window. The optimum is where marginal compute savings no longer beat marginal waiting.

### 4. Caching and Amdahl's law

A cache turns some expensive misses into cheap hits. Expected latency is a weighted average: hit rate times hit latency plus miss rate times miss latency. But Amdahl's law says only the cacheable fraction can improve; uncached work remains as a hard floor.

```python
hit_rate_w = 0.60
hit_ms_w = 4.0
miss_ms_w = 80.0
expected_cache_ms_w = hit_rate_w * hit_ms_w + (1 - hit_rate_w) * miss_ms_w
print("expected cache latency ms:", round(expected_cache_ms_w, 1))
assert round(expected_cache_ms_w, 1) == 34.4
```
▶ What you'll see: a 60% hit rate cuts the 80 ms miss path to 34.4 ms expected latency.

```python
cacheable_w = 0.75
speedup_hit_path_w = miss_ms_w / hit_ms_w
amdahl_speedup_w = 1 / ((1 - cacheable_w) + cacheable_w / speedup_hit_path_w)
print("hit-path speedup:", round(speedup_hit_path_w, 1), "overall speedup cap:", round(amdahl_speedup_w, 2))
assert round(amdahl_speedup_w, 2) == 3.48
```
▶ What you'll see: even a 20× faster cache hit gives only a 3.48× overall cap when 25% cannot be cached.

*Why it's done this way:* weighted averages answer what one random request experiences. Amdahl's law answers a different question: if part of the system cannot improve, total speedup is limited by that fixed part. Both are needed before calling caching a win.

### 5. Autoscaling trades cost against SLO violations

Autoscaling chooses how many replicas to run. More replicas lower utilization and queueing, but every replica costs money. A simple capacity model lets us reject replica counts that violate an SLO, then choose the cheapest feasible count.

```python
qps_w = 900.0
capacity_per_replica_w = 250.0
replicas_w = np.arange(3, 8)
util_w = qps_w / (replicas_w * capacity_per_replica_w)
base_ms_w = 35.0
latency_model_w = base_ms_w / np.maximum(1 - util_w, 0.05)  # queueing grows as utilization approaches 1.
print("replicas:", replicas_w)
print("utilization:", np.round(util_w, 2))
print("modeled latency ms:", np.round(latency_model_w, 1))
assert round(float(latency_model_w[2]), 1) == 125.0
```
▶ What you'll see: under-provisioned replica counts have high utilization and high modeled latency.

```python
cost_per_replica_hour_w = 1.20
slo_ms_w = 180.0
hourly_cost_w = replicas_w * cost_per_replica_hour_w
feasible_w = latency_model_w <= slo_ms_w
best_idx_w = int(np.where(feasible_w)[0][np.argmin(hourly_cost_w[feasible_w])])
print("feasible:", feasible_w)
print("cheapest feasible replicas:", int(replicas_w[best_idx_w]), "cost/hour:", round(float(hourly_cost_w[best_idx_w]), 2))
assert int(replicas_w[best_idx_w]) == 5
```
▶ What you'll see: five replicas are the cheapest setting that stays under the 180 ms SLO.

*Why it's done this way:* utilization is demand divided by capacity. Queueing delay rises nonlinearly near 100% utilization, so the cheapest raw capacity may be unacceptable. Optimization is constrained: minimize cost subject to latency meeting the SLO.

### 6. Spot and on-demand mix price reliability

Spot capacity is cheaper but interruptible; on-demand is expensive but reliable. The right mix depends on how much traffic can tolerate fallback or retry. Expected hourly cost is a weighted mix, while risk is the fraction placed on spot times the interruption probability.

```python
spot_share_w = np.array([0.0, 0.25, 0.50, 0.75])
on_demand_price_w = 1.20
spot_price_w = 0.42
replicas_total_w = 10
mix_cost_w = replicas_total_w * ((1 - spot_share_w) * on_demand_price_w + spot_share_w * spot_price_w)
print("spot share:", spot_share_w)
print("hourly cost:", np.round(mix_cost_w, 2))
assert round(float(mix_cost_w[2]), 2) == 8.10
```
▶ What you'll see: moving half the fleet to spot lowers cost from \$12.00/hour to \$8.10/hour.

```python
interrupt_prob_w = 0.08
risk_w = spot_share_w * interrupt_prob_w
risk_budget_w = 0.04
safe_mix_w = spot_share_w[risk_w <= risk_budget_w][-1]
print("interruption risk:", np.round(risk_w, 3))
print("largest safe spot share:", safe_mix_w)
assert safe_mix_w == 0.5
```
▶ What you'll see: a 50% spot share is the largest mix under a 4% interruption-risk budget.

*Why it's done this way:* cost is linear in fleet composition, but reliability is also a budget. The cheapest all-spot plan may violate availability or retry constraints; the mix calculation names the acceptable risk before spending less.

### 7. Pareto frontier: no free lunch between latency and cost

Many configurations trade lower latency for higher cost. A configuration is Pareto-efficient if no other configuration is both cheaper and faster. The frontier keeps only the decisions worth discussing.

```python
configs_w = np.array([
    [2, 210, 2.4], [3, 155, 3.6], [4, 118, 4.8], [5, 130, 5.5],
    [6, 96, 7.2], [4, 140, 5.0], [5, 125, 5.2], [7, 98, 9.0]
], dtype=float)  # columns: replicas, p95 latency, hourly cost.
lat_w = configs_w[:, 1]
cost_w = configs_w[:, 2]
pareto_w = np.ones(len(configs_w), dtype=bool)
for i_w in range(len(configs_w)):
    dominated_w = (lat_w <= lat_w[i_w]) & (cost_w <= cost_w[i_w]) & ((lat_w < lat_w[i_w]) | (cost_w < cost_w[i_w]))
    pareto_w[i_w] = not np.any(dominated_w)
print("Pareto config indexes:", np.where(pareto_w)[0])
assert np.array_equal(np.where(pareto_w)[0], np.array([0, 1, 2, 4]))
```
▶ What you'll see: dominated options disappear because another option is strictly better on both axes.

```python
plt.figure(figsize=(5, 3.4))
plt.scatter(cost_w[~pareto_w], lat_w[~pareto_w], color="gray", label="dominated")
plt.scatter(cost_w[pareto_w], lat_w[pareto_w], color="crimson", label="Pareto frontier")
front_order_w = np.argsort(cost_w[pareto_w])
plt.plot(cost_w[pareto_w][front_order_w], lat_w[pareto_w][front_order_w], color="crimson")
plt.title("7: latency-vs-cost Pareto frontier")
plt.xlabel("cost ($/hour)")
plt.ylabel("p95 latency (ms)")
plt.legend()
plt.show()
```
▶ What you'll see: look for the red lower-left boundary; gray points are worse choices.

*Why it's done this way:* a scalar objective can hide tradeoffs. Pareto filtering first removes obviously bad decisions, then humans or product owners can choose how much extra cost is worth a lower p95.

### 8. Cascades and early exit spend large models only when needed

A cascade sends easy requests to a cheap model and hard requests to a larger fallback. If confidence is high, we exit early; otherwise we pay extra latency and cost. The optimization variable is the threshold that decides which requests are easy.

```python
conf_w = np.array([0.97, 0.92, 0.88, 0.80, 0.73, 0.66, 0.58, 0.49, 0.40, 0.31])
small_correct_w = conf_w > 0.70  # toy rule: small model is reliable above 0.70.
large_correct_w = np.ones_like(small_correct_w, dtype=bool)
threshold_w = 0.75
cheap_route_w = conf_w >= threshold_w
quality_w = np.mean(np.where(cheap_route_w, small_correct_w, large_correct_w))
latency_w = np.mean(np.where(cheap_route_w, 10.0, 10.0 + 60.0))
print("cheap-route fraction:", round(float(np.mean(cheap_route_w)), 2), "quality:", round(float(quality_w), 2), "expected latency:", round(float(latency_w), 1))
assert round(float(np.mean(cheap_route_w)), 2) == 0.4 and round(float(latency_w), 1) == 46.0
```
▶ What you'll see: 40% of requests exit after the small model, lowering expected latency while preserving toy quality.

```python
thresholds_w = np.linspace(0.3, 0.95, 14)
latencies_cascade_w = []
qualities_cascade_w = []
for t_w in thresholds_w:
    route_w = conf_w >= t_w
    latencies_cascade_w.append(float(np.mean(np.where(route_w, 10.0, 70.0))))
    qualities_cascade_w.append(float(np.mean(np.where(route_w, small_correct_w, large_correct_w))))
plt.figure(figsize=(5, 3))
plt.plot(latencies_cascade_w, qualities_cascade_w, marker="o", color="purple")
plt.title("8: cascade threshold tradeoff")
plt.xlabel("expected latency (ms)")
plt.ylabel("quality proxy")
plt.show()
```
▶ What you'll see: lowering latency by exiting early can eventually reduce quality when hard requests skip fallback.

*Why it's done this way:* expected latency is the cheap-route fraction times cheap latency plus fallback fraction times both stages. Quality is also an expectation over routes. The threshold is good only if the requests it labels easy are truly safe for the small model.

### ✍️ Toy 1 · Tail latency is a percentile, not an average

Percentiles ask where sorted users land. This toy computes p50 and p95 on five requests so the slow tail is visible.

```python
import numpy as np
import matplotlib.pyplot as plt

t1_rng = np.random.default_rng(0)
t1_latencies = np.array([40, 42, 45, 50, 90], dtype=float)  # -> [40. 42. 45. 50. 90.]
print("latencies ms:", t1_latencies.tolist())              # -> [40.0, 42.0, 45.0, 50.0, 90.0]
t1_sorted = np.sort(t1_latencies)                           # -> [40. 42. 45. 50. 90.]
print("sorted latencies:", t1_sorted.tolist())             # -> [40.0, 42.0, 45.0, 50.0, 90.0]
t1_p50 = float(np.percentile(t1_latencies, 50))             # -> 45.0
t1_p95 = float(np.percentile(t1_latencies, 95))             # -> 82.0
t1_tail_ratio = t1_p95 / t1_p50                             # -> 1.8222222222222222
print("p50:", round(t1_p50, 1))                            # -> 45.0
print("p95:", round(t1_p95, 1))                            # -> 82.0
print("p95 / p50:", round(t1_tail_ratio, 3))               # -> 1.822
plt.figure(figsize=(4.6, 2.8))
plt.plot(t1_sorted, marker="o", color="#4c78a8")
plt.axhline(t1_p50, color="gray", linestyle="--")
plt.axhline(t1_p95, color="#e45756", linestyle="--")
plt.ylabel("ms")
plt.title("Toy 1 · p95 names the tail")
plt.show()
assert round(t1_p95, 1) == 82.0
```
▶ What you'll see: the p95 line sits near the lone 90 ms request, far above the median.

### ✍️ Toy 2 · Roofline throughput is the smaller ceiling

The roofline bound takes the minimum of compute peak and bandwidth times arithmetic intensity.

```python
import numpy as np

t2_rng = np.random.default_rng(0)
t2_peak = 16.0                                               # -> 16.0
t2_bandwidth = 2.0                                           # -> 2.0
t2_intensity = np.array([1.0, 4.0, 10.0])                    # -> [ 1.  4. 10.]
print("compute peak:", t2_peak)                             # -> 16.0
print("bandwidth:", t2_bandwidth)                           # -> 2.0
print("intensity:", t2_intensity.tolist())                  # -> [1.0, 4.0, 10.0]
t2_memory_ceiling = t2_bandwidth * t2_intensity              # -> [ 2.  8. 20.]
print("memory ceilings:", t2_memory_ceiling.tolist())       # -> [2.0, 8.0, 20.0]
t2_roof = np.minimum(t2_peak, t2_memory_ceiling)             # -> [ 2.  8. 16.]
print("roof throughput:", t2_roof.tolist())                 # -> [2.0, 8.0, 16.0]
plt.figure(figsize=(4.6, 2.8))
plt.plot(t2_intensity, t2_roof, marker="o", color="#4c78a8")
plt.axhline(t2_peak, color="black", linestyle="--")
plt.xlabel("FLOPs per byte")
plt.ylabel("throughput")
plt.title("Toy 2 · min(memory, compute)")
plt.show()
assert np.allclose(t2_roof, np.array([2.0, 8.0, 16.0]))
```
▶ What you'll see: low intensity is bandwidth-bound, while high intensity flattens at the compute peak.

### ✍️ Toy 3 · Batching trades compute savings for queue wait

Batching amortizes fixed overhead, but users wait for the batch to fill. This toy adds both terms.

```python
import numpy as np

t3_rng = np.random.default_rng(0)
t3_batch_sizes = np.array([1.0, 2.0, 4.0])                  # -> [1. 2. 4.]
t3_fixed_ms = 8.0                                           # -> 8.0
t3_per_item_ms = 2.0                                        # -> 2.0
print("batch sizes:", t3_batch_sizes.tolist())             # -> [1.0, 2.0, 4.0]
print("fixed ms:", t3_fixed_ms)                            # -> 8.0
print("per item ms:", t3_per_item_ms)                      # -> 2.0
t3_compute = t3_fixed_ms / t3_batch_sizes + t3_per_item_ms  # -> [10.  6.  4.]
print("compute/request:", t3_compute.tolist())             # -> [10.0, 6.0, 4.0]
t3_gap_ms = 2.0                                             # -> 2.0
t3_wait = t3_gap_ms * (t3_batch_sizes - 1) / 2              # -> [0. 1. 3.]
print("queue wait:", t3_wait.tolist())                     # -> [0.0, 1.0, 3.0]
t3_end_to_end = t3_compute + t3_wait                        # -> [10.  7.  7.]
print("end-to-end latency:", t3_end_to_end.tolist())       # -> [10.0, 7.0, 7.0]
plt.figure(figsize=(4.8, 2.8))
plt.plot(t3_batch_sizes, t3_compute, marker="o", label="compute")
plt.plot(t3_batch_sizes, t3_end_to_end, marker="s", label="compute + wait")
plt.xlabel("batch size")
plt.ylabel("ms")
plt.title("Toy 3 · queue wait changes optimum")
plt.legend()
plt.show()
assert np.allclose(t3_end_to_end, np.array([10.0, 7.0, 7.0]))
```
▶ What you'll see: compute keeps falling, but end-to-end latency stops improving once queue wait grows.

### ✍️ Toy 4 · Cache latency and Amdahl speedup use weighted averages

Caching has two computations: expected latency over hit/miss paths and the system-level speedup cap from the uncacheable fraction.

```python
import numpy as np

t4_rng = np.random.default_rng(0)
t4_hit_rate = 0.75                                          # -> 0.75
t4_hit_ms = 2.0                                             # -> 2.0
t4_miss_ms = 20.0                                           # -> 20.0
print("hit rate:", t4_hit_rate)                            # -> 0.75
print("hit ms:", t4_hit_ms)                                # -> 2.0
print("miss ms:", t4_miss_ms)                              # -> 20.0
t4_expected_ms = t4_hit_rate * t4_hit_ms + (1 - t4_hit_rate) * t4_miss_ms  # -> 6.5
print("expected latency ms:", round(t4_expected_ms, 3))     # -> 6.5
t4_cacheable = 0.80                                         # -> 0.8
t4_hit_speedup = t4_miss_ms / t4_hit_ms                     # -> 10.0
t4_amdahl = 1 / ((1 - t4_cacheable) + t4_cacheable / t4_hit_speedup)  # -> 3.5714285714285716
print("hit-path speedup:", round(t4_hit_speedup, 3))        # -> 10.0
print("Amdahl speedup cap:", round(t4_amdahl, 3))           # -> 3.571
plt.figure(figsize=(4.6, 2.8))
plt.bar(["hit", "miss", "expected"], [t4_hit_ms, t4_miss_ms, t4_expected_ms], color=["#54a24b", "#e45756", "#4c78a8"])
plt.ylabel("ms")
plt.title("Toy 4 · expected cache latency")
plt.show()
assert round(t4_amdahl, 3) == 3.571
```
▶ What you'll see: a high hit rate pulls expected latency down, but Amdahl's law still caps total speedup.

### ✍️ Toy 5 · Autoscaling chooses the cheapest SLO-safe replica count

More replicas lower utilization and modeled latency but increase hourly cost. This toy filters by SLO before minimizing cost.

```python
import numpy as np

t5_rng = np.random.default_rng(0)
t5_qps = 12.0                                               # -> 12.0
t5_capacity = 5.0                                           # -> 5.0
t5_replicas = np.array([2, 3, 4])                           # -> [2 3 4]
print("qps:", t5_qps)                                      # -> 12.0
print("capacity/replica:", t5_capacity)                    # -> 5.0
print("replicas:", t5_replicas.tolist())                   # -> [2, 3, 4]
t5_util = t5_qps / (t5_replicas * t5_capacity)              # -> [1.2 0.8 0.6]
print("utilization:", np.round(t5_util, 2).tolist())       # -> [1.2, 0.8, 0.6]
t5_base_ms = 10.0                                           # -> 10.0
t5_latency = t5_base_ms / np.maximum(1 - t5_util, 0.1)      # -> [100.  50.  25.]
print("modeled latency:", np.round(t5_latency, 1).tolist())  # -> [100.0, 50.0, 25.0]
t5_cost = t5_replicas * 3.0                                 # -> [ 6.  9. 12.]
t5_slo = 60.0                                               # -> 60.0
t5_feasible = t5_latency <= t5_slo                          # -> [False  True  True]
print("hourly cost:", t5_cost.tolist())                    # -> [6.0, 9.0, 12.0]
print("SLO feasible:", t5_feasible.tolist())               # -> [False, True, True]
t5_best_idx = np.where(t5_feasible)[0][np.argmin(t5_cost[t5_feasible])]  # -> 1
t5_best_replicas = int(t5_replicas[t5_best_idx])            # -> 3
print("cheapest feasible replicas:", t5_best_replicas)     # -> 3
plt.figure(figsize=(4.8, 2.8))
plt.scatter(t5_cost, t5_latency, s=90, color=np.where(t5_feasible, "#54a24b", "#e45756"))
plt.axhline(t5_slo, color="black", linestyle="--")
plt.xlabel("cost/hour")
plt.ylabel("latency ms")
plt.title("Toy 5 · filter by SLO, then cost")
plt.show()
assert t5_best_replicas == 3
```
▶ What you'll see: two replicas are cheap but violate the SLO, so three replicas are the cheapest acceptable plan.

### ✍️ Toy 6 · Spot mix prices reliability risk

Spot capacity lowers cost but adds interruption risk. This toy finds the largest spot share under a risk budget.

```python
import numpy as np
```

## 🛠️ Setup

```python
import numpy as np  # load NumPy for arrays, percentiles, simulations, and verification checks.
import matplotlib.pyplot as plt  # load Matplotlib for roofline, cost, latency, and frontier plots.
from math import ceil  # use the standard library for integer capacity calculations.
np.random.seed(0)  # make every stochastic example reproducible.

def p95(values):  # compute the 95th percentile as a readable helper.
    return float(np.percentile(np.asarray(values, dtype=float), 95))  # convert inputs and return a scalar.

def expected_latency(hit_rate, hit_ms, miss_ms):  # cache or route expected latency.
    return float(hit_rate * hit_ms + (1 - hit_rate) * miss_ms)  # weighted average over two paths.

def hourly_cost(calls_per_hour, cost_per_call):  # simple unit-cost model.
    return float(calls_per_hour * cost_per_call)  # total spend equals volume times unit price.

def pareto_mask(latencies, costs):  # mark latency-cost options that are not dominated.
    latencies = np.asarray(latencies, dtype=float)  # normalize latency input.
    costs = np.asarray(costs, dtype=float)  # normalize cost input.
    keep = np.ones(len(latencies), dtype=bool)  # start by keeping every option.
    for i in range(len(latencies)):  # test each option against all others.
        dominated = (latencies <= latencies[i]) & (costs <= costs[i]) & ((latencies < latencies[i]) | (costs < costs[i]))  # cheaper-or-faster with one strict win.
        keep[i] = not np.any(dominated)  # drop options dominated by at least one other option.
    return keep  # return the efficient frontier mask.
```
