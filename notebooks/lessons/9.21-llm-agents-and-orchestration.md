# 9.21 — LLM Agents & Orchestration

LLM agents wrap a language-model-like policy in a control loop: keep state, retrieve a small memory, plan the next move, call tools, observe the result, and decide whether to stop. In this lesson, the "LLM" is deliberately tiny and rule-based so the orchestration math is visible: every score, transition, memory choice, and vote is built from NumPy or plain Python rather than hidden inside an API.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build agent orchestration one idea at a time. Run each cell in order and read the printed intermediate values — every state update, ReAct decision, dependency rule, and stopping condition is spelled out so nothing is a black box. This walkthrough is self-contained (it imports what it needs) and uses a `_w` suffix on its variables so it never clashes with the examples below.

### 1. State, memory, and the agent loop

An agent is not just one model call. It is a recurrence: state goes in, a plan is chosen, an action is executed, an observation comes back, and the next state is formed. The lesson formula is

$$s_{t+1}=\mathrm{observe}(\mathrm{act}(\mathrm{plan}(s_t,m_t))).$$

Here `s_t` is a tiny dictionary, `m_t` is retrieved memory, and the plan/action/observation functions are pure Python so we can inspect every term.

```python
state_w = {"goal": "answer 2+3", "done": False, "answer": None, "trace": []}  # initial state s_0.
memory_w = ["calculator handles arithmetic", "stop after final answer", "search is for facts"]  # tiny memory store m.
print("initial state:", state_w)  # inspect the state before the loop starts.
print("memory count:", len(memory_w))  # inspect how much long-term context is available.
```
▶ What you'll see: a goal with no answer yet, plus three memory snippets the controller can consult.

```python
def plan_w(s_w, m_w):  # choose the next intended operation from state and memory.
    if s_w["done"]:
        return "stop"  # terminal states should not keep planning.
    return "calculate" if "2+3" in s_w["goal"] and "calculator handles arithmetic" in m_w else "ask"

def act_w(plan_name_w):  # execute the chosen operation.
    if plan_name_w == "calculate":
        return {"tool": "calculator", "result": 5}  # a toy tool result.
    return {"tool": "none", "result": "unknown"}

def observe_w(s_w, action_w):  # fold the observation back into state.
    new_s_w = dict(s_w)  # copy so the transition is explicit.
    new_s_w["trace"] = s_w["trace"] + [(action_w["tool"], action_w["result"])]
    if action_w["result"] == 5:
        new_s_w["answer"] = 5
        new_s_w["done"] = True
    return new_s_w

plan1_w = plan_w(state_w, memory_w)  # plan(s_t, m_t).
action1_w = act_w(plan1_w)  # act(plan).
state1_w = observe_w(state_w, action1_w)  # observe(action) -> s_{t+1}.
print("plan:", plan1_w, "action:", action1_w)  # inspect the middle of the recurrence.
print("next state:", state1_w)  # inspect s_1.
assert state1_w["answer"] == 5 and state1_w["done"] is True  # verify the toy transition.
```
▶ What you'll see: one loop step plans `calculate`, calls the calculator, records the observation, and marks the task done.

```python
plt.figure(figsize=(5, 2.8))  # create a compact state-machine sketch.
xs_w = np.arange(4)  # positions for the four loop nodes.
labels_w = ["state", "plan", "act", "observe"]  # conceptual loop pieces.
plt.scatter(xs_w, np.zeros_like(xs_w), s=550, color="teal")  # draw the nodes.
for i_w, label_w in enumerate(labels_w):
    plt.text(i_w, 0, label_w, color="white", ha="center", va="center")  # label each node.
for i_w in range(3):
    plt.arrow(i_w + 0.25, 0, 0.45, 0, head_width=0.05, color="black", length_includes_head=True)  # forward arrows.
plt.arrow(3.0, -0.08, -2.7, -0.28, head_width=0.05, color="gray", length_includes_head=True)  # loop back.
plt.ylim(-0.55, 0.35); plt.axis("off"); plt.title("1: an agent is a state-update loop"); plt.show()
```
▶ What you'll see: state flows through plan → act → observe, then loops back unless termination stops it.

*Why it's done this way: the recurrence separates reasoning from side effects. `plan` can be scored and audited before any tool runs, `act` is the only side-effect boundary, and `observe` is the mathematical state transition that makes the next step depend on evidence rather than wishful text.*

### 2. Planning with dependencies

Plans are often small dependency graphs. A step is ready only when every prerequisite is complete. The content block's worked plan has four steps with dependencies $A\to C$, $B\to C$, and $C\to D$, so two steps are initially ready: `A` and `B`.

```python
steps_w = ["A", "B", "C", "D"]  # four plan nodes.
deps_w = {"A": [], "B": [], "C": ["A", "B"], "D": ["C"]}  # prerequisites for each node.
completed_w = set()  # no work is done at t=0.
ready_w = [s for s in steps_w if s not in completed_w and all(d in completed_w for d in deps_w[s])]  # dependency rule.
print("initially ready:", ready_w)  # should be A and B.
assert ready_w == ["A", "B"]  # verify the lesson number: two ready steps.
```
▶ What you'll see: only `A` and `B` have no unmet prerequisites, so the controller has two legal first moves.

```python
adj_w = np.array([[0, 0, 1, 0],  # A points to C.
                  [0, 0, 1, 0],  # B points to C.
                  [0, 0, 0, 1],  # C points to D.
                  [0, 0, 0, 0]]) # D has no outgoing dependency.
print("dependency adjacency:\n", adj_w)  # inspect graph structure as a matrix.
plt.figure(figsize=(4.5, 3))  # draw dependency matrix.
plt.imshow(adj_w, cmap="Blues", aspect="auto")  # color edges in the DAG.
plt.xticks(range(4), steps_w); plt.yticks(range(4), steps_w)
plt.title("2: dependency edges in the plan"); plt.colorbar(label="edge"); plt.show()
```
▶ What you'll see: the two edges into C and one edge into D form a tiny directed acyclic graph.

```python
order_w = []  # execution order produced by the scheduler.
completed_w = set()  # reset completed set.
while len(order_w) < len(steps_w):
    ready_w = [s for s in steps_w if s not in completed_w and all(d in completed_w for d in deps_w[s])]  # legal nodes.
    chosen_w = ready_w[0]  # deterministic tie-breaker for inspectability.
    completed_w.add(chosen_w); order_w.append(chosen_w)  # transition: chosen step is now done.
print("scheduled order:", order_w)  # one valid topological order.
assert order_w == ["A", "B", "C", "D"]  # verify this deterministic schedule.
```
▶ What you'll see: the orchestrator can run A then B, but it must wait on C until both are complete.

*Why it's done this way: dependency scheduling prevents an agent from executing a step whose inputs do not exist yet. Mathematically, the ready mask is an indicator function over prerequisites; changing that mask changes the reachable actions, so orchestration controls behavior before generation ever starts.*

### 3. ReAct: reasoning traces choose tool actions

A ReAct loop alternates a short reasoning trace with an action. In a production system the trace may be text from an LLM; here it is a rule-based toy policy with action scores `[0.2, 0.6, 0.4]`. The controller picks the largest legal score, then records the observation.

```python
actions_w = np.array(["search", "calculate", "finish"])  # candidate tool actions.
scores_w = np.array([0.2, 0.6, 0.4])  # toy policy scores from a rule-based "LLM".
choice_w = int(np.argmax(scores_w))  # controller chooses the highest score.
print("action scores:", dict(zip(actions_w, scores_w)))  # inspect the policy distribution.
print("chosen action:", actions_w[choice_w], "score:", scores_w[choice_w])  # expected calculate, 0.6.
assert scores_w[choice_w] == 0.6 and actions_w[choice_w] == "calculate"  # verify lesson number.
```
▶ What you'll see: `calculate` wins because its score 0.6 is larger than search's 0.2 and finish's 0.4.

```python
def toy_llm_scores_w(question_w, scratchpad_w):  # a deterministic stand-in for model logits.
    needs_math_w = any(ch.isdigit() for ch in question_w) and "+" in question_w  # simple math detector.
    has_observation_w = "observation" in scratchpad_w  # know whether a tool already ran.
    if has_observation_w:
        return np.array([0.1, 0.1, 0.8])  # after evidence, finish should dominate.
    return np.array([0.2, 0.6, 0.4]) if needs_math_w else np.array([0.6, 0.1, 0.3])

scratch_w = "thought: need exact arithmetic"  # ReAct scratchpad before tool call.
scores2_w = toy_llm_scores_w("what is 2+3?", scratch_w)  # compute action scores.
print("scores before observation:", dict(zip(actions_w, scores2_w)))  # inspect first policy.
```
▶ What you'll see: before a tool observation exists, the calculator action receives the largest score.

```python
trace_w = []  # ReAct trace of thought/action/observation triples.
for t_w in range(2):
    scratch_text_w = " ".join([x[2] for x in trace_w if x[0] == "observation"])  # previous observations.
    policy_w = toy_llm_scores_w("what is 2+3?", scratch_text_w)  # score actions from current scratchpad.
    action_w = actions_w[int(np.argmax(policy_w))]  # choose action.
    obs_w = "observation: 5" if action_w == "calculate" else "observation: final 5"  # toy environment.
    trace_w.append(("thought", "choose highest legal score", scratch_text_w))
    trace_w.append(("action", action_w, f"score={policy_w.max():.1f}"))
    trace_w.append(("observation", action_w, obs_w))
print("ReAct trace:")
for row_w in trace_w:
    print(row_w)
assert trace_w[1][1] == "calculate" and trace_w[4][1] == "finish"  # first calculate, then finish.
```
▶ What you'll see: the first action calls the calculator; after the observation exists, the next action is `finish`.

```python
score_matrix_w = np.vstack([toy_llm_scores_w("what is 2+3?", ""), toy_llm_scores_w("what is 2+3?", "observation: 5")])  # compare action scores before and after evidence.
x_w = np.arange(len(actions_w))  # action positions.
plt.figure(figsize=(5, 3))  # create a compact ReAct score-shift plot.
plt.bar(x_w - 0.18, score_matrix_w[0], width=0.36, label="before observation", color="lightgray")  # first-step scores.
plt.bar(x_w + 0.18, score_matrix_w[1], width=0.36, label="after observation", color="teal")  # post-tool scores.
plt.xticks(x_w, actions_w); plt.ylim(0, 1); plt.ylabel("controller score")
plt.title("3: ReAct observation shifts the next action"); plt.legend(); plt.show()
```
▶ What you'll see: calculator is highest before evidence, then finish becomes highest after the tool observation enters the scratchpad.

*Why it's done this way: ReAct makes hidden control decisions explicit. The scratchpad is not magic memory; it is part of the state that changes the next action scores, so observing `5` should raise the finish score and lower the need for more tools.*

### 4. Memory retrieval and prompt budget

Agents rarely stuff all memory into the prompt. They retrieve a small top-k set, then act using that compressed context. If we retrieve 3 memories from a store of 10, the prompt uses only 30% of the memory store.

```python
memories_w = np.array(["math tool", "weather fact", "addition", "calendar", "subtraction",
                       "maps", "stop rule", "sports", "multiplication", "email"])  # toy memory store.
query_terms_w = {"math", "addition", "stop"}  # what the current task needs.
sim_w = np.array([sum(term in m for term in query_terms_w) for m in memories_w], dtype=float)  # overlap score.
print("memory scores:", list(zip(memories_w, sim_w.astype(int))))  # inspect retriever evidence.
```
▶ What you'll see: memories about math, addition, and stopping receive nonzero retrieval scores.

```python
k_w = 3  # retrieve only the top 3 snippets.
top_w = np.argsort(sim_w)[::-1][:k_w]  # indices of highest-scoring memories.
retrieved_w = memories_w[top_w]  # prompt memory m_t.
fraction_w = k_w / len(memories_w)  # prompt budget fraction.
print("retrieved:", retrieved_w.tolist())  # inspect selected context.
print("memory fraction used:", round(fraction_w, 2))  # 3/10 = 0.30.
assert round(fraction_w, 2) == 0.30  # verify lesson number.
```
▶ What you'll see: three relevant snippets are chosen, which is 30% of the 10-snippet store.

```python
plt.figure(figsize=(6, 3))  # visualize retrieval scores.
plt.bar(np.arange(len(memories_w)), sim_w, color=["teal" if i in top_w else "lightgray" for i in range(len(memories_w))])
plt.xticks(np.arange(len(memories_w)), memories_w, rotation=45, ha="right")
plt.ylabel("query overlap score"); plt.title("4: top-k memory retrieval"); plt.tight_layout(); plt.show()
```
▶ What you'll see: only the selected top-k bars are highlighted, showing exactly what enters the prompt.

*Why it's done this way: retrieval is a lossy projection from a large memory store to a small context window. The top-k operator trades recall for cost; if the score misses a relevant memory, every later action inherits that state error.*

### 5. Termination as a controller decision

An agent needs a stopping rule. If the termination probability after success is 0.8, the continuation probability is 0.2. Without that explicit controller, a successful agent can keep planning and waste tool calls.

```python
success_w = True  # the latest observation satisfied the goal.
p_stop_w = 0.8 if success_w else 0.1  # controller's termination probability.
p_continue_w = 1 - p_stop_w  # remaining probability mass.
print("P(stop):", p_stop_w, "P(continue):", round(p_continue_w, 1))  # inspect the complement.
assert round(p_continue_w, 1) == 0.2  # verify lesson number.
```
▶ What you'll see: success makes stopping likely, but a 20% continuation tail remains if the policy is not deterministic.

```python
state_names_w = ["working", "done"]  # two-state Markov controller.
T_w = np.array([[p_continue_w, p_stop_w],  # from working: continue or stop.
                [0.0, 1.0]])              # done is absorbing.
prob_w = np.array([1.0, 0.0])  # start in working.
history_w = []
for step_w in range(5):
    history_w.append(prob_w.copy())  # record state probabilities.
    prob_w = prob_w @ T_w  # next distribution.
history_w = np.array(history_w)
print("done probabilities:", np.round(history_w[:, 1], 3))  # inspect convergence to done.
```
▶ What you'll see: the probability of being done rises quickly because the done state is absorbing.

```python
plt.figure(figsize=(5, 3))  # create termination curve.
plt.plot(history_w[:, 0], marker="o", label="working")  # probability still looping.
plt.plot(history_w[:, 1], marker="o", label="done")  # probability terminated.
plt.title("5: termination probability absorbs the loop"); plt.xlabel("controller step"); plt.ylabel("probability"); plt.legend(); plt.show()
```
▶ What you'll see: `working` decays while `done` climbs toward 1, showing why explicit stop logic bounds the loop.

*Why it's done this way: termination is not a formatting choice; it changes the transition matrix. Making `done` absorbing prevents the recurrence from repeatedly re-entering planning after the task is already solved.*

### 6. Multi-agent orchestration and voting

Orchestration can branch to multiple agents, then combine their answers. Voting helps only when agents provide partly independent errors. In the worked arithmetic, two agent votes `[1, 1, 0]` plus a judge vote `1` gives three positive votes out of four, or 0.750.

```python
agent_votes_w = np.array([1, 1, 0])  # three toy agents: two say yes, one says no.
judge_vote_w = 1  # a judge agent also says yes.
all_votes_w = np.append(agent_votes_w, judge_vote_w)  # aggregate panel.
majority_w = float(np.mean(all_votes_w))  # fraction voting yes.
print("votes:", all_votes_w, "yes fraction:", round(majority_w, 3))  # inspect consensus.
assert round(majority_w, 3) == 0.750  # verify lesson number.
```
▶ What you'll see: the panel has 3 yes votes out of 4, so the majority score is 0.750.

```python
# Simulate correlated versus diverse agents on 200 toy binary tasks.
rng_w = np.random.default_rng(0)  # local reproducibility.
truth_w = rng_w.integers(0, 2, size=200)  # hidden correct labels.
shared_error_w = rng_w.random(200) < 0.25  # one shared failure mode for correlated agents.
correlated_w = np.vstack([np.where(shared_error_w, 1 - truth_w, truth_w) for _ in range(3)])  # all fail together.
diverse_w = np.vstack([np.where(rng_w.random(200) < 0.25, 1 - truth_w, truth_w) for _ in range(3)])  # independent-ish errors.
acc_corr_w = float(np.mean((correlated_w.mean(axis=0) >= 0.5) == truth_w))  # majority accuracy.
acc_div_w = float(np.mean((diverse_w.mean(axis=0) >= 0.5) == truth_w))  # majority accuracy.
print("correlated majority accuracy:", round(acc_corr_w, 3))
print("diverse majority accuracy:", round(acc_div_w, 3))
```
▶ What you'll see: diverse voters usually outperform correlated voters because their errors do not always line up.

```python
plt.figure(figsize=(4.5, 3))  # compare ensemble conditions.
plt.bar(["shared failure", "diverse errors"], [acc_corr_w, acc_div_w], color=["crimson", "seagreen"])
plt.ylim(0, 1); plt.ylabel("majority accuracy"); plt.title("6: voting only helps with diversity"); plt.show()
```
▶ What you'll see: the diverse-error bar is higher, while shared failure modes limit the value of orchestration.

*Why it's done this way: a majority vote reduces variance only when errors are not perfectly correlated. If every agent sees the same prompt and shares the same blind spot, orchestration adds cost without adding independent evidence.*

## 🛠️ Setup

```python
import numpy as np  # load NumPy for arrays, scores, masks, and numerical checks.
import matplotlib.pyplot as plt  # load Matplotlib for loop diagrams, bars, heatmaps, and curves.
from collections import deque  # load a standard-library queue for tiny orchestrators.
np.random.seed(0)  # make every example deterministic across notebook runs.

def toy_calculator(expr):  # define a safe toy arithmetic tool for the inline tasks in this lesson.
    allowed = {"2+3": 5, "4*3": 12, "10-7": 3, "6/2": 3.0}  # fixed task table avoids eval and external calls.
    return allowed.get(expr, None)  # return None when the tool cannot handle the expression.

def retrieve_top_k(query_terms, memories, k):  # define a transparent overlap retriever.
    scores = np.array([sum(term in text for term in query_terms) for text in memories], dtype=float)  # count term matches.
    order = np.argsort(scores)[::-1][:k]  # choose highest scores first.
    return order, scores  # return both indices and scores for inspection.

def choose_action(scores, names):  # define a deterministic controller policy.
    idx = int(np.argmax(scores))  # pick the largest score.
    return names[idx], idx  # return the chosen action and its index.

def show_bar(labels, values, title):  # define a small visualization helper.
    plt.figure(figsize=(4.5, 3))  # start a compact figure.
    plt.bar(labels, values, color="teal")  # draw one bar per value.
    plt.title(title)  # title the diagnostic plot.
    plt.ylabel("value")  # label the numeric axis.
    plt.show()  # display the figure.
```
