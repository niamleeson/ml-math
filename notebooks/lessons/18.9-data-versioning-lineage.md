# 18.9 — Data Versioning & Lineage

Data versioning and lineage make data-centric ML reproducible: a model should not just remember its code, but the exact records, transformations, validation results, and upstream dependencies that produced it. In this lesson, you will build tiny in-memory versioning tools from first principles — content hashes, diffs, Merkle-style deduplication, lineage DAGs, impact tracing, and rollback — using only NumPy, Matplotlib, and Python's `hashlib`.

```python
import numpy as np  # arrays for toy datasets, row ids, scores, and graph matrices.
import matplotlib.pyplot as plt  # compact visual checks for hashes, diffs, and lineage graphs.
import hashlib  # cryptographic content hashes for stable in-memory version ids.
```

### 1. Content hashes: stable IDs for data, not filenames

A dataset version needs an identifier that changes when the **contents** change. A filename or table name is only a pointer; it can be reused after an edit. A content hash turns a canonical byte representation of the rows into a fixed-length fingerprint. If two snapshots produce the same hash, we treat them as the same version; if one value changes, the hash should change dramatically.

```python
rows_w = np.array([[1, 10, 0],
                   [2, 20, 1],
                   [3, 30, 1]], dtype=int)  # row_id, feature, label.
print("snapshot rows:\n", rows_w)
print("shape:", rows_w.shape)
```
▶ What you'll see: a tiny 3-row snapshot with stable row ids and values.

```python
def snapshot_bytes_w(rows):
    rows = np.asarray(rows, dtype=int)
    ordered = rows[np.lexsort(rows.T[::-1])]  # canonical row order prevents order-only hash changes.
    return ";".join(",".join(map(str, row)) for row in ordered).encode("utf-8")

def hash_snapshot_w(rows):
    return hashlib.sha256(snapshot_bytes_w(rows)).hexdigest()[:12]

hash_v1_w = hash_snapshot_w(rows_w)
print("canonical bytes:", snapshot_bytes_w(rows_w))
print("version hash:", hash_v1_w)
assert len(hash_v1_w) == 12
```
▶ What you'll see: the rows become deterministic bytes, then a short SHA-256 fingerprint.

```python
rows_same_order_changed_w = rows_w[[2, 0, 1]]  # same content, different row order.
rows_value_changed_w = rows_w.copy(); rows_value_changed_w[1, 1] = 21  # one feature edit.
print("same content hash:", hash_snapshot_w(rows_same_order_changed_w))
print("one-value edit hash:", hash_snapshot_w(rows_value_changed_w))
assert hash_snapshot_w(rows_same_order_changed_w) == hash_v1_w
assert hash_snapshot_w(rows_value_changed_w) != hash_v1_w
```
▶ What you'll see: reordering rows leaves the hash alone, while one value edit creates a different version id.

*Why it's done this way: the hash is over canonicalized content, not over a mutable name. Sorting removes accidental row-order noise; hashing the resulting bytes gives a reproducibility contract: the same data gives the same id, and changed data gets a new id.*

### 2. Diffs: what changed between versions

A hash answers **whether** a snapshot changed, but ML owners also need to know **how** it changed. We can compare row ids to separate added, removed, kept, and edited records. This is the versioning equivalent of `git diff`: it converts a scary new fingerprint into a human-debuggable change set.

```python
old_rows_w = np.array([[1, 10, 0], [2, 20, 1], [3, 30, 1], [4, 40, 0]], dtype=int)
new_rows_w = np.array([[1, 10, 0], [2, 21, 1], [4, 40, 0], [5, 50, 1]], dtype=int)
print("old ids:", old_rows_w[:, 0])
print("new ids:", new_rows_w[:, 0])
```
▶ What you'll see: id 5 is new, id 3 vanished, and id 2 may have changed.

```python
def row_map_w(rows):
    return {int(row[0]): row.copy() for row in np.asarray(rows, dtype=int)}

old_map_w, new_map_w = row_map_w(old_rows_w), row_map_w(new_rows_w)
old_ids_w, new_ids_w = set(old_map_w), set(new_map_w)
added_w = sorted(new_ids_w - old_ids_w)
removed_w = sorted(old_ids_w - new_ids_w)
kept_w = sorted(old_ids_w & new_ids_w)
edited_w = [rid for rid in kept_w if not np.array_equal(old_map_w[rid], new_map_w[rid])]
print("added:", added_w, "removed:", removed_w, "kept:", kept_w, "edited:", edited_w)
assert added_w == [5] and removed_w == [3] and edited_w == [2]
```
▶ What you'll see: the diff cleanly separates one added row, one removed row, and one edited row.

```python
counts_w = np.array([len(added_w), len(removed_w), len(kept_w), len(edited_w)])
plt.figure(figsize=(4.6, 3))
plt.bar(["added", "removed", "kept", "edited"], counts_w, color=["seagreen", "crimson", "gray", "orange"])
plt.title("2: diff summary between snapshots")
plt.ylabel("row count")
plt.show()
```
▶ What you'll see: a compact count summary; kept rows dominate, while the risky changes are isolated.

*Why it's done this way: set differences on stable row ids expose the semantic change. The hash is excellent for identity, but the diff is what lets a model owner reason about retraining, validation failures, or bad labels.*

### 3. Merkle-style hashes: deduplicate shared chunks

Large datasets should not be copied wholesale whenever one row changes. A Merkle-style design hashes small chunks, then hashes the list of chunk hashes into one root hash. If a chunk is unchanged, it can be reused by the next version; only changed chunks need new storage. This is the same mathematical idea behind many content-addressed stores.

```python
chunked_w = np.array([[1, 10], [2, 20], [3, 30], [4, 40], [5, 50], [6, 60]], dtype=int)
chunk_size_w = 2
chunks_w = [chunked_w[i:i + chunk_size_w] for i in range(0, len(chunked_w), chunk_size_w)]
print("number of chunks:", len(chunks_w))
print("first chunk:\n", chunks_w[0])
```
▶ What you'll see: six rows are split into three small chunks of two rows each.

```python
def hash_array_w(arr):
    text = ";".join(",".join(map(str, row)) for row in np.asarray(arr, dtype=int))
    return hashlib.sha256(text.encode("utf-8")).hexdigest()[:10]

chunk_hashes_v1_w = [hash_array_w(chunk) for chunk in chunks_w]
root_v1_w = hashlib.sha256("|".join(chunk_hashes_v1_w).encode("utf-8")).hexdigest()[:12]
print("chunk hashes v1:", chunk_hashes_v1_w)
print("root hash v1:", root_v1_w)
```
▶ What you'll see: each chunk has its own id, and the root hash summarizes the ordered chunk ids.

```python
chunked_v2_w = chunked_w.copy(); chunked_v2_w[2, 1] = 31  # edit row 3, which lives in chunk 1.
chunks_v2_w = [chunked_v2_w[i:i + chunk_size_w] for i in range(0, len(chunked_v2_w), chunk_size_w)]
chunk_hashes_v2_w = [hash_array_w(chunk) for chunk in chunks_v2_w]
reused_w = np.array([a == b for a, b in zip(chunk_hashes_v1_w, chunk_hashes_v2_w)])
print("chunk hashes v2:", chunk_hashes_v2_w)
print("reused chunks:", reused_w.astype(int), "count:", int(reused_w.sum()))
assert int(reused_w.sum()) == 2
```
▶ What you'll see: only the middle chunk changes; two of three chunks are reused exactly.

```python
plt.figure(figsize=(4.8, 2.5))
plt.imshow(reused_w[None, :], cmap="Greens", aspect="auto", vmin=0, vmax=1)
plt.yticks([]); plt.xticks(range(3), ["chunk0", "chunk1", "chunk2"])
plt.title("3: Merkle-style reuse (green = unchanged)")
plt.show()
```
▶ What you'll see: the changed chunk stands out; unchanged chunks remain reusable across versions.

*Why it's done this way: hashing chunks turns storage into a tree of content identities. The root detects any change, while lower-level hashes localize the change and make deduplication possible.*

### 4. Lineage DAGs: transformations are part of the version

Knowing the input table is not enough. A reproducible training set also needs the filter rule, join rule, label rule, feature code, and validation status that produced it. We store those dependencies as a directed acyclic graph (DAG): nodes are versions or transforms, and edges say "this output depends on that input."

```python
nodes_w = ["raw", "filter:x>=20", "clean", "square", "features", "trainset", "model"]
edges_w = [("raw", "filter:x>=20"), ("filter:x>=20", "clean"), ("clean", "square"),
           ("square", "features"), ("features", "trainset"), ("trainset", "model")]
node_index_w = {name: i for i, name in enumerate(nodes_w)}
adj_w = np.zeros((len(nodes_w), len(nodes_w)), dtype=int)
for src_w, dst_w in edges_w:
    adj_w[node_index_w[src_w], node_index_w[dst_w]] = 1
print("nodes:", nodes_w)
print("adjacency rows -> columns:\n", adj_w)
```
▶ What you'll see: a small dependency matrix with arrows from raw data through transforms to the model.

```python
raw_values_w = np.array([1, 2, 3])
clean_values_w = raw_values_w[raw_values_w >= 2]
feature_values_w = clean_values_w ** 2
print("raw:", raw_values_w, "clean:", clean_values_w, "features:", feature_values_w)
assert np.array_equal(feature_values_w, np.array([4, 9]))
```
▶ What you'll see: the transform parameters reproduce the exact feature values `{4, 9}` from raw `{1,2,3}`.

```python
xpos_w = np.arange(len(nodes_w))
ypos_w = np.zeros(len(nodes_w))
plt.figure(figsize=(8, 2.6))
for src_w, dst_w in edges_w:
    i_w, j_w = node_index_w[src_w], node_index_w[dst_w]
    plt.annotate("", xy=(xpos_w[j_w] - 0.15, ypos_w[j_w]), xytext=(xpos_w[i_w] + 0.15, ypos_w[i_w]),
                 arrowprops=dict(arrowstyle="->", color="gray"))
plt.scatter(xpos_w, ypos_w, s=500, color="lightblue", edgecolor="black")
for i_w, name_w in enumerate(nodes_w):
    plt.text(xpos_w[i_w], ypos_w[i_w], name_w, ha="center", va="center", fontsize=8)
plt.axis("off"); plt.title("4: lineage DAG from raw data to model"); plt.show()
```
▶ What you'll see: a left-to-right lineage graph; the model is downstream of both data and transform choices.

*Why it's done this way: a DAG makes reproducibility a graph property. If every output stores its parents and transform parameters, rerunning the path from raw data can reconstruct the training set instead of relying on memory or mutable tables.*

### 5. Impact tracing and rollback: graph queries on versions

When a bad snapshot is discovered, the practical question is "which models used it?" Lineage turns that into a downstream graph search. When quality scores are versioned too, rollback becomes a deterministic query: choose the latest earlier version whose validation score passes the threshold.

```python
versions_w = np.array([1, 2, 3, 4])
quality_w = np.array([0.91, 0.93, 0.62, 0.94])
threshold_w = 0.90
bad_version_w = 3
print("quality scores:", quality_w)
print("pass mask:", (quality_w >= threshold_w).astype(int))
assert quality_w[2] == 0.62
```
▶ What you'll see: version 3 is the obvious failed snapshot, while versions 1, 2, and 4 pass.

```python
previous_w = versions_w[versions_w < bad_version_w]
previous_scores_w = quality_w[versions_w < bad_version_w]
rollback_w = int(previous_w[previous_scores_w >= threshold_w][-1])
print("rollback target before bad v3:", rollback_w)
assert rollback_w == 2
```
▶ What you'll see: the safe rollback target is version 2, the latest earlier passing version.

```python
impact_edges_w = [("D1", "M0"), ("D2", "M1"), ("D3", "M1"), ("D3", "M2"), ("D4", "M3")]
bad_node_w = "D3"
impacted_w = sorted(dst for src, dst in impact_edges_w if src == bad_node_w)
print("bad snapshot:", bad_node_w)
print("downstream impacted models:", impacted_w)
assert impacted_w == ["M1", "M2"]
```
▶ What you'll see: two models are downstream of the bad data version and need attention.

```python
plt.figure(figsize=(5, 3))
plt.plot(versions_w, quality_w, marker="o", color="teal")
plt.axhline(threshold_w, color="black", linestyle="--", label="pass threshold")
plt.scatter([bad_version_w], [quality_w[bad_version_w - 1]], color="red", s=90, label="bad v3")
plt.scatter([rollback_w], [quality_w[rollback_w - 1]], color="green", s=90, label="rollback v2")
plt.xticks(versions_w); plt.ylim(0.5, 1.0); plt.ylabel("validation score")
plt.title("5: rollback to latest earlier passing version")
plt.legend(); plt.show()
```
▶ What you'll see: version 3 falls below the threshold; version 2 is the last passing point before it.

*Why it's done this way: versioned quality scores prevent guesswork, and lineage edges define the blast radius. Rollback and impact tracing are not separate tricks; they are queries over the same version graph.*

### Basic 1 — Hash one row

**Goal.** Convert one record into a content hash, because versioning starts by giving data content a stable identity. We build it in 2 steps.

```python
row_b1 = np.array([101, 7, 1], dtype=int) # Store one record as row_id, feature, label.

```
▶ What you'll see: the row becomes the string `101,7,1` before hashing.

```python
hash_b1 = hashlib.sha256(row_text_b1.encode("utf-8")).hexdigest()[:12] # Hash the row bytes and keep a short readable prefix.
print("row hash:", hash_b1) # Inspect the stable row identity.
assert len(hash_b1) == 12 # Verify the lesson uses a 12-character prefix.
```
▶ What you'll see: a short hexadecimal fingerprint for that exact row content.

👀 Takeaway: hashes identify content, not variable names or storage locations.

### Basic 2 — Hash a snapshot canonically

**Goal.** Hash an entire toy dataset after sorting rows, because a version id should not change just because rows arrive in a different order. We build it in 3 steps.

```python
rows_b2 = np.array([[2, 20, 1], [1, 10, 0], [3, 30, 1]], dtype=int) # Create rows in non-sorted order.
print("input rows:\n", rows_b2) # Inspect the arrival order before canonicalization.
```
▶ What you'll see: row id 2 appears before row id 1.

```python
ordered_b2 = rows_b2[np.argsort(rows_b2[:, 0])] # Sort by row id so the same set of records has one canonical order.
text_b2 = ";".join(",".join(map(str, row)) for row in ordered_b2) # Serialize sorted rows with semicolon row separators.
print("canonical text:", text_b2) # Inspect the exact snapshot bytes in human-readable form.
```

```python
hash_b2 = hashlib.sha256(text_b2.encode("utf-8")).hexdigest()[:12] # Hash the canonical snapshot content.
print("snapshot hash:", hash_b2) # Inspect the version id for the whole dataset.
assert ordered_b2[0, 0] == 1 and ordered_b2[-1, 0] == 3 # Verify canonical order by row id.
```
▶ What you'll see: sorting produces a stable snapshot string before hashing.

👀 Takeaway: canonicalization keeps harmless ordering differences from creating fake versions.

### Basic 3 — Prove one value changes the hash

**Goal.** Edit one feature and compare hashes, because content-addressed versioning should flag even small data changes. We build it in 2 steps.

```python
rows_b3 = np.array([[1, 10, 0], [2, 20, 1], [3, 30, 1]], dtype=int) # Define a baseline snapshot.
changed_b3 = rows_b3.copy() # Copy it so the original remains available for comparison.

print("old row 2:", rows_b3[1], "new row 2:", changed_b3[1]) # Inspect the exact edit.
```
▶ What you'll see: only the middle feature changed from 20 to 21.

```python
text_old_b3 = ";".join(",".join(map(str, row)) for row in rows_b3) # Serialize old content.
text_new_b3 = ";".join(",".join(map(str, row)) for row in changed_b3) # Serialize edited content.
hash_old_b3 = hashlib.sha256(text_old_b3.encode("utf-8")).hexdigest()[:12] # Hash old snapshot.
hash_new_b3 = hashlib.sha256(text_new_b3.encode("utf-8")).hexdigest()[:12] # Hash new snapshot.
print("old hash:", hash_old_b3, "new hash:", hash_new_b3) # Compare version ids.
assert hash_old_b3 != hash_new_b3 # Verify one value edit creates a new content identity.
```

▶ What you'll see: the two short hashes are completely different.

👀 Takeaway: content hashes are sensitive to the bytes that define the dataset.

### Basic 6 — Hash chunks for deduplication

**Goal.** Split rows into chunks and hash each chunk, because unchanged chunks can be reused across dataset versions. We build it in 3 steps.

```python
rows_b6 = np.array([[1, 10], [2, 20], [3, 30], [4, 40]], dtype=int) # Define four rows of feature data.
chunks_b6 = [rows_b6[:2], rows_b6[2:]] # Split into two fixed-size chunks.
print("chunk shapes:", [chunk.shape for chunk in chunks_b6]) # Inspect the chunk layout.
```
▶ What you'll see: the data is divided into two 2-row chunks.

```python
texts_b6 = [";".join(",".join(map(str, row)) for row in chunk) for chunk in chunks_b6] # Serialize each chunk independently.
hashes_b6 = [hashlib.sha256(text.encode("utf-8")).hexdigest()[:10] for text in texts_b6] # Hash each chunk's content.
print("chunk hashes:", hashes_b6) # Inspect per-chunk identities.
```

```python
root_b6 = hashlib.sha256("|".join(hashes_b6).encode("utf-8")).hexdigest()[:12] # Hash the ordered chunk ids into a root version id.
print("root hash:", root_b6) # Inspect the dataset-level Merkle-style identity.
assert len(hashes_b6) == 2 and len(root_b6) == 12 # Verify the expected number and size of ids.
```
▶ What you'll see: two chunk ids roll up into one root id.

👀 Takeaway: chunk hashes make it possible to reuse unchanged pieces of a dataset.

### Basic 7 — Detect chunk reuse

**Goal.** Edit one row and identify which chunks can be reused, because Merkle-style storage localizes changes. We build it in 2 steps.

```python
old_b7 = np.array([[1, 10], [2, 20], [3, 30], [4, 40]], dtype=int) # Define an old two-chunk snapshot.
new_b7 = old_b7.copy(); new_b7[2, 1] = 31 # Edit row 3, which belongs to the second chunk.
print("edited row old/new:", old_b7[2], new_b7[2]) # Inspect the localized change.
```
▶ What you'll see: only row 3's feature changes.

```python
old_chunks_b7 = [old_b7[:2], old_b7[2:]] # Split the old snapshot into chunks.
new_chunks_b7 = [new_b7[:2], new_b7[2:]] # Split the new snapshot the same way.
old_hashes_b7 = [hashlib.sha256(str(chunk.tolist()).encode("utf-8")).hexdigest()[:10] for chunk in old_chunks_b7] # Hash old chunks.
new_hashes_b7 = [hashlib.sha256(str(chunk.tolist()).encode("utf-8")).hexdigest()[:10] for chunk in new_chunks_b7] # Hash new chunks.
reuse_b7 = np.array([a == b for a, b in zip(old_hashes_b7, new_hashes_b7)]) # Compare chunk identities.

```
▶ What you'll see: chunk 0 is reused and chunk 1 is replaced.

👀 Takeaway: Merkle-style hashes avoid copying unchanged chunks when a small edit occurs.

### Basic 9 — Build a tiny lineage adjacency matrix

```python
nodes_b9 = ["raw", "clean", "features", "model"] # Name four lineage nodes.
```

```python
adj_b9 = np.zeros((len(nodes_b9), len(nodes_b9)), dtype=int) # Allocate a directed adjacency matrix.

```

👀 Takeaway: lineage DAGs make dependency tracking explicit and queryable.

### Basic 10 — Roll back to the latest passing version

**Goal.** Pick the latest previous version that passed validation, because rollback should be a deterministic rule rather than a guess. We build it in 2 steps.

```python
versions_b10 = np.array([1, 2, 3, 4]) # Define four snapshot versions.
scores_b10 = np.array([0.91, 0.93, 0.62, 0.94]) # Store versioned validation quality scores.
threshold_b10 = 0.90 # Define the pass threshold.
print("scores:", scores_b10) # Inspect quality history.
```
▶ What you'll see: version 3 failed badly while the others passed.
