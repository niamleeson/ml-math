# 20.16 — Streaming & Real-Time ML

Streaming ML turns event time into continuously updated features and decisions while accepting that real systems deliver events late, out of order, and under capacity limits. In this lesson, we build the core machinery from scratch with NumPy and the standard library: event-time windows, watermarks, online statistics, compact stream summaries, and online SGD.

### 1. Event time and processing time

A stream has two clocks: **event time**, when the action happened, and **processing time**, when our system saw it. Real-time ML features usually need event time, because a delayed mobile event should still update the historical minute when it occurred, not the minute when the server finally received it.

```python
event_time_w = np.array([1., 3., 7., 4., 12., 9.])
arrival_time_w = np.array([1.2, 3.1, 7.2, 8.5, 12.2, 13.0])
value_w = np.array([2., 1., 3., 5., 4., 2.])
order_w = np.argsort(arrival_time_w)
print("event-time order:", event_time_w[np.argsort(event_time_w)])
print("arrival-order event times:", event_time_w[order_w])
print("delays:", np.round(arrival_time_w - event_time_w, 2))
```
▶ What you'll see: the event at time 4 arrives after the event at time 7, so arrival order is not historical order.

```python
plt.figure(figsize=(5, 3))
plt.scatter(event_time_w, arrival_time_w, s=90, color="teal")
plt.plot([0, 14], [0, 14], "k--", linewidth=1, label="no delay")
plt.xlabel("event time")
plt.ylabel("arrival / processing time")
plt.title("1: out-of-order stream arrivals")
plt.legend()
plt.show()
```
▶ What you'll see: delayed events sit above the diagonal; the farther above, the more they can rewrite older event-time features.

*Why it's done this way:* a feature like “clicks in the last 5 minutes” is mathematically a function of event timestamps. Replacing event time with processing time changes the variable itself, so the model learns from queue behavior instead of user behavior.

### 2. Tumbling windows

A **tumbling window** partitions time into disjoint intervals such as $[0,5),[5,10),[10,15)$. The bucket id is $\lfloor t/W\rfloor$, so every event belongs to exactly one window.

```python
width_w = 5.0
window_id_w = np.floor(event_time_w / width_w).astype(int)
sums_w = defaultdict(float)
for wid_w, val_w in zip(window_id_w, value_w):
    sums_w[int(wid_w)] += float(val_w)
print("window ids:", window_id_w)
print("tumbling sums:", dict(sorted(sums_w.items())))
assert sums_w[0] == 8.0 and sums_w[1] == 5.0 and sums_w[2] == 4.0
```
▶ What you'll see: events at minutes 1, 3, and 4 contribute to $[0,5)$; minutes 7 and 9 contribute to $[5,10)$.

```python
plt.figure(figsize=(5, 3))
plt.bar(["[0,5)", "[5,10)", "[10,15)"], [sums_w[0], sums_w[1], sums_w[2]], color="teal")
plt.ylabel("sum(value)")
plt.title("2: tumbling-window sums")
plt.show()
```
▶ What you'll see: non-overlapping bars, one aggregate per fixed event-time interval.

*Why it's done this way:* `floor(t / W)` creates a partition, so no event is double-counted and no event is omitted. That makes tumbling windows cheap and easy to reconcile with batch tables.

### 3. Sliding windows

A **sliding window** answers a moving question: at query time $q$, include events in $(q-W,q]$. Sliding windows are smoother than tumbling windows because the boundary moves with the query time instead of jumping at fixed bucket edges.

```python
query_w = np.arange(5., 15.1, 2.5)
slide_counts_w = []
for q_w in query_w:
    mask_w = (event_time_w > q_w - width_w) & (event_time_w <= q_w)
    slide_counts_w.append(int(np.sum(mask_w)))
print("query times:", query_w)
print("counts in last 5 minutes:", slide_counts_w)
assert slide_counts_w[:3] == [3, 3, 2]
```
▶ What you'll see: each query time gets its own recent-history count.

```python
plt.figure(figsize=(5, 3))
plt.step(query_w, slide_counts_w, where="post", color="purple")
plt.xlabel("query event time")
plt.ylabel("count in (q-5,q]")
plt.title("3: sliding-window counts over time")
plt.show()
```
▶ What you'll see: the aggregate changes as the lookback interval slides across the event timeline.

*Why it's done this way:* the condition $(q-W)<t\le q$ is interval membership, not bucket assignment. One event can contribute to several query windows, which buys smoother recency features at a higher compute cost.

### 4. Session windows

A **session window** groups events until the inactivity gap exceeds a threshold. Unlike fixed windows, the boundary depends on behavior: a burst of clicks is one session even if it crosses a wall-clock boundary.

```python
session_times_w = np.array([0., 1., 2.5, 9., 10., 20., 21.])
gap_w = 4.0
new_session_w = np.r_[True, np.diff(session_times_w) > gap_w]
session_id_w = np.cumsum(new_session_w) - 1
print("new-session flags:", new_session_w.astype(int))
print("session ids:", session_id_w)
assert list(np.bincount(session_id_w)) == [3, 2, 2]
```
▶ What you'll see: long gaps before minutes 9 and 20 start new sessions.

```python
plt.figure(figsize=(5, 2.5))
plt.scatter(session_times_w, session_id_w, c=session_id_w, cmap="viridis", s=90)
plt.xlabel("event time")
plt.ylabel("session id")
plt.title("4: session windows from inactivity gaps")
plt.show()
```
▶ What you'll see: nearby events share a session row; quiet periods force a jump to the next row.

*Why it's done this way:* the rule is the inequality $\Delta t>g$. That makes sessions match visits, conversations, or bursts better than a clock partition when the feature should describe intent rather than wall-clock time.

### 5. Watermarks and late data

A **watermark** is a cutoff saying the system probably has all events before a time. With maximum seen event time $t_{max}$ and allowed lateness $\ell$, the watermark is $w=t_{max}-\ell$. An event is late if $t_{event}<w$.

```python
allowed_lateness_w = 3.0
max_seen_w = -np.inf
watermarks_w = []
late_flags_w = []
for idx_w in order_w:
    t_w = float(event_time_w[idx_w])
    max_seen_w = max(max_seen_w, t_w)
    watermark_w = max_seen_w - allowed_lateness_w
    late_w = t_w < watermark_w
    watermarks_w.append(watermark_w)
    late_flags_w.append(late_w)
    print(f"event={t_w:.1f}, max={max_seen_w:.1f}, watermark={watermark_w:.1f}, late={late_w}")
```
▶ What you'll see: the watermark trails the largest event time by exactly the lateness budget.

```python
current_watermark_w = max(event_time_w) - allowed_lateness_w
too_late_w = 6.0 < current_watermark_w
print("current watermark:", current_watermark_w)
print("event time 6 late?", too_late_w)
assert current_watermark_w == 9.0 and too_late_w
plt.figure(figsize=(5, 3))
plt.plot(watermarks_w, marker="o", label="watermark")
plt.plot(event_time_w[order_w], marker="s", label="arrived event time")
plt.xlabel("arrival index")
plt.ylabel("event time")
plt.title("5: watermark trails max event time")
plt.legend()
plt.show()
```
▶ What you'll see: once the watermark reaches 9, an event from time 6 falls outside the allowed-lateness contract.

*Why it's done this way:* the formula $w=t_{max}-\ell$ turns a messy operational choice into a clear inequality. Larger $\ell$ accepts more delayed truth but publishes later; smaller $\ell$ lowers latency but can bias features by dropping real events.

### 6. EMA streaming features

An exponential moving average updates one state value by $x_t=\alpha v_t+(1-\alpha)x_{t-1}$. The latest value receives weight $\alpha$, and older history decays geometrically.

```python
values_w = np.array([7., 8., 10., 9., 13., 12., 11., 14.])
alpha_w = 0.3
ema_w = []
state_w = values_w[0]
for v_w in values_w:
    state_w = alpha_w * v_w + (1 - alpha_w) * state_w
    ema_w.append(state_w)
print("raw values:", values_w)
print("EMA:", np.round(ema_w, 3))
assert round(alpha_w * 10 + (1 - alpha_w) * 8, 1) == 8.6
```
▶ What you'll see: the EMA follows the stream while smoothing abrupt jumps.

```python
running_mean_w = np.cumsum(values_w) / np.arange(1, len(values_w) + 1)
plt.figure(figsize=(5, 3))
plt.plot(values_w, marker="o", label="raw")
plt.plot(ema_w, marker="s", label="EMA α=0.3")
plt.plot(running_mean_w, marker="^", label="running mean")
plt.xlabel("arrival index")
plt.ylabel("feature value")
plt.title("6: EMA vs true running mean")
plt.legend()
plt.show()
```
▶ What you'll see: the EMA reacts faster than the running mean after the stream rises, but it is less jagged than raw values.

*Why it's done this way:* expanding the recurrence gives weights $\alpha,\alpha(1-\alpha),\alpha(1-\alpha)^2,\dots$. That geometric decay is why one state variable can represent a recency-weighted history.

### 7. Welford online mean and variance

Welford's algorithm updates mean and variance without storing the stream. For a new value $x$, use $\delta=x-\mu_{n-1}$, $\mu_n=\mu_{n-1}+\delta/n$, and update $M_2$ with $\delta(x-\mu_n)$.

```python
stats_w = np.array([2., 4., 4., 4., 5., 5., 7., 9.])
n_w = 0
mean_w = 0.0
M2_w = 0.0
means_w = []
vars_w = []
for x_w in stats_w:
    n_w += 1
    delta_w = x_w - mean_w
    mean_w += delta_w / n_w
    M2_w += delta_w * (x_w - mean_w)
    means_w.append(mean_w)
    vars_w.append(M2_w / (n_w - 1) if n_w > 1 else 0.0)
print("online mean:", round(mean_w, 3), "online sample variance:", round(vars_w[-1], 3))
print("batch mean:", round(float(np.mean(stats_w)), 3), "batch sample variance:", round(float(np.var(stats_w, ddof=1)), 3))
assert abs(mean_w - np.mean(stats_w)) < 1e-12
assert abs(vars_w[-1] - np.var(stats_w, ddof=1)) < 1e-12
```
▶ What you'll see: online mean and sample variance match the batch NumPy calculation.

```python
plt.figure(figsize=(5, 3))
plt.plot(means_w, marker="o", label="online mean")
plt.plot(vars_w, marker="s", label="online sample variance")
plt.xlabel("events processed")
plt.title("7: Welford state after each event")
plt.legend()
plt.show()
```
▶ What you'll see: statistics stabilize as more evidence arrives.

*Why it's done this way:* variance formulas based on $\sum x^2-n\mu^2$ can subtract nearly equal large numbers. Welford accumulates local deviations around the current mean, which is numerically stable and exact for streaming use.

### 8. Reservoir sampling

Reservoir sampling keeps a uniform sample of size $k$ from a stream of unknown length. Keep the first $k$ items; for item $i$, include it with probability $k/i$ and replace a random slot.

```python
rng_w = np.random.default_rng(0)
stream_w = np.arange(1, 21)
k_w = 5
reservoir_w = []
for i_w, item_w in enumerate(stream_w, start=1):
    if i_w <= k_w:
        reservoir_w.append(int(item_w))
    else:
        j_w = rng_w.integers(1, i_w + 1)
        if j_w <= k_w:
            reservoir_w[j_w - 1] = int(item_w)
print("reservoir sample:", reservoir_w)
assert len(reservoir_w) == k_w
```
▶ What you'll see: five stored items summarize a stream of twenty.

```python
trials_w = 1000
hit_w = 0
for seed_w in range(trials_w):
    rng_trial_w = np.random.default_rng(seed_w)
    res_w = []
    for i_w, item_w in enumerate(stream_w, start=1):
        if i_w <= k_w:
            res_w.append(int(item_w))
        else:
            j_w = rng_trial_w.integers(1, i_w + 1)
            if j_w <= k_w:
                res_w[j_w - 1] = int(item_w)
    hit_w += int(1 in res_w)
print("estimated P(item 1 kept):", round(hit_w / trials_w, 3), "target:", k_w / len(stream_w))
plt.figure(figsize=(4, 3))
plt.bar(["estimated", "target"], [hit_w / trials_w, k_w / len(stream_w)], color=["teal", "gray"])
plt.ylim(0, 0.4)
plt.title("8: uniform reservoir probability")
plt.show()
```
▶ What you'll see: the empirical probability is close to the theoretical $k/n=0.25$ target.

*Why it's done this way:* a new item enters with probability $k/i$. An old item survives that step with probability $1-(k/i)(1/k)=1-1/i$. Multiplying these survival terms telescopes, leaving every item with final probability $k/n$.

### 9. Count-Min sketch

A Count-Min sketch approximates key frequencies with several hashed rows of counters. Updates increment one counter per row; queries take the minimum across rows. Collisions can only add counts, so estimates are upper bounds.

```python
tokens_w = ["ad", "click", "ad", "view", "click", "ad", "like", "view", "ad", "share", "click"]
depth_w, width2_w = 3, 8
seeds_w = np.array([3, 7, 11])
sketch_w = np.zeros((depth_w, width2_w), dtype=int)
def hash_w(token, seed, width):
    total = sum((i + 1) * ord(ch) for i, ch in enumerate(token))
    return (total + 17 * seed) % width
for tok_w in tokens_w:
    for row_w, seed_w in enumerate(seeds_w):
        sketch_w[row_w, hash_w(tok_w, int(seed_w), width2_w)] += 1
print("sketch rows:\n", sketch_w)
```
▶ What you'll see: each event touches exactly three counters, independent of vocabulary size.

```python
true_counts_w = Counter(tokens_w)
for q_w in ["ad", "click", "like", "missing"]:
    est_w = min(sketch_w[row_w, hash_w(q_w, int(seeds_w[row_w]), width2_w)] for row_w in range(depth_w))
    print(q_w, "true=", true_counts_w[q_w], "estimate=", est_w)
    assert est_w >= true_counts_w[q_w]
```
▶ What you'll see: estimates match or overestimate true counts; they never undercount.

*Why it's done this way:* each row is a different lossy counting table. Taking the minimum chooses the least-contaminated upper bound, which reduces collision damage while keeping memory fixed.

### 10. Online SGD update

For squared error with prediction $\hat y=w^Tx$, the loss is $\frac12(y-\hat y)^2$. The gradient is $-(y-\hat y)x$, so gradient descent uses $w\leftarrow w+\eta(y-\hat y)x$.

```python
X_w = np.array([[1., 0.], [1., 1.], [1., 2.], [1., 3.]])
y_w = np.array([1., 2., 3., 4.])
w_w = np.zeros(2)
eta_w = 0.1
pred_first_w = float(w_w @ X_w[0])
err_first_w = y_w[0] - pred_first_w
w_w = w_w + eta_w * err_first_w * X_w[0]
print("after first update w:", np.round(w_w, 3))
assert np.allclose(w_w, [0.1, 0.0])
```
▶ What you'll see: the first event updates only the bias because its non-bias feature is zero.

```python
w_sgd_w = np.zeros(2)
losses_sgd_w = []
for epoch_w in range(40):
    for x_w, y_one_w in zip(X_w, y_w):
        err_w = y_one_w - float(w_sgd_w @ x_w)
        w_sgd_w += eta_w * err_w * x_w
    losses_sgd_w.append(float(np.mean((y_w - X_w @ w_sgd_w) ** 2)))
print("learned w:", np.round(w_sgd_w, 3), "final MSE:", round(losses_sgd_w[-1], 5))
assert losses_sgd_w[-1] < losses_sgd_w[0]
plt.figure(figsize=(5, 3))
plt.plot(losses_sgd_w, color="seagreen")
plt.xlabel("epoch")
plt.ylabel("MSE")
plt.title("10: online SGD loss decreasing")
plt.show()
```
▶ What you'll see: repeated online updates reduce error on the toy line $y=1+x$.

*Why it's done this way:* the residual sign says whether the prediction was too low or too high, and multiplying by $x$ assigns the correction to the features that produced the prediction.

### 11. Backpressure and freshness lag

Streaming ML also has a capacity equation. If input rate exceeds service rate, queued lag grows by $\lambda_{in}-\lambda_{out}$ events per second; stale queues mean stale features even when the code is mathematically correct.

```python
input_rate_w = np.array([900., 1000., 1200., 1300., 800., 700., 1100.])
service_rate_w = 1000.0
lag_w = []
state_lag_w = 0.0
for rate_w in input_rate_w:
    state_lag_w = max(0.0, state_lag_w + rate_w - service_rate_w)
    lag_w.append(state_lag_w)
lag_w = np.array(lag_w)
print("lag after each second:", lag_w.astype(int))
assert lag_w[3] == 500.0
```
▶ What you'll see: lag accumulates during 1200/s and 1300/s bursts, then drains when input falls below capacity.

```python
plt.figure(figsize=(5, 3))
plt.plot(input_rate_w, marker="o", label="input/sec")
plt.axhline(service_rate_w, color="black", linestyle="--", label="service/sec")
plt.plot(lag_w, marker="s", label="queued lag")
plt.title("11: backpressure creates freshness lag")
plt.legend()
plt.show()
```
▶ What you'll see: queued lag rises exactly when input sits above the service line.

*Why it's done this way:* freshness is not only a model metric; it is a queue budget. A feature computed from old state can make a bad real-time decision even if the feature formula is correct.

### Basic 6 — Update a watermark

**Goal.** Compute $w=t_{max}-\ell$ as events arrive, because the watermark is the late-data cutoff. We build it in 3 steps.

```python
event_time_b6 = np.array([1., 3., 7., 4., 12., 9.])
arrival_time_b6 = np.array([1.2, 3.1, 7.2, 8.5, 12.2, 13.0])
order_b6 = np.argsort(arrival_time_b6)
lateness_b6 = 3.0
print("arrival order:", order_b6)
```
▶ What you'll see: watermarks will be updated in processing order.

```python
max_seen_b6 = -np.inf
watermarks_b6 = []
for idx_b6 in order_b6:
    max_seen_b6 = max(max_seen_b6, float(event_time_b6[idx_b6]))

print("watermarks:", watermarks_b6)
assert watermarks_b6[-1] == 9.0
```
