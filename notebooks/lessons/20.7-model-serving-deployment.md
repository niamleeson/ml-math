# 20.7 — Model Serving & Deployment

Model serving is the production discipline of turning a trained artifact into reliable live predictions: load the model, warm it before users arrive, route traffic through safe release patterns, watch latency and errors, and scale or roll back before customers pay for surprises. In this lesson, we build a tiny serving cluster from scratch with NumPy and the standard library so every queue, load-balancer choice, percentile, replica decision, and rollout rule is visible.

### 1. Artifacts, warmup, and the first-user latency trap

A trained model artifact is not automatically ready for traffic. A server must load weights, allocate memory, and often run a warmup pass that triggers compilation or cache population. If that work happens on the first real request, the first user waits for both warmup and inference. If warmup happens before routing, users see only steady-state inference.

```python
load_seconds_w = 4.0  # time to fetch and deserialize the model artifact.
warmup_seconds_w = 30.0  # one-time compile/cache cost before the server is ready.
inference_ms_w = 45.0  # steady-state per-request model latency.
first_user_cold_ms_w = 1000 * (load_seconds_w + warmup_seconds_w) + inference_ms_w  # bad path.
first_user_warm_ms_w = inference_ms_w  # good path after readiness is true.
print("cold first request ms:", round(first_user_cold_ms_w, 1))
print("warm first request ms:", round(first_user_warm_ms_w, 1))
assert first_user_cold_ms_w == 34045.0
```
▶ What you'll see: the cold path is 34,045 ms, while a warmed server answers in 45 ms.

```python
stages_w = np.array([load_seconds_w, warmup_seconds_w, inference_ms_w / 1000])  # seconds.
plt.figure(figsize=(5, 3))
plt.bar(["load", "warmup", "inference"], stages_w, color=["gray", "orange", "teal"])
plt.title("1: one-time serving work vs per-request work")
plt.ylabel("seconds")
plt.show()
```
▶ What you'll see: warmup dominates one-time startup cost, so hiding it behind readiness matters much more than shaving a few milliseconds from one request.

*Why it's done this way:* serving separates **readiness** from **liveness**. A process can be alive but not ready for user traffic. Warming before routing moves unavoidable setup cost out of the request path, which protects the user-visible latency budget and makes rollback safer because a green pool can be proven ready before it receives traffic.

### 2. Request queueing and p50/p99 latency from a simulated server

A serving replica processes finite work. If requests arrive faster than it can finish them, they wait in a FIFO queue. For request $i$, the start time is `max(arrival_i, previous_finish)`, queue wait is `start_i - arrival_i`, and latency is `wait + service_time_i`. Percentiles summarize the distribution: p50 is the median user, while p99 is the unlucky tail user.

```python
arrival_gap_ms_w = np.array([0, 20, 25, 40, 40, 45, 60, 80, 85, 120], dtype=float)  # inter-arrival gaps.
arrival_ms_w = np.cumsum(arrival_gap_ms_w)  # absolute arrival times.
service_ms_w = np.array([50, 55, 45, 70, 65, 50, 45, 60, 55, 45], dtype=float)  # inference times.
print("arrivals:", arrival_ms_w.astype(int))
print("service times:", service_ms_w.astype(int))
```
▶ What you'll see: several requests arrive before earlier work can finish, which creates a queue.

```python
start_ms_w = np.zeros_like(arrival_ms_w)
finish_ms_w = np.zeros_like(arrival_ms_w)
for i_w in range(len(arrival_ms_w)):
    start_ms_w[i_w] = max(arrival_ms_w[i_w], finish_ms_w[i_w - 1] if i_w else 0.0)
    finish_ms_w[i_w] = start_ms_w[i_w] + service_ms_w[i_w]
wait_ms_w = start_ms_w - arrival_ms_w
latency_ms_w = finish_ms_w - arrival_ms_w
print("queue waits:", wait_ms_w.astype(int))
print("latencies:", latency_ms_w.astype(int))
assert int(wait_ms_w.max()) == 115
```
▶ What you'll see: waits rise when arrivals bunch together; the slowest request waits 115 ms before inference even starts.

```python
p50_w = float(np.percentile(latency_ms_w, 50))
p99_w = float(np.percentile(latency_ms_w, 99))
print("p50 latency ms:", round(p50_w, 1))
print("p99 latency ms:", round(p99_w, 1))
assert round(p50_w, 1) == 117.5
plt.figure(figsize=(5, 3))
plt.plot(latency_ms_w, marker="o", label="request latency")
plt.axhline(p50_w, color="green", linestyle="--", label="p50")
plt.axhline(p99_w, color="red", linestyle="--", label="p99")
plt.title("2: p50 and p99 from one queued server")
plt.xlabel("request index")
plt.ylabel("latency ms")
plt.legend()
plt.show()
```
▶ What you'll see: p50 sits near the middle of the request latencies, while p99 hugs the worst tail request.

*Why it's done this way:* queueing explains why average service time is not enough. A model can be fast per request and still produce bad p99 when arrivals burst. Production serving watches tail percentiles because users experience individual requests, not the mean of a spreadsheet.

### 3. Load balancing spreads requests across replicas

A load balancer chooses which replica handles each request. Round-robin is simple: cycle through replicas. Least-queue is adaptive: send the next request to the replica that becomes available earliest. The second policy usually lowers tail latency because it reacts to different service times and temporary backlog.

```python
arrivals_lb_w = np.arange(0, 480, 40, dtype=float)  # 12 requests, one every 40 ms.
service_lb_w = np.array([100, 40, 120, 35, 45, 150, 40, 45, 110, 35, 50, 45], dtype=float)
replicas_w = 3
print("requests:", len(arrivals_lb_w), "replicas:", replicas_w)
```
▶ What you'll see: demand is steady, but service time varies enough to make routing matter.

```python
def simulate_policy_w(arrivals, service, replicas, policy):
    available = np.zeros(replicas)
    chosen = []
    latency = []
    for t, s in zip(arrivals, service):
        r = len(chosen) % replicas if policy == "round_robin" else int(np.argmin(available))
        start = max(t, available[r])
        available[r] = start + s
        chosen.append(r)
        latency.append(available[r] - t)
    return np.array(chosen), np.array(latency)

rr_rep_w, rr_lat_w = simulate_policy_w(arrivals_lb_w, service_lb_w, replicas_w, "round_robin")
lq_rep_w, lq_lat_w = simulate_policy_w(arrivals_lb_w, service_lb_w, replicas_w, "least_queue")
print("round-robin p99:", round(float(np.percentile(rr_lat_w, 99)), 1))
print("least-queue p99:", round(float(np.percentile(lq_lat_w, 99)), 1))
assert np.percentile(lq_lat_w, 99) <= np.percentile(rr_lat_w, 99)
```
▶ What you'll see: least-queue has p99 no worse than round-robin on this bursty toy workload.

```python
plt.figure(figsize=(5, 3))
plt.plot(rr_lat_w, marker="o", label="round-robin")
plt.plot(lq_lat_w, marker="s", label="least-queue")
plt.title("3: load-balancing policy changes latency")
plt.xlabel("request index")
plt.ylabel("latency ms")
plt.legend()
plt.show()
```
▶ What you'll see: the adaptive policy avoids some spikes by steering around replicas that are still busy.

*Why it's done this way:* a load balancer is a routing rule, not magic extra capacity. It cannot make service time disappear, but it can prevent avoidable head-of-line blocking by keeping work spread across replicas. The best routing policy depends on what signal is available cheaply: round-robin needs no state, least-queue needs current backlog or availability.

### 4. Autoscaling from demand, utilization, and queue length

Replica count is a control decision. The capacity arithmetic is $r=\lceil q/c\rceil$: if demand is $q$ requests per second and one replica safely serves $c$ qps, the cluster needs at least that many replicas. In practice we also scale on utilization and queue length, because bursts create backlog before average qps catches up.

```python
demand_qps_w = np.array([180, 260, 420, 650, 900, 780, 520, 300], dtype=float)
capacity_per_replica_w = 150.0
target_util_w = 0.70
needed_by_capacity_w = np.ceil(demand_qps_w / capacity_per_replica_w).astype(int)
needed_by_target_w = np.ceil(demand_qps_w / (capacity_per_replica_w * target_util_w)).astype(int)
print("raw capacity replicas:", needed_by_capacity_w)
print("70% target replicas:", needed_by_target_w)
assert int(np.ceil(900 / 150)) == 6
```
▶ What you'll see: 900 qps needs 6 replicas at absolute capacity, but 9 replicas to keep utilization near 70%.

```python
replicas_auto_w = [2]
queue_auto_w = []
for q_w in demand_qps_w:
    current_w = replicas_auto_w[-1]
    util_w = q_w / (current_w * capacity_per_replica_w)
    backlog_w = max(0.0, q_w - current_w * capacity_per_replica_w)
    queue_auto_w.append(backlog_w)
    if util_w > 0.75 or backlog_w > 50:
        current_w += 1
    elif util_w < 0.35 and current_w > 1:
        current_w -= 1
    replicas_auto_w.append(current_w)
replicas_auto_w = np.array(replicas_auto_w[:-1])
queue_auto_w = np.array(queue_auto_w)
print("autoscaler replicas:", replicas_auto_w)
print("queue pressure qps:", queue_auto_w.astype(int))
```
▶ What you'll see: the reactive autoscaler lags demand because it only adds one replica per time step.

```python
fig, ax1 = plt.subplots(figsize=(6, 3))
ax1.plot(demand_qps_w, marker="o", color="steelblue", label="load qps")
ax1.set_ylabel("load qps")
ax2 = ax1.twinx()
ax2.step(np.arange(len(replicas_auto_w)), replicas_auto_w, where="mid", color="crimson", label="replicas")
ax2.set_ylabel("replicas")
plt.title("4: replicas-vs-load under reactive autoscaling")
fig.legend(loc="upper left", bbox_to_anchor=(0.12, 0.88))
plt.show()
```
▶ What you'll see: load rises before replicas catch up; this is the operational reason for cooldowns, predictive scaling, and headroom.

*Why it's done this way:* scaling on a target utilization leaves safety margin for variance, while queue length catches overload directly. The tradeoff is cost versus latency: too few replicas save money but build queues; too many replicas reduce tail latency but waste idle capacity.

### 5. Blue-green, canary, and shadow deployment patterns

Deployment is controlled traffic movement. **Blue-green** keeps two complete environments and flips traffic when green passes checks. **Canary** sends a small user-visible fraction to the candidate first. **Shadow** mirrors requests to the candidate but serves the old response, producing evaluations with zero user exposure.

```python
total_requests_w = 40_000
canary_fraction_w = 0.05
shadow_fraction_w = 1.00
canary_requests_w = int(total_requests_w * canary_fraction_w)
shadow_evals_w = int(total_requests_w * shadow_fraction_w)
print("5% canary requests:", canary_requests_w)
print("shadow evaluations:", shadow_evals_w, "served by candidate:", 0)
assert canary_requests_w == 2000
```
▶ What you'll see: a 5% canary exposes 2,000 users out of 40,000; shadow mode evaluates all 40,000 with zero served candidate responses.

```python
old_error_w = 0.0030
candidate_error_w = 0.0042
error_limit_w = 0.0050
latency_p99_old_w = 180.0
latency_p99_candidate_w = 210.0
latency_limit_w = 250.0
promote_w = candidate_error_w < error_limit_w and latency_p99_candidate_w < latency_limit_w
print("candidate error margin:", round(error_limit_w - candidate_error_w, 4))
print("candidate latency margin ms:", round(latency_limit_w - latency_p99_candidate_w, 1))
print("promote candidate?", promote_w)
assert promote_w is True
```
▶ What you'll see: the candidate passes both guardrails, so a progressive rollout can continue.

```python
patterns_w = ["blue-green", "canary", "shadow"]
user_exposure_w = [1.0, canary_fraction_w, 0.0]
evaluation_volume_w = [1.0, canary_fraction_w, shadow_fraction_w]
x_w = np.arange(len(patterns_w))
plt.figure(figsize=(6, 3))
plt.bar(x_w - 0.18, user_exposure_w, width=0.36, label="served exposure", color="teal")
plt.bar(x_w + 0.18, evaluation_volume_w, width=0.36, label="candidate evals", color="orange")
plt.xticks(x_w, patterns_w)
plt.ylim(0, 1.1)
plt.title("5: rollout patterns separate exposure from evidence")
plt.legend()
plt.show()
```
▶ What you'll see: shadow gives full evaluation volume with no user exposure; canary gives small exposure and small evaluation volume; blue-green moves all traffic at cutover.

*Why it's done this way:* deployments should produce evidence before irreversible user impact. Canary limits blast radius, shadow finds technical errors without changing responses, and blue-green makes rollback a routing flip instead of a rebuild. The right pattern depends on whether you need behavioral feedback, safety from user impact, or instant cutover.

## 🛠️ Setup

```python
import numpy as np  # Import NumPy for synthetic traffic, queues, percentile math, and autoscaling arrays.
import matplotlib.pyplot as plt  # Import Matplotlib for latency, load, rollout, and replica visualizations.
from collections import deque  # Import deque for tiny FIFO queue simulations.
from dataclasses import dataclass  # Import dataclass for small readable server records.
np.random.seed(0)  # Make all examples reproducible.

def percentiles(values):  # Summarize a latency array with production-style percentiles.
    values = np.asarray(values, dtype=float)  # Convert input to a numeric NumPy array.
    return float(np.percentile(values, 50)), float(np.percentile(values, 99))  # Return p50 and p99.

def simulate_single_server(arrivals, service):  # Simulate FIFO processing on one replica.
    arrivals = np.asarray(arrivals, dtype=float)  # Ensure arrival times are numeric.
    service = np.asarray(service, dtype=float)  # Ensure service times are numeric.
    starts = np.zeros_like(arrivals)  # Store request start times.
    finishes = np.zeros_like(arrivals)  # Store request finish times.
    for i in range(len(arrivals)):  # Process requests in arrival order.
        starts[i] = max(arrivals[i], finishes[i - 1] if i else 0.0)  # FIFO start after previous finish.
        finishes[i] = starts[i] + service[i]  # Finish after service time.
    return starts, finishes, finishes - arrivals  # Return start, finish, and latency.

def route_requests(arrivals, service, replicas, policy="least_queue"):  # Simulate a tiny load balancer.
    available = np.zeros(replicas)  # Track when each replica is next free.
    chosen = []  # Store chosen replica id per request.
    latency = []  # Store request latency.
    for t, s in zip(np.asarray(arrivals, float), np.asarray(service, float)):  # Route each request.
        r = len(chosen) % replicas if policy == "round_robin" else int(np.argmin(available))  # Choose replica.
        start = max(t, available[r])  # Wait if the replica is busy.
        available[r] = start + s  # Update replica availability.
        chosen.append(r)  # Record routing choice.
        latency.append(available[r] - t)  # Record user-visible latency.
    return np.array(chosen), np.array(latency)  # Return arrays for inspection.
```

### Basic 7 — Route with least-queue balancing

**Goal.** Send each request to the replica that becomes available first, because adaptive routing can reduce avoidable waiting. We build it in 2 steps.

```python
arrivals_b7 = np.arange(0, 240, 40, dtype=float)  # Define six arrivals.
service_b7 = np.array([100, 40, 120, 35, 45, 150], dtype=float)  # Define varied service times.

```
▶ What you'll see: some requests are much slower than others, so static cycling may be suboptimal.

plt.show()
```
▶ What you'll see: least-queue routes around a busy replica when possible.

👀 Takeaway: a stateful load balancer can lower tail latency without adding replicas.

### Basic 8 — Check a deployment guardrail

**Goal.** Compare candidate metrics to thresholds, because rollout decisions should be explicit and reversible. We build it in 2 steps.

for i_a5 in range(windows_a5):  # Generate window latencies.
    normal_a5 = rng_a5.normal(85 + 2 * i_a5, 8, size=120)  # Median slowly rises.
    tail_a5 = rng_a5.exponential(20 + 8 * max(0, i_a5 - 4), size=10)  # Tail worsens after stage 4.
    latency_samples_a5.append(np.concatenate([normal_a5, 100 + tail_a5]))  # Store sample.
p50_a5 = np.array([np.percentile(x_a5, 50) for x_a5 in latency_samples_a5])  # Compute p50.

```
▶ What you'll see: p99 grows more sharply than p50 as tail behavior deteriorates.
