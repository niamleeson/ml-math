# 21.5 — Semantic Web & RDF

Semantic Web and RDF make knowledge portable by reducing many kinds of facts to one uniform shape: a subject–predicate–object triple. In this lesson, you will build that idea from scratch as a tiny graph database, then add pattern matching, joins, and lightweight RDFS inference so symbolic facts can be queried and explained without any RDF library.

This walkthrough is self-contained (it imports what it needs) and uses a `_w` suffix on its variables so it never clashes with the examples below.

### 1. Triples: one fact as subject–predicate–object

RDF starts with the smallest possible knowledge record: a triple `(subject, predicate, object)`. Read it like a sentence: **Ada — worksAt — Uni**. The subject is the thing being described, the predicate is the directed relation, and the object is either another thing or a literal value. This uniform shape matters because links, attributes, and types can all be stored and queried the same way.

```python
triple_w = ("ex:Ada", "ex:worksAt", "ex:Uni")  # one directed labeled edge.
subject_w, predicate_w, object_w = triple_w  # unpack the sentence-like pieces.
print("subject:", subject_w)
print("predicate:", predicate_w)
print("object:", object_w)
```
▶ What you'll see: the triple splits cleanly into the thing, the relation, and the value/thing it points to.

```python
facts_w = [
    ("ex:Ada", "rdf:type", "ex:Professor"),
    ("ex:Ada", "ex:worksAt", "ex:Uni"),
    ("ex:Cy", "rdf:type", "ex:Professor"),
    ("ex:Cy", "ex:worksAt", "ex:Uni"),
]
print("number of triples:", len(facts_w))
print("first fact as a sentence:", " ".join(facts_w[0]))
assert len(facts_w) == 4
```
▶ What you'll see: type facts and ordinary relationship facts have exactly the same triple structure.

```python
nodes_w = sorted({s for s, p, o in facts_w} | {o for s, p, o in facts_w if o.startswith("ex:")})
idx_w = {node: i for i, node in enumerate(nodes_w)}
adj_w = np.zeros((len(nodes_w), len(nodes_w)))
for s_w, p_w, o_w in facts_w:
    if o_w in idx_w:
        adj_w[idx_w[s_w], idx_w[o_w]] += 1
print("nodes:", nodes_w)
print("adjacency counts:\n", adj_w.astype(int))
plt.figure(figsize=(4, 3))
plt.imshow(adj_w, cmap="Blues")
plt.xticks(range(len(nodes_w)), nodes_w, rotation=45, ha="right")
plt.yticks(range(len(nodes_w)), nodes_w)
plt.title("1: triples as directed graph edges")
plt.colorbar(label="edge count")
plt.show()
```
▶ What you'll see: a tiny adjacency matrix where facts become directed edges between named resources.

*Why it's done this way:* RDF chooses triples because one narrow record shape gives every system the same exchange format. A table schema might store types, people, and workplaces in separate layouts; triples make them all edges, so the same query machinery can inspect them.

### 2. IRIs: globally meaningful names instead of local column names

The `ex:` prefix above is shorthand for an IRI namespace. An IRI is a globally scoped name, so `ex:Ada` does not depend on a local table called `people`. In code we can keep readable prefixes, but the logic is that each resource name should be stable enough to merge with facts from another source.

```python
prefix_w = "https://example.org/"
compact_w = "ex:Ada"
expanded_w = compact_w.replace("ex:", prefix_w)
print("compact:", compact_w)
print("expanded IRI:", expanded_w)
assert expanded_w == "https://example.org/Ada"
```
▶ What you'll see: a short notebook-friendly name expands to a globally scoped identifier.

```python
def expand_w(term_w):
    if term_w.startswith("ex:"):
        return term_w.replace("ex:", "https://example.org/")
    if term_w.startswith("rdf:"):
        return term_w.replace("rdf:", "http://www.w3.org/1999/02/22-rdf-syntax-ns#")
    if term_w.startswith("rdfs:"):
        return term_w.replace("rdfs:", "http://www.w3.org/2000/01/rdf-schema#")
    return term_w

expanded_facts_w = [(expand_w(s_w), expand_w(p_w), expand_w(o_w)) for s_w, p_w, o_w in facts_w]
print("expanded first triple:")
print(expanded_facts_w[0])
```
▶ What you'll see: the compact RDF terms become long, collision-resistant names.

```python
lengths_w = np.array([len(term_w) for triple_w in expanded_facts_w for term_w in triple_w])
plt.figure(figsize=(4, 3))
plt.hist(lengths_w, bins=5, color="slateblue")
plt.title("2: IRI strings are verbose but stable")
plt.xlabel("characters in expanded term")
plt.ylabel("count")
plt.show()
```
▶ What you'll see: expanded identifiers are longer than labels, but the verbosity buys unambiguous merging.

*Why it's done this way:* local labels are convenient until two systems both say `id=7` or `name=Ada`. IRIs trade shortness for global meaning, which is exactly what linked data needs when graphs are combined.

### 3. An RDF graph store is a set of triples

Mathematically, an RDF graph is a set of triples. A set removes duplicate assertions automatically: saying the same fact twice should not create two different worlds. For learning, we will implement the store as a Python `set` plus tiny helper operations.

```python
graph_w = set()
for triple_w in facts_w + [("ex:Ada", "ex:worksAt", "ex:Uni")]:
    graph_w.add(triple_w)
print("input assertions including duplicate:", len(facts_w) + 1)
print("stored unique triples:", len(graph_w))
assert len(graph_w) == 4
```
▶ What you'll see: the duplicate `Ada worksAt Uni` assertion is stored once.

```python
def add_w(graph_w, s_w, p_w, o_w):
    graph_w.add((s_w, p_w, o_w))
    return graph_w

def triples_with_w(graph_w, s_w=None, p_w=None, o_w=None):
    return sorted(t_w for t_w in graph_w
                  if (s_w is None or t_w[0] == s_w)
                  and (p_w is None or t_w[1] == p_w)
                  and (o_w is None or t_w[2] == o_w))

add_w(graph_w, "ex:Uni", "rdf:type", "ex:University")
print("facts about Ada:", triples_with_w(graph_w, s_w="ex:Ada"))
print("type triples:", triples_with_w(graph_w, p_w="rdf:type"))
assert ("ex:Uni", "rdf:type", "ex:University") in graph_w
```
▶ What you'll see: subject and predicate filters already behave like simple graph-index lookups.

```python
predicates_w = sorted({p_w for s_w, p_w, o_w in graph_w})
counts_w = [sum(1 for s_w, p_w, o_w in graph_w if p_w == pred_w) for pred_w in predicates_w]
plt.figure(figsize=(4.5, 3))
plt.bar(predicates_w, counts_w, color="teal")
plt.title("3: predicate counts in the graph store")
plt.ylabel("triples")
plt.xticks(rotation=20)
plt.show()
```
▶ What you'll see: `rdf:type` is just another predicate, so type membership is queryable like any other edge.

*Why it's done this way:* using set semantics keeps the logical meaning clean: a fact is either asserted or not. Indexes can make retrieval faster later, but the core model is just membership in a triple set.

### 4. Basic graph patterns: matching variables against triples

SPARQL-style querying begins with a triple pattern. A term that starts with `?` is a variable; constants must match exactly. Matching `(?x, ex:worksAt, ex:Uni)` returns bindings for every subject that works at Uni. That is filtering plus variable assignment.

```python
def is_var_w(term_w):
    return isinstance(term_w, str) and term_w.startswith("?")

def match_one_w(pattern_w, triple_w, binding_w=None):
    binding_w = {} if binding_w is None else dict(binding_w)
    for pat_w, val_w in zip(pattern_w, triple_w):
        if is_var_w(pat_w):
            if pat_w in binding_w and binding_w[pat_w] != val_w:
                return None
            binding_w[pat_w] = val_w
        elif pat_w != val_w:
            return None
    return binding_w

print(match_one_w(("?x", "ex:worksAt", "ex:Uni"), ("ex:Ada", "ex:worksAt", "ex:Uni")))
print(match_one_w(("?x", "ex:worksAt", "ex:Uni"), ("ex:Ada", "rdf:type", "ex:Professor")))
```
▶ What you'll see: the first triple binds `?x` to Ada; the second fails because the predicate is different.

```python
def query_one_w(graph_w, pattern_w):
    results_w = []
    for triple_w in sorted(graph_w):
        binding_w = match_one_w(pattern_w, triple_w)
        if binding_w is not None:
            results_w.append(binding_w)
    return results_w

workers_w = query_one_w(graph_w, ("?x", "ex:worksAt", "ex:Uni"))
print("workers at Uni:", workers_w)
assert {b_w["?x"] for b_w in workers_w} == {"ex:Ada", "ex:Cy"}
```
▶ What you'll see: two bindings, one for Ada and one for Cy, because both match the pattern.

```python
plt.figure(figsize=(4, 3))
plt.bar([b_w["?x"] for b_w in workers_w], [1] * len(workers_w), color="seagreen")
plt.title("4: one binding per matching triple")
plt.ylabel("matched?")
plt.ylim(0, 1.2)
plt.show()
```
▶ What you'll see: each matching worker becomes one row in the query result.

*Why it's done this way:* a triple pattern is the graph analogue of a database selection. Variables make the unknown part explicit, and the binding dictionary is the row that will later be joined with other rows.

### 5. Joins over patterns: a tiny SPARQL engine

A basic graph pattern can contain several triple patterns. The key operation is a join: bindings from pattern 1 and pattern 2 survive only when they agree on shared variables. To ask for professors who work at Uni, bind `?x` from the type pattern and keep only the same `?x` in the workplace pattern.

```python
def compatible_w(left_w, right_w):
    for key_w in set(left_w) & set(right_w):
        if left_w[key_w] != right_w[key_w]:
            return False
    merged_w = dict(left_w)
    merged_w.update(right_w)
    return merged_w

def query_w(graph_w, patterns_w):
    rows_w = [{}]
    for pattern_w in patterns_w:
        next_rows_w = []
        for row_w in rows_w:
            for triple_w in sorted(graph_w):
                hit_w = match_one_w(pattern_w, triple_w, row_w)
                if hit_w is not None:
                    next_rows_w.append(hit_w)
        rows_w = next_rows_w
    return rows_w

patterns_w = [("?x", "rdf:type", "ex:Professor"), ("?x", "ex:worksAt", "ex:Uni")]
prof_workers_w = query_w(graph_w, patterns_w)
print("professors at Uni:", prof_workers_w)
assert {b_w["?x"] for b_w in prof_workers_w} == {"ex:Ada", "ex:Cy"}
```
▶ What you'll see: Ada and Cy survive the join because each has both required triples.

```python
patterns2_w = [("?x", "rdf:type", "ex:Professor"), ("?place", "rdf:type", "ex:University"), ("?x", "ex:worksAt", "?place")]
rows2_w = query_w(graph_w, patterns2_w)
print("professor/place rows:", rows2_w)
assert rows2_w == [{"?x": "ex:Ada", "?place": "ex:Uni"}, {"?x": "ex:Cy", "?place": "ex:Uni"}]
```
▶ What you'll see: the same `?place` variable connects the university type fact to the workplace fact.

```python
labels_w = [row_w["?x"].split(":")[1] for row_w in rows2_w]
plt.figure(figsize=(4, 3))
plt.scatter([0, 1], [1, 1], s=120, color="darkorange")
for i_w, label_w in enumerate(labels_w):
    plt.text(i_w, 1.04, label_w, ha="center")
plt.xticks([0, 1], labels_w)
plt.yticks([])
plt.title("5: joined rows that satisfy all patterns")
plt.ylim(0.8, 1.25)
plt.show()
```
▶ What you'll see: only rows satisfying every pattern remain; the visualization is the final joined answer table.

*Why it's done this way:* joins are what make RDF query more than edge lookup. Shared variables force separate facts to describe the same entity, which turns a bag of triples into relational answers.

### 6. RDFS entailment: adding facts that rules logically imply

RDFS adds lightweight meaning with rules such as subclass, subproperty, domain, and range. If `Professor rdfs:subClassOf Person` and `Ada rdf:type Professor`, then Ada is also a Person. This is not a new observation; it is an entailed triple justified by existing schema triples.

```python
schema_w = {
    ("ex:Professor", "rdfs:subClassOf", "ex:Person"),
    ("ex:teachesAt", "rdfs:subPropertyOf", "ex:worksAt"),
    ("ex:worksAt", "rdfs:domain", "ex:Person"),
    ("ex:worksAt", "rdfs:range", "ex:Organization"),
}
data_w = {
    ("ex:Ada", "rdf:type", "ex:Professor"),
    ("ex:Ada", "ex:teachesAt", "ex:Uni"),
}
rdfs_graph_w = set(schema_w | data_w)
print("starting triples:", len(rdfs_graph_w))
```
▶ What you'll see: a small graph mixes data facts with schema facts that describe how predicates and classes behave.

```python
def rdfs_step_w(graph_w):
    new_w = set()
    for s_w, p_w, o_w in graph_w:
        if p_w == "rdf:type":
            for c_w, rel_w, parent_w in graph_w:
                if c_w == o_w and rel_w == "rdfs:subClassOf":
                    new_w.add((s_w, "rdf:type", parent_w))
        for prop_w, rel_w, super_w in graph_w:
            if p_w == prop_w and rel_w == "rdfs:subPropertyOf":
                new_w.add((s_w, super_w, o_w))
        for prop_w, rel_w, cls_w in graph_w:
            if p_w == prop_w and rel_w == "rdfs:domain":
                new_w.add((s_w, "rdf:type", cls_w))
            if p_w == prop_w and rel_w == "rdfs:range":
                new_w.add((o_w, "rdf:type", cls_w))
    return new_w - graph_w

new_once_w = rdfs_step_w(rdfs_graph_w)
print("new triples after one rule pass:", sorted(new_once_w))
assert ("ex:Ada", "rdf:type", "ex:Person") in new_once_w
assert ("ex:Ada", "ex:worksAt", "ex:Uni") in new_once_w
```
▶ What you'll see: subclass and subproperty rules immediately infer `Ada type Person` and `Ada worksAt Uni`.

```python
def closure_w(graph_w, max_rounds_w=10):
    graph_w = set(graph_w)
    counts_w = [len(graph_w)]
    for _ in range(max_rounds_w):
        new_w = rdfs_step_w(graph_w)
        if not new_w:
            break
        graph_w |= new_w
        counts_w.append(len(graph_w))
    return graph_w, counts_w

closed_w, counts_w = closure_w(rdfs_graph_w)
print("triple counts by round:", counts_w)
print("entailed facts:", sorted(closed_w - rdfs_graph_w))
assert ("ex:Uni", "rdf:type", "ex:Organization") in closed_w
plt.figure(figsize=(4, 3))
plt.plot(range(len(counts_w)), counts_w, marker="o", color="purple")
plt.title("6: RDFS closure grows then stops")
plt.xlabel("round")
plt.ylabel("triples in graph")
plt.show()
```
▶ What you'll see: the graph gains inferred triples for a few rounds, then reaches a fixed point with no new facts.

*Why it's done this way:* RDFS inference is forward chaining over simple rules. We repeatedly add only facts that are forced by the current graph; stopping at a fixed point gives queries a richer graph without needing a heavyweight theorem prover.

### ✍️ Toy 2 · Compact names expand to IRIs

Prefixes keep examples readable. Expansion replaces each compact prefix with a longer globally scoped
string.

```python
import numpy as np                              # arrays and tiny numeric checks.

t2_rng = np.random.default_rng(0)               # reproducible toy seed.
print("rng seed:", 0)                           # -> 0
t2_prefixes = {"ex:": "https://ex.org/", "foaf:": "http://xmlns.com/foaf/0.1/"}
print("prefix keys:", sorted(t2_prefixes))      # -> ['ex:', 'foaf:']
t2_terms = ["ex:Ana", "foaf:knows", "ex:Bo"]
print("compact terms:", t2_terms)               # -> ['ex:Ana', 'foaf:knows', 'ex:Bo']

def t2_expand(t2_term):
    for t2_short, t2_long in t2_prefixes.items():
        if t2_term.startswith(t2_short):
            return t2_term.replace(t2_short, t2_long)
    return t2_term

t2_expanded = [t2_expand(t2_term) for t2_term in t2_terms]
print("expanded terms:", t2_expanded)           # -> ['https://ex.org/Ana', 'http://xmlns.com/foaf/0.1/knows', 'https://ex.org/Bo']
t2_lengths = np.array([len(t2_term) for t2_term in t2_expanded])  # -> [18 32 17]
print("expanded lengths:", t2_lengths.tolist()) # -> [18, 32, 17]
assert t2_expanded[0] == "https://ex.org/Ana"

plt.figure(figsize=(5.0, 2.8))
plt.bar(["subject", "predicate", "object"], t2_lengths, color="#4c78a8")
plt.ylabel("characters")
plt.title("Toy 2 · IRI expansion lengthens labels")
plt.show()
```
▶ What you'll see: short terms become longer IRIs while preserving the same subject–predicate–object order.

### ✍️ Toy 4 · A graph pattern returns variable bindings

A pattern with `?who` matches triples whose constants agree and records the matching subject.

```python
import numpy as np                              # arrays and tiny numeric checks.

t4_rng = np.random.default_rng(0)               # reproducible toy seed.
print("rng seed:", 0)                           # -> 0
t4_pattern = ("?who", "ex:likes", "ex:Tea")
print("pattern:", t4_pattern)                   # -> ('?who', 'ex:likes', 'ex:Tea')
t4_triples = [
    ("ex:Ben", "ex:likes", "ex:Tea"),
    ("ex:Ben", "ex:likes", "ex:Juice"),
    ("ex:Dee", "ex:likes", "ex:Tea"),
]
print("candidate triples:", t4_triples)         # -> [('ex:Ben', 'ex:likes', 'ex:Tea'), ('ex:Ben', 'ex:likes', 'ex:Juice'), ('ex:Dee', 'ex:likes', 'ex:Tea')]

def t4_is_var(t4_term):
    return isinstance(t4_term, str) and t4_term.startswith("?")

def t4_match(t4_pattern, t4_triple):
    t4_binding = {}
    for t4_pat, t4_val in zip(t4_pattern, t4_triple):
        if t4_is_var(t4_pat):
            t4_binding[t4_pat] = t4_val
        elif t4_pat != t4_val:
            return None
    return t4_binding

t4_raw = [t4_match(t4_pattern, t4_triple) for t4_triple in t4_triples]
print("raw matches:", t4_raw)                   # -> [{'?who': 'ex:Ben'}, None, {'?who': 'ex:Dee'}]
t4_bindings = [t4_hit for t4_hit in t4_raw if t4_hit is not None]
print("bindings:", t4_bindings)                 # -> [{'?who': 'ex:Ben'}, {'?who': 'ex:Dee'}]
t4_flags = np.array([t4_hit is not None for t4_hit in t4_raw], dtype=int)  # -> [1 0 1]
print("match flags:", t4_flags.tolist())        # -> [1, 0, 1]
assert [t4_row["?who"] for t4_row in t4_bindings] == ["ex:Ben", "ex:Dee"]

plt.figure(figsize=(4.8, 2.6))
plt.bar(["Ben Tea", "Ben Juice", "Dee Tea"], t4_flags, color=["seagreen" if t4_flag else "lightgray" for t4_flag in t4_flags])
plt.ylim(0, 1.2)
plt.ylabel("matched?")
plt.title("Toy 4 · constants filter, variables bind")
plt.show()
```
▶ What you'll see: only Tea triples match, and each match produces one `?who` binding.

### ✍️ Toy 5 · Shared variables join pattern rows

Two pattern result tables join only when they bind the same `?x` to the same resource.

```python
import numpy as np                              # arrays and tiny numeric checks.

t5_rng = np.random.default_rng(0)               # reproducible toy seed.

t5_graph = {

    ("ex:Ana", "ex:worksAt", "ex:Lab"),
    ("ex:Bo", "rdf:type", "ex:Student"),
    ("ex:Bo", "ex:worksAt", "ex:Cafe"),
    ("ex:Cai", "rdf:type", "ex:Staff"),
    ("ex:Cai", "ex:worksAt", "ex:Lab"),
}
print("graph size:", len(t5_graph))             # -> 6

def t5_match(t5_pattern, t5_triple):

    for t5_pat, t5_val in zip(t5_pattern, t5_triple):
        if isinstance(t5_pat, str) and t5_pat.startswith("?"):
            t5_binding[t5_pat] = t5_val
```

### Advanced 5 — Explain inferred triples with provenance

**Goal.** Record which rule produced each inferred triple, because symbolic systems are useful only when they can explain their answers. We build it in 5 steps.

```python
graph_a5 = {("ex:Professor", "rdfs:subClassOf", "ex:Person"), ("ex:Ada", "rdf:type", "ex:Professor"), ("ex:worksAt", "rdfs:range", "ex:Organization"), ("ex:Ada", "ex:worksAt", "ex:Uni")}  # Define schema and data.
explanations_a5 = {}  # Map inferred triple -> explanation tuple.
print("starting triples:", len(graph_a5))  # Inspect starting graph size.
```
▶ What you'll see: the graph has one subclass opportunity and one range opportunity.

```python
closed_a5 = set(graph_a5)  # Copy graph for closure.
for s_a5, p_a5, o_a5 in list(closed_a5):  # Scan initial triples for one explanatory pass.
    if p_a5 == "rdf:type":  # Subclass rule trigger.
        for c_a5, rel_a5, parent_a5 in list(closed_a5):  # Scan schema facts.
            if c_a5 == o_a5 and rel_a5 == "rdfs:subClassOf":  # Match class hierarchy.
                fact_a5 = (s_a5, "rdf:type", parent_a5)  # Build inferred fact.
                explanations_a5[fact_a5] = ("subClassOf", (s_a5, p_a5, o_a5), (c_a5, rel_a5, parent_a5))  # Store provenance.
                closed_a5.add(fact_a5)  # Add inferred fact.
print("after subclass pass:", sorted(closed_a5 - graph_a5))  # Inspect new facts so far.
```

```python
for s_a5, p_a5, o_a5 in list(closed_a5):  # Scan again for range rules.
    for prop_a5, rel_a5, cls_a5 in list(closed_a5):  # Scan schema facts.
```
