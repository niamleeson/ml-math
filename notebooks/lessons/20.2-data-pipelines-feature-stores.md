# 20.2 — Data Pipelines & Feature Stores

Data pipelines and feature stores turn raw events into model-ready values with contracts: every feature has an entity key, an event timestamp, a transformation rule, and a serving rule. In this lesson, you will build those pieces from scratch with lists, dicts, NumPy, and Matplotlib, then inspect why point-in-time joins, freshness checks, and shared offline/online transformations prevent leakage and train/serve skew.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build feature pipelines one idea at a time. Run each cell in order and read the printed intermediate values — every timestamp, join, aggregation, and cache lookup is spelled out so the production contract is visible. This walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

import numpy as np  # arrays, simple statistics, and deterministic synthetic data.
import matplotlib.pyplot as plt  # compact visualizations for timelines and distributions.

### 1. A feature is a timestamped fact, not just a number

A feature value only means something when we know **which entity** it belongs to and **when the source fact became true**. The same customer can have different transaction counts at different read times, so the timestamp is part of the value's identity. We will store each feature row as a tiny dictionary with `entity`, `event_time`, `name`, and `value` so later joins can ask, "what was known as of the label time?"

```python
feature_log_w = [
    {"entity": "u1", "event_time": 90, "name": "tx_30m", "value": 2},
    {"entity": "u1", "event_time": 100, "name": "tx_30m", "value": 3},
    {"entity": "u2", "event_time": 95, "name": "tx_30m", "value": 1},
]
print("first feature row:", feature_log_w[0])
print("feature identity fields:", sorted(feature_log_w[0].keys()))
```
▶ What you'll see: a feature row carries an entity key, an event timestamp, a name, and a value.

```python
read_time_w = 118
age_w = read_time_w - feature_log_w[1]["event_time"]
print("read time:", read_time_w, "event time:", feature_log_w[1]["event_time"])
print("feature age:", age_w, "minutes")
assert age_w == 18
```
▶ What you'll see: the feature emitted at time 100 is 18 minutes old when read at time 118.

```python
plt.figure(figsize=(5, 2.6))
for row_w in feature_log_w:
    plt.scatter(row_w["event_time"], 0, s=90, label=f"{row_w['entity']}={row_w['value']}")
plt.axvline(read_time_w, color="black", linestyle="--", label="read time")
plt.yticks([]); plt.xlabel("time (minutes)"); plt.title("1: feature rows are timestamped facts")
plt.legend(loc="upper left", fontsize=8); plt.show()
```
▶ What you'll see: feature events sit on a timeline, and the read time is a separate vertical line to the right.

*Why it's done this way:* a model consumes a number, but a pipeline must know whether that number existed at the decision time. Attaching entity and event time lets every downstream step reproduce the same value instead of silently using a newer snapshot.

### 2. Point-in-time-correct joins exclude the future

Training rows usually have label times: the moment we pretend we made the prediction. A point-in-time join picks the latest feature for the same entity with `event_time <= label_time`. Anything after the label time is future information and must be excluded, even if it is present in the offline table when we run the training job.

```python
labels_w = [
    {"entity": "u1", "label_time": 105, "label": 1},
    {"entity": "u1", "label_time": 120, "label": 0},
    {"entity": "u2", "label_time": 110, "label": 1},
]
feature_log_w.append({"entity": "u1", "event_time": 125, "name": "tx_30m", "value": 9})
print("label rows:", labels_w)
print("u1 feature times:", [r["event_time"] for r in feature_log_w if r["entity"] == "u1"])
```
▶ What you'll see: user `u1` has a tempting feature at time 125, but both label times are earlier than or equal to 120.

```python
def point_in_time_lookup_w(rows, entity, label_time, name):
    candidates = [r for r in rows if r["entity"] == entity and r["name"] == name and r["event_time"] <= label_time]
    if not candidates:
        return None
    return max(candidates, key=lambda r: r["event_time"])

joined_w = []
for lab_w in labels_w:
    feat_w = point_in_time_lookup_w(feature_log_w, lab_w["entity"], lab_w["label_time"], "tx_30m")
    joined_w.append({**lab_w, "feature_time": feat_w["event_time"], "tx_30m": feat_w["value"]})
print("point-in-time join:", joined_w)
assert joined_w[1]["feature_time"] == 100
```
▶ What you'll see: the row labeled at time 120 uses the feature from time 100, not the future value from time 125.

```python
naive_w = max([r for r in feature_log_w if r["entity"] == "u1" and r["name"] == "tx_30m"], key=lambda r: r["event_time"])
leak_minutes_w = naive_w["event_time"] - labels_w[1]["label_time"]
print("naive latest feature time:", naive_w["event_time"])
print("leakage minutes:", leak_minutes_w)
assert leak_minutes_w == 5
```
▶ What you'll see: the naive latest-value join leaks 5 minutes into the future for the label at time 120.

```python
plt.figure(figsize=(6, 2.8))
for row_w in feature_log_w:
    if row_w["entity"] == "u1":
        color_w = "crimson" if row_w["event_time"] > 120 else "seagreen"
        plt.scatter(row_w["event_time"], row_w["value"], s=100, color=color_w)
        plt.text(row_w["event_time"] + 0.5, row_w["value"], f"v={row_w['value']}")
plt.axvline(120, color="black", linestyle="--", label="label time 120")
plt.title("2: point-in-time join rejects future rows"); plt.xlabel("event time"); plt.ylabel("feature value")
plt.legend(); plt.show()
```
▶ What you'll see: the red point at time 125 is to the right of the label-time line, so it must not be joined.

*Why it's done this way:* offline training has access to historical files that include facts created after the prediction moment. The `<= label_time` filter simulates what the online system would have known, which keeps validation metrics honest.

### 3. Windowed aggregations create features from event streams

Many useful features are not raw events; they are aggregates over a recent window, such as "transactions in the last 30 minutes." To compute one, filter events for the entity to the interval `(as_of - window, as_of]`, then count or summarize them. The window boundary is part of the feature definition, so offline and online code must share it exactly.

```python
events_w = [
    {"entity": "u1", "time": 70, "amount": 12.0},
    {"entity": "u1", "time": 91, "amount": 5.0},
    {"entity": "u1", "time": 104, "amount": 7.0},
    {"entity": "u1", "time": 119, "amount": 3.0},
    {"entity": "u2", "time": 96, "amount": 20.0},
]
print("u1 event times:", [e["time"] for e in events_w if e["entity"] == "u1"])
```
▶ What you'll see: `u1` has four transaction events spread across time.

```python
def tx_count_window_w(events, entity, as_of, window):
    start = as_of - window
    used = [e for e in events if e["entity"] == entity and start < e["time"] <= as_of]
    return len(used), used

count_w, used_w = tx_count_window_w(events_w, "u1", as_of=120, window=30)
print("events used:", [(e["time"], e["amount"]) for e in used_w])
print("tx_count_30m:", count_w)
assert count_w == 3
```
▶ What you'll see: only events at 91, 104, and 119 fall inside `(90, 120]`, so the 30-minute count is 3.

```python
plt.figure(figsize=(6, 2.8))
for e_w in events_w:
    if e_w["entity"] == "u1":
        in_window_w = 90 < e_w["time"] <= 120
        plt.scatter(e_w["time"], e_w["amount"], color="seagreen" if in_window_w else "gray", s=90)
plt.axvspan(90, 120, color="seagreen", alpha=0.15, label="30m window")
plt.axvline(120, color="black", linestyle="--", label="as_of")
plt.title("3: windowed aggregation uses only recent events"); plt.xlabel("time"); plt.ylabel("amount")
plt.legend(); plt.show()
```
▶ What you'll see: the shaded window contains exactly the events counted by the feature.

*Why it's done this way:* a window turns a long event history into a fixed-size model input while preserving recency. Using `(start, as_of]` avoids double-counting boundary events when windows are computed repeatedly.

### 4. Freshness and TTL decide whether a stored value is usable

A feature store can return a value that is point-in-time correct but too old to trust. Freshness is the age calculation `t_read - t_event`; a TTL or SLA says the maximum acceptable age. If age exceeds the TTL, the serving layer should mark the feature missing or fall back instead of pretending the stale value is current.

```python
read_time_w = 118
feature_time_w = 100
ttl_w = 30
age_w = read_time_w - feature_time_w
fresh_w = age_w <= ttl_w
print("age:", age_w, "ttl:", ttl_w, "fresh?", fresh_w)
assert age_w == 18 and fresh_w
```
▶ What you'll see: age 18 is within a 30-minute freshness SLA.

```python
late_read_w = 145
late_age_w = late_read_w - feature_time_w
late_fresh_w = late_age_w <= ttl_w
print("late age:", late_age_w, "ttl:", ttl_w, "fresh?", late_fresh_w)
assert late_age_w == 45 and not late_fresh_w
```
▶ What you'll see: the same stored value is stale at read time 145 because it is 45 minutes old.

```python
plt.figure(figsize=(5, 2.8))
plt.bar(["read 118", "read 145"], [age_w, late_age_w], color=["seagreen", "crimson"])
plt.axhline(ttl_w, color="black", linestyle="--", label="TTL=30")
plt.ylabel("feature age"); plt.title("4: TTL separates fresh from stale")
plt.legend(); plt.show()
```
▶ What you'll see: the first bar is below the TTL line and the second bar is above it.

*Why it's done this way:* freshness checks make serving failures visible. Without a TTL, a model can keep receiving a syntactically valid number whose source pipeline stopped updating long ago.

### 5. Train/serve skew appears when transformations differ

Train/serve skew happens when the offline training code and online serving code compute nominally the same feature differently. A common example is offline using a 30-minute transaction count while online accidentally uses a 20-minute count. The model learns from one distribution and serves on another, so even a perfect model file is fed inconsistent inputs.

```python
offline_count_w, _ = tx_count_window_w(events_w, "u1", as_of=120, window=30)
online_count_w, _ = tx_count_window_w(events_w, "u1", as_of=120, window=20)
skew_w = abs(online_count_w - offline_count_w)
print("offline 30m count:", offline_count_w)
print("online 20m count:", online_count_w)
print("absolute skew:", skew_w)
assert offline_count_w == 3 and online_count_w == 2
```
▶ What you'll see: changing only the window from 30 to 20 minutes changes the feature from 3 to 2.

```python
feature_contract_w = {"name": "tx_count", "window": 30, "aggregation": "count"}
shared_offline_w, _ = tx_count_window_w(events_w, "u1", 120, feature_contract_w["window"])
shared_online_w, _ = tx_count_window_w(events_w, "u1", 120, feature_contract_w["window"])
print("shared contract:", feature_contract_w)
print("offline:", shared_offline_w, "online:", shared_online_w)
assert shared_offline_w == shared_online_w == 3
```
▶ What you'll see: using one shared contract makes offline and online agree on the same value.

```python
plt.figure(figsize=(4.6, 3))
plt.bar(["offline", "online buggy", "online shared"], [offline_count_w, online_count_w, shared_online_w], color=["seagreen", "crimson", "steelblue"])
plt.title("5: skew from mismatched windows"); plt.ylabel("tx_count feature")
plt.xticks(rotation=15); plt.show()
```
▶ What you'll see: the buggy online bar is lower, while the shared-contract bar matches offline.

*Why it's done this way:* a feature store is less about storage than about a transformation contract. Reusing one definition prevents the most expensive production bug: a model trained on features it never actually receives.

### 6. Entity keying and hashing make lookups stable

Feature rows need stable keys so offline joins and online lookups address the same entity. In production those keys may be composite, like `(user_id, merchant_id)`, and often get hashed for sharding. The important rule is determinism: the same logical key must always map to the same storage key and shard.

```python
def stable_key_w(parts):
    return "|".join(str(p) for p in parts)

def shard_w(key, n_shards):
    digest = hashlib.md5(key.encode("utf-8")).hexdigest()
    return int(digest[:8], 16) % n_shards

key_w = stable_key_w(("u1", "merchantA"))
print("stable key:", key_w)
print("shard among 8:", shard_w(key_w, 8))
```
▶ What you'll see: the composite entity becomes one deterministic string and one deterministic shard number.

```python
keys_w = [stable_key_w(("u1", "merchantA")), stable_key_w(("u1", "merchantB")), stable_key_w(("u2", "merchantA"))]
shards_w = np.array([shard_w(k, 4) for k in keys_w])
print("keys:", keys_w)
print("shards:", shards_w)
assert np.all(shards_w >= 0) and np.all(shards_w < 4)
```
▶ What you'll see: every composite key maps into one of four shard ids.

```python
plt.figure(figsize=(4.5, 3))
plt.bar(range(len(keys_w)), shards_w, color="mediumpurple")
plt.xticks(range(len(keys_w)), ["u1-A", "u1-B", "u2-A"])
plt.yticks(range(4)); plt.ylabel("shard id"); plt.title("6: deterministic entity-key hashing")
plt.show()
```
▶ What you'll see: keys with small text differences can land on different shards, but repeated hashing stays stable.

*Why it's done this way:* entity keys are the join boundary. If offline uses one key format and online uses another, the feature store returns misses or wrong rows even when the feature computation itself is correct.

### 7. A tiny in-memory feature store ties the contract together

A feature store keeps historical feature rows for offline training and latest valid rows for online serving. We can build a miniature version with a dictionary from `(entity, feature_name)` to a sorted list of timestamped values. The read path then applies both point-in-time filtering and TTL checks.

```python
store_w = defaultdict(list)
def write_feature_w(entity, name, event_time, value):
    store_w[(entity, name)].append({"event_time": event_time, "value": value})
    store_w[(entity, name)].sort(key=lambda r: r["event_time"])

for row_w in feature_log_w:
    write_feature_w(row_w["entity"], row_w["name"], row_w["event_time"], row_w["value"])
print("stored keys:", list(store_w.keys()))
print("u1 history:", store_w[("u1", "tx_30m")])
```
▶ What you'll see: the store has per-entity feature histories sorted by event time.

```python
def read_feature_w(entity, name, as_of, ttl=None):
    rows = [r for r in store_w.get((entity, name), []) if r["event_time"] <= as_of]
    if not rows:
        return None
    latest = rows[-1]
    age = as_of - latest["event_time"]
    if ttl is not None and age > ttl:
        return None
    return {"value": latest["value"], "event_time": latest["event_time"], "age": age}

print("offline read at 120:", read_feature_w("u1", "tx_30m", as_of=120, ttl=30))
print("stale read at 160:", read_feature_w("u1", "tx_30m", as_of=160, ttl=30))
```
▶ What you'll see: the read at 120 succeeds with the time-100 feature, while the read at 160 is missing because the latest value is stale.

```python
training_reads_w = [read_feature_w(l["entity"], "tx_30m", l["label_time"], ttl=30) for l in labels_w]
coverage_w = sum(x is not None for x in training_reads_w) / len(training_reads_w)
print("training reads:", training_reads_w)
print("coverage:", round(coverage_w, 3))
assert round(coverage_w, 3) == 1.0
```
▶ What you'll see: all three training labels have a usable feature under the 30-minute TTL.

*Why it's done this way:* one read API forces every caller to obey the same timestamp and freshness semantics. The store can be simple here because the hard part is the contract, not the database.

## 🛠️ Setup

```python
import numpy as np  # NumPy handles arrays, counts, averages, and deterministic toy data.
import matplotlib.pyplot as plt  # Matplotlib creates the timeline, bar, and distribution plots.
from collections import defaultdict  # defaultdict lets us group events and feature histories with standard-library containers.
import hashlib  # hashlib gives deterministic hashes for entity keys without external services.
np.random.seed(0)  # Fix the global seed so every example is reproducible.

def window_count(events, entity, as_of, window):  # Count entity events in the open-closed interval (as_of-window, as_of].
    start = as_of - window  # Compute the left boundary of the freshness window.
    used = [e for e in events if e["entity"] == entity and start < e["time"] <= as_of]  # Keep only eligible events.
    return len(used), used  # Return both the count and the included events for inspection.

def point_in_time(rows, entity, name, as_of):  # Find the latest feature row that existed by the requested time.
    candidates = [r for r in rows if r["entity"] == entity and r["name"] == name and r["event_time"] <= as_of]  # Filter by key and time.
    return None if not candidates else max(candidates, key=lambda r: r["event_time"])  # Return the newest non-future row.

def feature_age(event_time, read_time):  # Compute feature age using the production freshness formula.
    return read_time - event_time  # Age is read time minus the time the source fact became true.

def stable_entity_key(parts):  # Build a deterministic composite key from simple parts.
    return "|".join(str(p) for p in parts)  # Join parts with a delimiter used consistently offline and online.

def stable_shard(key, n_shards):  # Map an entity key to a deterministic shard id.
    digest = hashlib.md5(key.encode("utf-8")).hexdigest()  # Hash the key into reproducible hexadecimal text.
    return int(digest[:8], 16) % n_shards  # Convert part of the hash to an integer shard id.

def show_timeline(times, values, title, cutoff=None):  # Draw a compact feature/event timeline.
    plt.figure(figsize=(5, 2.8))  # Create a notebook-sized figure.
    plt.scatter(times, values, s=80, color="teal")  # Plot each event or feature point.
    if cutoff is not None:  # Add a vertical line when a decision or read time matters.
        plt.axvline(cutoff, color="black", linestyle="--", label="cutoff")  # Show the point-in-time boundary.
        plt.legend()  # Display the cutoff label.
    plt.xlabel("time")  # Label the horizontal time axis.
    plt.ylabel("value")  # Label the feature/event value axis.
    plt.title(title)  # Give the plot an example-specific title.
    plt.show()  # Display the figure.
```

### Basic 6 — Point-in-time lookup

**Goal.** Select the latest feature at or before a label time, because training must simulate what serving would have known. We build it in 2 steps.

```python
features_b6 = [
    {"entity": "u1", "event_time": 90, "name": "tx_count", "value": 2},
    {"entity": "u1", "event_time": 100, "name": "tx_count", "value": 3},
    {"entity": "u1", "event_time": 125, "name": "tx_count", "value": 9},
]
label_time_b6 = 120
print("feature times:", [r["event_time"] for r in features_b6])
```
▶ What you'll see: one feature row arrives after the label time and is therefore dangerous.
