# 20.5 — CI/CD for ML

CI/CD for ML is the release system that makes model change safe: a candidate artifact must pass data-contract checks, smoke training, evaluation thresholds, packaging checks, and live rollout budgets before it receives full traffic. In this lesson, we build that system from scratch with small NumPy simulations so every gate, rollout fraction, and rollback trigger is inspectable.

## 📖 Concept walkthrough — build each idea from scratch

Before the worked examples, we build the ML CI/CD release loop one idea at a time. Run each cell in order and inspect the printed numbers: a pipeline is just a dependency graph, a release gate is just Boolean arithmetic, and a canary is just controlled exposure plus live thresholds. The walkthrough uses `_w` suffixes so it stays separate from the examples below.

```python
import numpy as np  # arrays, synthetic metrics, and small numerical checks.
import matplotlib.pyplot as plt  # compact visual diagnostics for gates and rollouts.
from collections import defaultdict, deque  # stdlib graph tools for the tiny DAG executor.
np.random.seed(0)  # make the toy release reproducible.
```
▶ What you'll see: the only dependencies for the walkthrough are NumPy, Matplotlib, and the Python standard library.

### 1. A pipeline DAG is an executable dependency contract

An ML pipeline is not only a list of commands. It is a **directed acyclic graph**: data validation must finish before training, training before evaluation, evaluation before packaging, and packaging before rollout. Topological order is the rule that turns dependencies into a safe execution sequence.

```python
steps_w = ["schema", "smoke_train", "eval", "package", "canary"]  # release stages.
edges_w = [("schema", "smoke_train"), ("smoke_train", "eval"), ("eval", "package"), ("package", "canary")]  # before -> after.
print("steps:", steps_w)
print("dependencies:", edges_w)
```
▶ What you'll see: five named stages and four dependency edges that say what must happen before what.

```python
def topo_order_w(nodes, edges):
    children = defaultdict(list)
    indeg = {n: 0 for n in nodes}
    for before, after in edges:
        children[before].append(after)
        indeg[after] += 1
    ready = deque([n for n in nodes if indeg[n] == 0])
    order = []
    while ready:
        node = ready.popleft()
        order.append(node)
        for child in children[node]:
            indeg[child] -= 1
            if indeg[child] == 0:
                ready.append(child)
    if len(order) != len(nodes):
        raise ValueError("cycle detected")
    return order

order_w = topo_order_w(steps_w, edges_w)
print("topological order:", order_w)
assert order_w == ["schema", "smoke_train", "eval", "package", "canary"]
```
▶ What you'll see: the graph becomes the exact safe execution order.

```python
pos_w = {"schema": (0, 0), "smoke_train": (1, 0), "eval": (2, 0), "package": (3, 0), "canary": (4, 0)}
plt.figure(figsize=(7, 2.4))
for node, (x, y) in pos_w.items():
    plt.scatter([x], [y], s=900, color="lightsteelblue", edgecolor="black")
    plt.text(x, y, node, ha="center", va="center", fontsize=9)
for before, after in edges_w:
    x0, y0 = pos_w[before]
    x1, y1 = pos_w[after]
    plt.arrow(x0 + 0.22, y0, x1 - x0 - 0.44, 0, head_width=0.05, length_includes_head=True, color="black")
plt.axis("off")
plt.title("1: ML CI/CD pipeline as a DAG")
plt.show()
```
▶ What you'll see: a left-to-right DAG where each arrow is a prerequisite, not decoration.

*Why it's done this way:* A DAG makes release order explicit and checkable. If someone adds a new packaging step, it must declare its parents; the topological executor then prevents accidental evaluation of an artifact that has not been trained or packaged yet.

### 2. Staged gates make failure cheap and inspectable

The lesson's release formula is deliberately simple: `release = 1` only if every gate is `1`. The engineering value is not the multiplication itself; it is the staged design. Cheap gates run early, expensive gates run only after the candidate has earned them.

```python
gates_w = {
    "schema": 24 == 24,
    "smoke_train": (0.90 - 0.62) >= 0.20,
    "eval": 0.184 <= 0.190,
    "package": True,
    "rollout_safety": 8 <= 10,
}
release_w = int(np.prod([int(v) for v in gates_w.values()]))
print("gates:", gates_w)
print("release decision:", release_w)
assert release_w == 1
```
▶ What you'll see: every gate passes, so the Boolean product allows release.

```python
bad_schema_gates_w = dict(gates_w)
bad_schema_gates_w["schema"] = (23 == 24)
bad_release_w = int(np.prod([int(v) for v in bad_schema_gates_w.values()]))
print("schema mismatch blocks release:", bad_schema_gates_w)
print("release decision:", bad_release_w)
assert bad_release_w == 0
```
▶ What you'll see: one missing column changes the release product from 1 to 0.

```python
plt.figure(figsize=(6, 3))
plt.bar(list(gates_w.keys()), [int(v) for v in gates_w.values()], color="seagreen")
plt.ylim(0, 1.2)
plt.xticks(rotation=25, ha="right")
plt.ylabel("gate pass = 1")
plt.title("2: all gates must pass")
plt.show()
```
▶ What you'll see: a row of passing gates; any bar at 0 would stop the release.

*Why it's done this way:* ML failures hide in different places: a schema drift is cheap to catch, a statistical regression is costlier, and live behavior is costliest. Staging gates preserves speed because obvious failures stop before they consume training, evaluation, or user traffic.

### 3. Statistical evaluation gates compare a candidate against a budget

A model can pass code tests and still be worse. The evaluation gate turns model quality into a release inequality: the candidate's measured error must be below a maximum, and often below the baseline by enough margin to justify change.

```python
rng_w = np.random.default_rng(0)
labels_w = rng_w.integers(0, 2, size=500)
base_errors_w = np.r_[np.ones(99, dtype=bool), np.zeros(401, dtype=bool)]
cand_errors_w = np.r_[np.ones(92, dtype=bool), np.zeros(408, dtype=bool)]
base_err_w = float(base_errors_w.mean())
cand_err_w = float(cand_errors_w.mean())
print("baseline error:", round(base_err_w, 3), "candidate error:", round(cand_err_w, 3))
assert cand_err_w < base_err_w
```
▶ What you'll see: a synthetic candidate error rate below the synthetic baseline.

```python
max_error_w = 0.190
margin_w = max_error_w - cand_err_w
quality_gate_w = cand_err_w <= max_error_w
print("max allowed error:", max_error_w)
print("candidate clears by:", round(margin_w, 3), "gate:", quality_gate_w)
assert quality_gate_w and margin_w > 0
```
▶ What you'll see: the candidate clears the 0.190 budget by a small positive margin.

```python
plt.figure(figsize=(4.8, 3))
plt.bar(["baseline", "candidate", "budget"], [base_err_w, cand_err_w, max_error_w], color=["gray", "teal", "black"])
plt.ylabel("error rate")
plt.title("3: offline evaluation gate")
plt.show()
```
▶ What you'll see: the candidate bar sits below the budget line-as-bar and below the baseline.

*Why it's done this way:* Release gates need a numeric contract, not a vague feeling that the model is better. A fixed budget makes the decision reproducible, while comparison to the baseline prevents shipping a candidate that merely satisfies an old minimum but regresses current production quality.

### 4. Canary rollout is controlled exposure plus live arithmetic

A canary routes only a fraction of requests to the candidate. The core math is small: candidate requests equal `fraction × total`, expected errors equal `requests × error_rate`, and promotion happens only if live error and latency stay inside budget.

```python
total_requests_w = 40_000
fractions_w = np.array([0.01, 0.05, 0.10, 0.25, 0.50])
canary_requests_w = (fractions_w * total_requests_w).astype(int)
expected_errors_w = canary_requests_w * 0.004
print("canary requests:", canary_requests_w)
print("expected errors at 0.4%:", expected_errors_w.astype(int))
assert canary_requests_w[1] == 2000 and int(expected_errors_w[1]) == 8
```
▶ What you'll see: a 5% canary of 40,000 requests produces 2,000 candidate requests and about 8 expected errors.

```python
observed_error_rates_w = np.array([0.0035, 0.0040, 0.0042, 0.0065, 0.0080])
error_budget_w = 0.006
safe_prefix_w = observed_error_rates_w <= error_budget_w
print("observed error rates:", observed_error_rates_w)
print("safe at each stage:", safe_prefix_w)
assert safe_prefix_w.tolist() == [True, True, True, False, False]
```
▶ What you'll see: the rollout is safe early, then violates the error budget at 25% exposure.

```python
plt.figure(figsize=(6, 3))
plt.plot(fractions_w * 100, observed_error_rates_w, marker="o", color="crimson", label="candidate live error")
plt.axhline(error_budget_w, color="black", linestyle="--", label="budget")
plt.xlabel("traffic sent to candidate (%)")
plt.ylabel("error rate")
plt.title("4: canary error-rate over rollout")
plt.legend()
plt.show()
```
▶ What you'll see: the canary curve crosses the dashed budget as traffic increases; that crossing is the stop signal.

*Why it's done this way:* Offline metrics cannot reveal every production interaction. Canarying limits blast radius: the candidate earns each larger traffic slice with live evidence, and the first budget crossing stops expansion before the whole population is exposed.

### 5. Automated rollback turns symptoms into a deterministic action

Rollback should not depend on a human remembering thresholds during an incident. The pipeline watches live metrics, computes threshold violations, and automatically restores the last good artifact when latency or errors exceed the contract.

```python
live_p95_w = np.array([132, 141, 149, 180, 176])
latency_budget_w = 150
latency_over_w = live_p95_w - latency_budget_w
rollback_points_w = latency_over_w > 0
print("p95 latency:", live_p95_w)
print("ms over budget:", latency_over_w)
assert int(latency_over_w[3]) == 30
```
▶ What you'll see: the fourth window is 30 ms over the 150 ms p95 budget.

```python
current_artifact_w = "model_2026_07_candidate"
previous_good_w = "model_2026_06_stable"
should_rollback_w = bool(np.any(rollback_points_w) or np.any(observed_error_rates_w > error_budget_w))
active_after_w = previous_good_w if should_rollback_w else current_artifact_w
print("rollback triggered:", should_rollback_w)
print("active artifact after control loop:", active_after_w)
assert active_after_w == previous_good_w
```
▶ What you'll see: the control loop chooses the previous stable artifact automatically.

```python
plt.figure(figsize=(5.5, 3))
plt.plot(np.arange(len(live_p95_w)), live_p95_w, marker="o", color="darkorange")
plt.axhline(latency_budget_w, color="black", linestyle="--", label="p95 budget")
plt.xlabel("monitoring window")
plt.ylabel("p95 latency (ms)")
plt.title("5: rollback trigger from live latency")
plt.legend()
plt.show()
```
▶ What you'll see: latency crosses the budget in the same window that triggers rollback.

*Why it's done this way:* Automated rollback closes the loop between monitoring and deployment. The rule is intentionally boring: if live metrics exceed the release contract, route back to the last known-good artifact. Boring is exactly what you want when users are already seeing failures.

## 🛠️ Setup

```python
import numpy as np  # arrays, synthetic metrics, and deterministic toy simulations.
import matplotlib.pyplot as plt  # compact plots for pipelines, gates, and rollout curves.
from collections import defaultdict, deque  # stdlib data structures for the tiny DAG executor.
np.random.seed(0)  # make all examples reproducible.

def topo_sort(nodes, edges):
    children = defaultdict(list)
    indeg = {n: 0 for n in nodes}
    for before, after in edges:
        children[before].append(after)
        indeg[after] += 1
    ready = deque([n for n in nodes if indeg[n] == 0])
    order = []
    while ready:
        node = ready.popleft()
        order.append(node)
        for child in children[node]:
            indeg[child] -= 1
            if indeg[child] == 0:
                ready.append(child)
    if len(order) != len(nodes):
        raise ValueError("cycle detected")
    return order

def gate_product(gates):
    return int(np.prod([int(v) for v in gates.values()]))

def error_rate(errors):
    return float(np.mean(np.asarray(errors, dtype=float)))

def rollback_decision(error_rates, latencies, error_budget=0.006, latency_budget=150):
    return bool(np.any(np.asarray(error_rates) > error_budget) or np.any(np.asarray(latencies) > latency_budget))
```
▶ What you'll see: reusable helpers for topological order, Boolean gates, metric summaries, and rollback checks.
