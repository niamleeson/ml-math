# 9.20 — Tool Use & Function Calling

Tool use lets a language model stop pretending it can do every exact operation in text and instead emit a structured request to a small external function. In this lesson, we build the whole loop from scratch: choose a tool, serialize JSON arguments, validate those arguments against a schema, dispatch a plain Python function, read the observation, and decide when to retry or fall back.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build tool use one idea at a time. Run each cell in order and read the printed intermediate values — every piece of the control loop is visible, from the probability of choosing a tool to the exact checks that stop bad arguments. This walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

```python
import json  # serialize and parse tool-call arguments.
import re  # simple pattern checks for string arguments.
import numpy as np  # arrays and softmax arithmetic for toy model decisions.
import matplotlib.pyplot as plt  # all walkthrough visualizations.
np.random.seed(0)  # reproducibility for any random toy choices.
```

### 1. A model action is a tool choice plus arguments

A function-calling model does not directly return the answer first. It returns an **action**: either speak normally or call a named tool with arguments. The simplest decomposition is

$$p(a\mid x)=p(\mathrm{tool}\mid x)\,p(\mathrm{args}\mid x,\mathrm{tool}).$$

The first factor chooses which operation is useful; the second factor fills in the structured inputs for that operation. Separating the two is important because a model can choose the right tool but still produce invalid arguments, or choose a plausible tool when no tool is needed.

```python
logits_w = np.array([2.0, 1.0, 0.0])  # scores for calculator, weather, no_tool.
tools_w = ["calculator", "weather", "no_tool"]  # candidate actions.
exp_w = np.exp(logits_w - np.max(logits_w))  # subtract max for stable softmax.
probs_w = exp_w / exp_w.sum()  # p(tool | x).
print("tool probabilities:", dict(zip(tools_w, np.round(probs_w, 3))))
assert np.allclose(np.round(probs_w, 3), [0.665, 0.245, 0.090])
```
▶ What you'll see: the calculator is most likely, but the action is still a distribution rather than a guarantee.

```python
plt.figure(figsize=(4.6, 3))
plt.bar(tools_w, probs_w, color=["seagreen", "steelblue", "gray"])
plt.ylabel("p(tool | prompt)")
plt.title("1: choosing a tool is a softmax decision")
plt.ylim(0, 1)
plt.show()
```
▶ What you'll see: the logit gap turns into a large probability gap; the highest logit receives most of the action mass.

*Why it's done this way: softmax turns unconstrained model scores into normalized probabilities, so the system can inspect confidence and route only high-value calls to tools instead of forcing every prompt through a function.*

### 2. JSON arguments are structured tokens, not trusted data

After a tool is chosen, the model emits arguments as text. JSON is useful because it gives the text a parseable shape: object keys, strings, numbers, booleans, and lists. But parseable is not the same as correct. We first parse the JSON, then compare the result to the tool's schema.

```python
raw_args_w = '{"expression": "6*7", "precision": 0}'  # what the model emitted.
args_w = json.loads(raw_args_w)  # convert JSON text into a Python dict.
print("parsed args:", args_w)
print("types:", {k: type(v).__name__ for k, v in args_w.items()})
```
▶ What you'll see: JSON turns text into typed fields, so `precision` is an integer rather than the characters `"0"`.

```python
schema_w = {"required": ["expression", "precision", "units"]}  # a tiny schema fragment.
present_w = [name for name in schema_w["required"] if name in args_w]  # required fields supplied.
completeness_w = len(present_w) / len(schema_w["required"])
print("present required fields:", present_w)
print("schema completeness:", round(completeness_w, 3))
assert round(completeness_w, 3) == 0.667
```
▶ What you'll see: two of three required fields were present, so the call is parseable but incomplete.

```python
plt.figure(figsize=(4.6, 3))
plt.bar(["present", "missing"], [len(present_w), len(schema_w["required"]) - len(present_w)], color=["seagreen", "crimson"])
plt.ylabel("required-field count")
plt.title("2: JSON parsed, schema still incomplete")
plt.ylim(0, len(schema_w["required"]))
plt.show()
```
▶ What you'll see: parsing produced usable fields, but the missing required-field bar shows why validation is still needed.

*Why it's done this way: JSON parsing answers “is this valid syntax?”, while schema checks answer “does this tool have the inputs it needs?”; the separation prevents a well-formed but incomplete object from reaching business logic.*

### 3. Validation checks type, range, and semantic shape

A useful schema is more than a list of names. It checks that fields have the right **type**, values fall inside allowed **ranges**, and strings match safe **patterns**. For a calculator, an expression like `6*7` is valid arithmetic, while `six times seven` is not something our toy evaluator understands.

```python
calc_schema_w = {
    "expression": {"type": str, "pattern": r"^[0-9+\-*/ ().]+$"},
    "precision": {"type": int, "min": 0, "max": 4},
}
print("schema fields:", list(calc_schema_w.keys()))
print("raw args:", args_w)
```
▶ What you'll see: the schema states both what fields exist and what each field is allowed to look like.

```python
errors_w = []
for field_w, rule_w in calc_schema_w.items():
    value_w = args_w.get(field_w)
    if value_w is None:
        errors_w.append(field_w + " is missing")
    elif not isinstance(value_w, rule_w["type"]):
        errors_w.append(field_w + " has wrong type")
    elif "pattern" in rule_w and re.fullmatch(rule_w["pattern"], value_w) is None:
        errors_w.append(field_w + " fails pattern")
    elif "min" in rule_w and not (rule_w["min"] <= value_w <= rule_w["max"]):
        errors_w.append(field_w + " out of range")
print("validation errors:", errors_w)
assert errors_w == []
```
▶ What you'll see: this call passes validation because the expression is numeric arithmetic and precision is in range.

```python
bad_args_w = {"expression": "six times seven", "precision": 9}
bad_errors_w = []
for field_w, rule_w in calc_schema_w.items():
    value_w = bad_args_w.get(field_w)
    if value_w is None:
        bad_errors_w.append(field_w + " is missing")
    elif not isinstance(value_w, rule_w["type"]):
        bad_errors_w.append(field_w + " has wrong type")
    elif "pattern" in rule_w and re.fullmatch(rule_w["pattern"], value_w) is None:
        bad_errors_w.append(field_w + " fails pattern")
    elif "min" in rule_w and not (rule_w["min"] <= value_w <= rule_w["max"]):
        bad_errors_w.append(field_w + " out of range")
print("bad validation errors:", bad_errors_w)
assert bad_errors_w == ["expression fails pattern", "precision out of range"]
```
▶ What you'll see: the semantically wrong expression and out-of-range precision are caught before dispatch.

```python
plt.figure(figsize=(4.8, 3))
plt.bar(["valid call", "bad call"], [len(errors_w), len(bad_errors_w)], color=["seagreen", "crimson"])
plt.ylabel("validation error count")
plt.title("3: validation blocks unsafe arguments")
plt.show()
```
▶ What you'll see: the valid call has zero errors, while the bad call accumulates two concrete validation failures.

*Why it's done this way: validation narrows an open-ended language output into a contract; the math is a set-membership test where each argument must lie inside the allowed type/range/pattern set before the function is allowed to run.*

### 4. Dispatch executes exact code and returns an observation

Once the call is valid, a dispatcher maps the tool name to a plain function. The key boundary is that the model does **not** invent the tool output. The external function computes it, and the model receives the result as an observation for the next text step.

```python
def calculator_w(expression, precision):
    allowed_w = set("0123456789+-*/ ().")
    assert set(expression) <= allowed_w
    value_w = eval(expression, {"__builtins__": {}}, {})
    return round(float(value_w), precision)

def unit_convert_w(value, factor):
    return float(value) * float(factor)

tools_map_w = {"calculator": calculator_w, "unit_convert": unit_convert_w}
print("registered tools:", list(tools_map_w.keys()))
```
▶ What you'll see: tool names are just keys in a dispatch table, and the values are ordinary Python functions.

```python
call_w = {"tool": "calculator", "args": {"expression": "6*7", "precision": 0}}
result_w = tools_map_w[call_w["tool"]](**call_w["args"])
observation_w = {"tool": call_w["tool"], "result": result_w}
print("observation:", observation_w)
assert observation_w["result"] == 42.0
```
▶ What you'll see: the exact arithmetic result is returned by code, not generated from memory.

```python
plt.figure(figsize=(5.2, 2.4))
plt.axis("off")
steps_w = ["tool name", "validated args", "dispatcher", "observation"]
xs_w = np.linspace(0.08, 0.92, len(steps_w))
for x_w, label_w in zip(xs_w, steps_w):
    plt.text(x_w, 0.55, label_w, ha="center", va="center", bbox=dict(boxstyle="round", fc="white", ec="steelblue"))
for left_w, right_w in zip(xs_w[:-1], xs_w[1:]):
    plt.annotate("", xy=(right_w - 0.08, 0.55), xytext=(left_w + 0.08, 0.55), arrowprops=dict(arrowstyle="->", color="gray"))
plt.title("4: dispatch turns a call into an observation")
plt.show()
```
▶ What you'll see: the structured call flows through the dispatcher before the model receives the computed observation.

*Why it's done this way: dispatch makes tool use a controlled state transition — `(tool, args)` becomes an observation — which keeps exact computation outside probabilistic text generation and makes failures inspectable.*

### 5. Observations update the next-token distribution

The observation is then folded back into the model's context. In a toy logit view, evidence can add a boost to the answer token that matches the tool output. A boost of `+1.2` multiplies odds by $e^{1.2}$, which is why even a small-looking logit change can strongly alter the final answer.

```python
base_logits_w = np.array([0.0, 0.0])  # logits for answer tokens "40" and "42" before seeing the tool.
boost_w = 1.2  # observation supports the correct token "42".
after_logits_w = base_logits_w + np.array([0.0, boost_w])
odds_multiplier_w = float(np.exp(boost_w))
print("odds multiplier from +1.2:", round(odds_multiplier_w, 3))
assert round(odds_multiplier_w, 3) == 3.320
```
▶ What you'll see: adding 1.2 to a logit makes the supported answer about 3.32 times more likely in odds space.

```python
before_probs_w = np.exp(base_logits_w) / np.exp(base_logits_w).sum()
after_probs_w = np.exp(after_logits_w) / np.exp(after_logits_w).sum()
print("before observation:", np.round(before_probs_w, 3))
print("after observation:", np.round(after_probs_w, 3))
```
▶ What you'll see: the probability of `42` moves from 0.5 to about 0.769 after the observation boost.

```python
plt.figure(figsize=(4.6, 3))
x_w = np.arange(2)
plt.bar(x_w - 0.18, before_probs_w, width=0.36, label="before", color="gray")
plt.bar(x_w + 0.18, after_probs_w, width=0.36, label="after", color="seagreen")
plt.xticks(x_w, ["40", "42"])
plt.ylabel("answer probability")
plt.title("5: observation shifts answer odds")
plt.legend()
plt.show()
```
▶ What you'll see: the tool observation concentrates probability on the answer that agrees with the external computation.

*Why it's done this way: logits are additive evidence, while probabilities must sum to one; adding an observation as logit evidence is equivalent to multiplying odds, so reliable tool results can dominate a weak prior without hard-coding every answer.*

### 6. Retries and fallbacks stop tool loops

Tool calls fail: JSON may not parse, validation may reject arguments, or the function may return an error. A deployed loop needs a stopping rule. We track attempts, successes, and a maximum retry count so the system can fall back instead of calling forever.

```python
attempts_w = ["validation_error", "parse_error", "success"]
successes_w = np.array([a == "success" for a in attempts_w])
success_rate_w = successes_w.mean()
print("attempts:", attempts_w)
print("tool success rate:", round(success_rate_w, 3))
assert round(success_rate_w, 3) == 0.333
```
▶ What you'll see: one success after three attempts gives a success rate of 1/3.

```python
max_retries_w = 2
failed_before_success_w = int((~successes_w).sum())
should_fallback_w = failed_before_success_w >= max_retries_w and successes_w[-1] == False
print("failed attempts before final state:", failed_before_success_w)
print("fallback if still failing?", should_fallback_w)
assert failed_before_success_w == 2
```
▶ What you'll see: two failures is enough to trigger fallback if a later success does not arrive.

```python
plt.figure(figsize=(4.6, 3))
plt.bar(["failures", "successes"], [failed_before_success_w, int(successes_w.sum())], color=["crimson", "seagreen"])
plt.axhline(max_retries_w, color="black", linestyle="--", label="retry limit")
plt.ylabel("count")
plt.title("6: retry budget makes loops finite")
plt.legend()
plt.show()
```
▶ What you'll see: the failure bar reaches the retry limit, showing why a stop rule is part of the tool design.

*Why it's done this way: a retry loop is a finite-state controller, not an act of hope; counting failures bounds cost and prevents the agent from converting validation mistakes into an infinite action loop.*

### ✍️ Toy 1 · Tool choice is a softmax action

A function-calling model first chooses among tool actions. Logit gaps become inspectable tool
probabilities after softmax.

```python
import numpy as np
import matplotlib.pyplot as plt

t1_rng = np.random.default_rng(0)                         # seeded generator for reproducibility
t1_bonus = float(t1_rng.integers(0, 1))                   # deterministic no-op score bonus  # -> 0.0
print("score bonus:", t1_bonus)                           # -> 0.0
t1_tools = np.array(["calculator", "weather", "no_tool"]) # candidate actions
print("tools:", t1_tools.tolist())                        # -> ['calculator', 'weather', 'no_tool']
t1_logits = np.array([2.0, 1.0, 0.0]) + t1_bonus          # tool logits  # -> [2.0, 1.0, 0.0]
print("tool logits:", t1_logits.tolist())                 # -> [2.0, 1.0, 0.0]
t1_shifted = t1_logits - np.max(t1_logits)                # stable scores  # -> [0.0, -1.0, -2.0]
print("shifted logits:", t1_shifted.tolist())             # -> [0.0, -1.0, -2.0]
t1_exp = np.exp(t1_shifted)                               # exponentials  # -> [1.0, 0.368, 0.135]
print("exp scores:", np.round(t1_exp, 3).tolist())        # -> [1.0, 0.368, 0.135]
t1_probs = t1_exp / t1_exp.sum()                          # softmax probabilities  # -> [0.665, 0.245, 0.09]
print("tool probabilities:", np.round(t1_probs, 3).tolist())  # -> [0.665, 0.245, 0.09]
t1_choice = t1_tools[int(np.argmax(t1_probs))]            # most likely action  # -> calculator
print("chosen tool:", t1_choice)                          # -> calculator
assert t1_choice == "calculator" and np.allclose(np.round(t1_probs, 3), [0.665, 0.245, 0.09])

plt.figure(figsize=(4.6, 2.8))
plt.bar(t1_tools, t1_probs, color=["seagreen", "steelblue", "gray"])
plt.ylim(0, 1)
plt.ylabel("p(tool)")
plt.title("Toy 1 · softmax over tools")
plt.show()
```
▶ What you'll see: the calculator bar gets most probability mass, but the other actions remain possible.

### ✍️ Toy 4 · Dispatch turns a call into an observation

After validation, dispatch maps a tool name to exact code. The observation is computed by the tool,
not invented by the model.

```python
import numpy as np

t4_rng = np.random.default_rng(0)                         # seeded generator for reproducibility

plt.figure(figsize=(5.2, 2.4))

```

### ✍️ Toy 5 · Observations boost matching answer logits

A tool result becomes evidence in the next text step. Adding `+1.2` to the matching answer's logit
multiplies its odds.

```python
import numpy as np

t5_rng = np.random.default_rng(0)                         # seeded generator for reproducibility
t5_boost = float(t5_rng.integers(12, 13)) / 10            # observation logit boost  # -> 1.2
print("observation boost:", t5_boost)                     # -> 1.2
t5_answers = np.array(["6", "7"])                         # candidate answer tokens
print("answers:", t5_answers.tolist())                    # -> ['6', '7']
t5_base_logits = np.array([0.0, 0.0])                     # before tool result  # -> [0.0, 0.0]
print("base logits:", t5_base_logits.tolist())            # -> [0.0, 0.0]
t5_after_logits = t5_base_logits + np.array([0.0, t5_boost])  # boost answer 7  # -> [0.0, 1.2]
print("after logits:", t5_after_logits.tolist())          # -> [0.0, 1.2]
t5_odds_multiplier = np.exp(t5_boost)                     # odds multiplier  # -> 3.32
print("odds multiplier:", round(float(t5_odds_multiplier), 3))  # -> 3.32
t5_before_exp = np.exp(t5_base_logits)                    # before exponentials  # -> [1.0, 1.0]
print("before exp:", t5_before_exp.tolist())              # -> [1.0, 1.0]
t5_after_exp = np.exp(t5_after_logits - np.max(t5_after_logits)) # after exponentials  # -> [0.301, 1.0]
print("after exp:", np.round(t5_after_exp, 3).tolist())   # -> [0.301, 1.0]
t5_before_probs = t5_before_exp / t5_before_exp.sum()     # before probabilities  # -> [0.5, 0.5]
print("before probabilities:", t5_before_probs.tolist())  # -> [0.5, 0.5]
t5_after_probs = t5_after_exp / t5_after_exp.sum()        # after probabilities  # -> [0.231, 0.769]
print("after probabilities:", np.round(t5_after_probs, 3).tolist())  # -> [0.231, 0.769]
assert round(float(t5_after_probs[1]), 3) == 0.769

plt.figure(figsize=(4.6, 2.8))
t5_x = np.arange(t5_answers.size)
plt.bar(t5_x - 0.18, t5_before_probs, width=0.36, color="gray", label="before")
plt.bar(t5_x + 0.18, t5_after_probs, width=0.36, color="seagreen", label="after")
plt.xticks(t5_x, t5_answers)
```
