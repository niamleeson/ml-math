# 9.20 — Tool Use & Function Calling

Tool use lets a language model delegate exact operations (arithmetic, lookups, API calls) to external functions and fold the results back into text. Instead of asking one model call to *be* a calculator, we factor the behavior into a **decision** — which tool, with which arguments — and a **dispatch** step that runs real code. This notebook builds that whole machinery from scratch in numpy + the standard library so you can watch every intermediate value: the tool-selection distribution, the parsed arguments, the schema check, and the observe-and-continue loop.

## 📖 Concept walkthrough — build each idea from scratch

The central identity for function calling is the factorization

$$p(a\mid x)=p(\mathrm{tool}\mid x)\,p(\mathrm{args}\mid x,\mathrm{tool}).$$

The model first decides *whether and which* tool to invoke, then emits *arguments* constrained by that tool's schema, and only afterward reads the observation. We'll build each factor as a tiny, inspectable component.

### 1. The factorized decision: choosing a tool

A real LLM produces a probability over an action vocabulary. We mimic just the part that matters — a score for each candidate tool — with a deterministic keyword featurizer plus a softmax. That keeps the notebook CPU-only while preserving the exact quantity ($p(\mathrm{tool}\mid x)$) a trained model would output.

```python
import numpy as np

# A toy "tool router": each tool has keyword cues. The router scores a query
# against every tool, then softmaxes the scores into p(tool | x).
TOOLS_w = ["calculator", "weather", "search"]
CUES_w = {
    "calculator": ["add", "plus", "sum", "times", "multiply", "minus", "divide", "+", "*"],
    "weather":    ["weather", "temperature", "forecast", "rain", "hot", "cold"],
    "search":     ["who", "what", "when", "where", "define", "lookup", "search"],
}

def tool_scores_w(query):
    q = query.lower()
    # count how many cue words for each tool appear in the query
    return np.array([sum(c in q for c in CUES_w[t]) for t in TOOLS_w], dtype=float)

def softmax_w(z):
    z = z - z.max()            # subtract max for numerical stability
    e = np.exp(z)
    return e / e.sum()

query_w = "what is 12 plus 30?"
scores_w = tool_scores_w(query_w)
p_tool_w = softmax_w(scores_w)
print("tools :", TOOLS_w)
print("scores:", scores_w)
print("p_tool:", np.round(p_tool_w, 3))
```

▶ **What you'll see:** the `calculator` tool gets the highest score (cues `plus` and, via the digits, an arithmetic intent), so `p_tool` puts most mass on it.

*Why it's done this way:* we compute an explicit distribution over tools rather than hard-coding a rule so the mechanism matches a real model, where tool choice is a learned soft decision. The softmax turns arbitrary real-valued scores into a normalized probability, and subtracting the max before exponentiating avoids overflow without changing the result (softmax is shift-invariant: $\mathrm{softmax}(z+c)=\mathrm{softmax}(z)$). Keeping the router separate from the tools is the whole point of function calling — the language model decides, external code executes.

### 2. Emitting arguments as a structured call

Once a tool is chosen, the second factor $p(\mathrm{args}\mid x,\mathrm{tool})$ produces the arguments. Real models emit a JSON string; we emit the same structure and *parse* it, because the parse step is where things break in practice.

```python
import json, re

def extract_call_w(query, tool):
    # Produce a JSON function-call string, then parse it back to a dict.
    # (A real model emits the string; here we synthesize it deterministically.)
    if tool == "calculator":
        nums = [int(n) for n in re.findall(r"-?\d+", query)]
        op = "add" if any(w in query.lower() for w in ["add", "plus", "sum", "+"]) else "mul"
        call = {"name": "calculator", "arguments": {"op": op, "a": nums[0], "b": nums[1]}}
    elif tool == "weather":
        m = re.search(r"in ([a-zA-Z ]+)", query)
        call = {"name": "weather", "arguments": {"city": (m.group(1).strip() if m else "unknown")}}
    else:
        call = {"name": "search", "arguments": {"q": query}}
    json_str = json.dumps(call)          # the "emitted" JSON
    return json_str, json.loads(json_str)  # round-trip through JSON like a real parser

json_w, parsed_w = extract_call_w(query_w, "calculator")
print("emitted JSON:", json_w)
print("parsed dict :", parsed_w)
```

▶ **What you'll see:** a JSON string like `{"name": "calculator", "arguments": {"op": "add", "a": 12, "b": 30}}` and the same content parsed into a Python dict.

*Why it's done this way:* arguments are conditioned on the chosen tool because each tool has a different signature — `calculator` needs `(op, a, b)`, `weather` needs `city`. Round-tripping through `json.dumps`/`json.loads` mirrors the real failure surface: a model can emit *almost*-valid JSON, and the parse either succeeds (giving a typed dict) or raises. Separating "emit a string" from "parse the string" makes that boundary explicit so we can validate before executing.

### 3. Schema validation — necessary but not sufficient

A parsed call can still be wrong: missing keys, wrong types, out-of-range values. We check the call against a lightweight schema *before* running anything.

```python
SCHEMAS_w = {
    "calculator": {"op": str, "a": int, "b": int},
    "weather":    {"city": str},
    "search":     {"q": str},
}

def validate_call_w(parsed):
    name = parsed.get("name")
    if name not in SCHEMAS_w:
        return False, f"unknown tool {name!r}"
    schema, args = SCHEMAS_w[name], parsed.get("arguments", {})
    for key, typ in schema.items():
        if key not in args:
            return False, f"missing arg {key!r}"
        if not isinstance(args[key], typ):
            return False, f"arg {key!r} expected {typ.__name__}, got {type(args[key]).__name__}"
    return True, "ok"

ok_w, msg_w = validate_call_w(parsed_w)
bad_w = {"name": "calculator", "arguments": {"op": "add", "a": 12}}  # missing b
print("valid call :", validate_call_w(parsed_w))
print("broken call:", validate_call_w(bad_w))
assert ok_w and msg_w == "ok"
```

▶ **What you'll see:** the well-formed call validates as `(True, 'ok')`; the broken call reports `(False, "missing arg 'b'")`.

*Why it's done this way:* validation catches the mechanical errors (missing/mistyped arguments) that would otherwise crash the tool or, worse, run with garbage. But it is only *necessary*, not *sufficient*: a call can be perfectly schema-valid and still semantically wrong (adding the wrong two numbers). We validate first because it's cheap and it converts a whole class of silent failures into an explicit, catchable signal.

### 4. The dispatcher — routing a validated call to real code

The dispatcher is the bridge between the model's decision and actual computation. It maps a tool name to a Python function and calls it with the parsed arguments.

```python
def tool_calculator_w(op, a, b):
    return a + b if op == "add" else a * b

def tool_weather_w(city):
    # deterministic pseudo-weather so the notebook is reproducible
    return {"city": city, "temp_c": 15 + (len(city) % 10)}

def tool_search_w(q):
    return f"top result for {q!r}"

REGISTRY_w = {"calculator": tool_calculator_w, "weather": tool_weather_w, "search": tool_search_w}

def dispatch_w(parsed):
    ok, msg = validate_call_w(parsed)
    if not ok:
        return {"error": msg}          # refuse to execute an invalid call
    fn = REGISTRY_w[parsed["name"]]
    return {"result": fn(**parsed["arguments"])}  # unpack args by keyword

print("dispatch valid :", dispatch_w(parsed_w))
print("dispatch broken:", dispatch_w(bad_w))
assert dispatch_w(parsed_w) == {"result": 42}
```

▶ **What you'll see:** the valid calculator call returns `{'result': 42}`; the broken call short-circuits to `{'error': "missing arg 'b'"}` without ever executing.

*Why it's done this way:* the dispatcher unpacks arguments by keyword (`fn(**args)`), which is exactly why the schema's key names must match the function's parameter names — the validation in step 3 is what makes this unpacking safe. Crucially, the model never produces the *result*; it only produces the *call*. Letting the model invent tool outputs would destroy the separation between computation (exact, verifiable) and language (fluent, fallible).

### 5. The full pipeline: one query, one tool result

Now compose the four factors — route, extract, validate, dispatch — into a single function-call step and watch each intermediate value.

```python
def call_once_w(query):
    scores = tool_scores_w(query)
    p = softmax_w(scores)
    tool = TOOLS_w[int(np.argmax(p))]      # pick the argmax tool
    _, parsed = extract_call_w(query, tool)
    out = dispatch_w(parsed)
    return {"query": query, "p_tool": np.round(p, 3), "tool": tool,
            "call": parsed["arguments"], "observation": out}

for q in ["what is 7 plus 5?", "weather in Paris", "who wrote Hamlet?"]:
    r = call_once_w(q)
    print(f"{q:24s} -> {r['tool']:10s} {r['call']} => {r['observation']}")
```

▶ **What you'll see:** three queries route to `calculator`, `weather`, and `search` respectively, each with sensible parsed arguments and a concrete observation.

*Why it's done this way:* stringing the factors together shows the complete $p(a\mid x)=p(\mathrm{tool}\mid x)\,p(\mathrm{args}\mid x,\mathrm{tool})$ decomposition in action — first the tool distribution, then the tool-conditioned arguments, then execution. Returning every intermediate (not just the final answer) is deliberate: when a tool-using system misbehaves, the bug is almost always in *one* of these stages, and you can only localize it if each stage's output is visible.

### 6. The observe-and-fold-back loop (multi-step)

A single call rarely finishes a task. The agent loop appends each observation back into the context and decides whether to call again or stop — with an explicit budget so it can't loop forever.

```python
def solve_w(task, max_steps=4):
    # Toy multi-step task: a list of sub-queries to resolve in order.
    context, transcript = [], []
    for step in range(max_steps):
        if not task:
            break                       # stopping rule: nothing left to do
        q = task.pop(0)
        r = call_once_w(q)
        context.append(r["observation"])   # fold the observation back in
        transcript.append((step, r["tool"], r["observation"]))
    return transcript, context

tape_w, ctx_w = solve_w(["3 plus 4", "weather in Rome", "8 times 2"])
for step, tool, obs in tape_w:
    print(f"step {step}: {tool:10s} -> {obs}")
assert len(tape_w) == 3
```

▶ **What you'll see:** three steps, each printing the tool used and its observation, in order.

*Why it's done this way:* folding observations back into the context is what makes tool use *compositional* — later decisions can depend on earlier results. The `max_steps` budget is not optional: retries without a stopping rule are exactly how tool loops turn into runaway agent loops. A bounded loop guarantees termination and makes cost predictable, which is the difference between a demo and a deployable system.

## 🟢 Basics (warm-up)

### Basic 1 — A stable softmax over tool scores

We start with the primitive every router needs: turning raw scores into a probability distribution.

```python
def softmax_b1(z):
    z = np.asarray(z, float)
    z = z - z.max()
    e = np.exp(z)
    return e / e.sum()

p_b1 = softmax_b1([2.0, 0.5, 0.5])
print("distribution:", np.round(p_b1, 3), "sum =", p_b1.sum())
assert abs(p_b1.sum() - 1.0) < 1e-9
assert np.argmax(p_b1) == 0
```

👀 **Takeaway:** softmax maps arbitrary scores to a normalized distribution; the largest score gets the most mass.

### Basic 2 — Keyword features for a query

The router needs to turn text into numbers. Here is the simplest featurizer: count cue words.

```python
cues_b2 = {"calculator": ["plus", "times"], "weather": ["weather", "forecast"]}
def features_b2(query):
    q = query.lower()
    return {tool: sum(c in q for c in cs) for tool, cs in cues_b2.items()}

print(features_b2("what is 2 plus 2?"))
print(features_b2("today's weather forecast"))
assert features_b2("2 plus 2")["calculator"] == 1
```

👀 **Takeaway:** a query becomes a small vector of per-tool cue counts — the input to tool selection.

### Basic 3 — Argmax tool selection

Given scores, pick the tool. We separate scoring (soft) from selection (hard) so both are inspectable.

```python
tools_b3 = ["calculator", "weather", "search"]
scores_b3 = np.array([3.0, 1.0, 0.0])
choice_b3 = tools_b3[int(np.argmax(scores_b3))]
print("scores:", scores_b3, "-> choice:", choice_b3)
assert choice_b3 == "calculator"
```

👀 **Takeaway:** the hard decision is just an `argmax` over the soft scores.

### Basic 4 — Emitting a JSON function call

Function calling communicates through JSON. We build a call dict and serialize it.

```python
call_b4 = {"name": "calculator", "arguments": {"op": "add", "a": 5, "b": 9}}
json_b4 = json.dumps(call_b4)
print("json:", json_b4)
assert json.loads(json_b4)["arguments"]["a"] == 5
```

👀 **Takeaway:** a call is a name plus a typed argument dict, transported as JSON.

### Basic 5 — Parsing the JSON back

The consumer parses the string. This round-trip is where malformed output is caught.

```python
good_b5 = '{"name": "search", "arguments": {"q": "hello"}}'
parsed_b5 = json.loads(good_b5)
print("parsed:", parsed_b5)
assert parsed_b5["name"] == "search"
```

👀 **Takeaway:** `json.loads` turns the emitted string into a typed Python object you can validate.

### Basic 6 — Catching malformed JSON

Real models sometimes emit broken JSON. Handle it explicitly rather than crashing.

```python
def safe_parse_b6(s):
    try:
        return True, json.loads(s)
    except json.JSONDecodeError as e:
        return False, str(e)

print("valid  :", safe_parse_b6('{"a": 1}')[0])
print("invalid:", safe_parse_b6('{"a": 1')[0])   # missing closing brace
assert safe_parse_b6('{"a": 1')[0] is False
```

👀 **Takeaway:** wrap parsing in try/except so malformed output becomes a handled error, not an exception.

### Basic 7 — Extracting numbers with a regex

Argument extraction often means pulling structured values out of text.

```python
nums_b7 = [int(n) for n in re.findall(r"-?\d+", "add 14 and -6 please")]
print("numbers:", nums_b7)
assert nums_b7 == [14, -6]
```

👀 **Takeaway:** regexes turn free text into the typed arguments a tool expects.

### Basic 8 — A tiny tool registry

The dispatcher looks tools up by name in a registry mapping strings to functions.

```python
registry_b8 = {"add": lambda a, b: a + b, "mul": lambda a, b: a * b}
print("add:", registry_b8["add"](3, 4))
print("mul:", registry_b8["mul"](3, 4))
assert registry_b8["mul"](3, 4) == 12
```

👀 **Takeaway:** a name→function dict is all the routing infrastructure a dispatcher needs.

### Basic 9 — Calling a tool with unpacked arguments

Keyword-unpacking (`**args`) is how a parsed call becomes a function call.

```python
def area_b9(width, height):
    return width * height

args_b9 = {"width": 4, "height": 5}
print("area:", area_b9(**args_b9))
assert area_b9(**args_b9) == 20
```

👀 **Takeaway:** `fn(**args)` connects a JSON argument dict directly to a Python function — provided the keys match the parameters.

### Basic 10 — One end-to-end call

Compose parse → dispatch for a single query and inspect the observation.

```python
registry_b10 = {"calculator": lambda op, a, b: a + b if op == "add" else a * b}
raw_b10 = '{"name": "calculator", "arguments": {"op": "add", "a": 20, "b": 22}}'
parsed_b10 = json.loads(raw_b10)
result_b10 = registry_b10[parsed_b10["name"]](**parsed_b10["arguments"])
print("observation:", result_b10)
assert result_b10 == 42
```

👀 **Takeaway:** parse the call, look up the function, unpack the arguments, run — that is the whole minimal pipeline.

## 🟡 Easy

### Easy 1 — Probabilistic routing over three tools

Combine featurizing, scoring, and softmax into a reusable router that returns a full distribution.

```python
tools_e1 = ["calculator", "weather", "search"]
cues_e1 = {"calculator": ["plus", "times", "minus"], "weather": ["weather", "temp"],
           "search": ["who", "what", "define"]}
def route_e1(query):
    q = query.lower()
    s = np.array([sum(c in q for c in cues_e1[t]) for t in tools_e1], float)
    s = s - s.max(); p = np.exp(s) / np.exp(s).sum()
    return dict(zip(tools_e1, np.round(p, 3)))

print(route_e1("what is the capital of France?"))
assert max(route_e1("3 plus 3"), key=route_e1("3 plus 3").get) == "calculator"
```

👀 **Takeaway:** a router returns `p(tool | x)` for every tool, not just the winner — useful for confidence thresholds.

### Easy 2 — Schema-driven validation

Validate a call against a per-tool schema of required keys and types.

```python
schemas_e2 = {"calculator": {"op": str, "a": int, "b": int}, "search": {"q": str}}
def validate_e2(parsed):
    sch = schemas_e2.get(parsed.get("name"))
    if sch is None:
        return False
    args = parsed.get("arguments", {})
    return all(k in args and isinstance(args[k], t) for k, t in sch.items())

print(validate_e2({"name": "calculator", "arguments": {"op": "add", "a": 1, "b": 2}}))
print(validate_e2({"name": "calculator", "arguments": {"op": "add", "a": 1}}))
assert validate_e2({"name": "search", "arguments": {"q": "hi"}}) is True
```

👀 **Takeaway:** schemas let one validator serve every tool by looking up the expected keys and types.

### Easy 3 — Confidence thresholding (when NOT to call a tool)

If no tool clears a confidence threshold, decline rather than force a bad call.

```python
def route_or_abstain_e3(query, tau=0.5):
    p = np.array(list(route_e1(query).values()))
    top = p.max()
    return (tools_e1[int(np.argmax(p))] if top >= tau else "abstain"), float(top)

print(route_or_abstain_e3("5 times 5"))       # confident -> calculator
print(route_or_abstain_e3("hello there"))     # no cues -> abstain
assert route_or_abstain_e3("hello there")[0] == "abstain"
```

👀 **Takeaway:** a threshold on the top probability turns the router into a system that knows when to stay silent.

### Easy 4 — Dispatch with error handling

A robust dispatcher validates, executes, and converts tool exceptions into structured errors.

```python
def safe_divide_e4(a, b):
    return a / b
registry_e4 = {"divide": safe_divide_e4}
def dispatch_e4(name, args):
    try:
        return {"result": registry_e4[name](**args)}
    except Exception as ex:            # e.g. ZeroDivisionError
        return {"error": type(ex).__name__}

print(dispatch_e4("divide", {"a": 10, "b": 2}))
print(dispatch_e4("divide", {"a": 10, "b": 0}))
assert dispatch_e4("divide", {"a": 10, "b": 0})["error"] == "ZeroDivisionError"
```

👀 **Takeaway:** wrapping execution in try/except keeps a single failing tool from crashing the whole agent.

Plot `p(tool | x)` for a few queries to see how sharply the router commits.

## 🔴 Advanced

### Advanced 1 — Multi-step agent loop with a step budget

Chain calls, folding each observation into a running context, and stop on an explicit budget.

```python
def agent_loop_a1(subtasks, max_steps=5):
    registry = {"calc": lambda op, a, b: a + b if op == "add" else a * b}
    ctx, tape = [], []
    steps = 0
    for op, a, b in subtasks:
        if steps >= max_steps:
            break
        obs = registry["calc"](op=op, a=a, b=b)
        ctx.append(obs); tape.append(obs); steps += 1
    return tape, steps

tape_a1, n_a1 = agent_loop_a1([("add", 1, 2), ("mul", 3, 4), ("add", 5, 6)])
print("observations:", tape_a1, "| steps:", n_a1)
assert tape_a1 == [3, 12, 11] and n_a1 == 3
```

👀 **Takeaway:** a bounded loop makes multi-step tool use compositional *and* guaranteed to terminate.

### Advanced 2 — Argument grounding beats schema validity

Show that a schema-valid call can be semantically wrong, and add a grounding check.

```python
def parse_calc_a2(query):
    nums = [int(n) for n in re.findall(r"-?\d+", query)]
    op = "add" if "plus" in query.lower() else "mul"
    return {"op": op, "a": nums[0], "b": nums[1]}

q_a2 = "what is 12 plus 30"
args_a2 = parse_calc_a2(q_a2)
schema_ok_a2 = isinstance(args_a2["a"], int) and isinstance(args_a2["b"], int)
# grounding check: do the extracted numbers actually appear in the query?
grounded_a2 = all(str(v) in q_a2 for v in (args_a2["a"], args_a2["b"]))
print("args:", args_a2, "| schema_ok:", schema_ok_a2, "| grounded:", grounded_a2)
assert schema_ok_a2 and grounded_a2
```

👀 **Takeaway:** validation confirms *shape*; grounding confirms the arguments actually came from the input — both are needed.

### Advanced 3 — Parallel tool calls and result merging

Some queries need several tools at once; issue them together and merge observations.

```python
def parallel_calls_a3(calls):
    reg = {"calc": lambda a, b: a + b, "len": lambda s: len(s)}
    return {name: reg[name](**args) for name, args in calls}

results_a3 = parallel_calls_a3([("calc", {"a": 2, "b": 3}), ("len", {"s": "hello"})])
print("merged results:", results_a3)
assert results_a3 == {"calc": 5, "len": 5}
```

👀 **Takeaway:** independent tool calls can run together and be merged by name, cutting round-trips.

### Advanced 4 — Evaluating a tool-use system

Score end-to-end behavior with three metrics: tool-selection accuracy, argument validity, and answer exact-match.

```python
gold_a4 = [("3 plus 4", "calculator", 7), ("6 times 7", "calculator", 42)]
def run_a4(query):
    tool = "calculator"
    nums = [int(n) for n in re.findall(r"-?\d+", query)]
    op = "add" if "plus" in query else "mul"
    val = nums[0] + nums[1] if op == "add" else nums[0] * nums[1]
    args_valid = len(nums) == 2
    return tool, args_valid, val

tool_acc = np.mean([run_a4(q)[0] == t for q, t, _ in gold_a4])
arg_valid = np.mean([run_a4(q)[1] for q, _, _ in gold_a4])
exact = np.mean([run_a4(q)[2] == g for q, _, g in gold_a4])
print(f"tool_acc={tool_acc:.2f}  arg_valid={arg_valid:.2f}  exact_match={exact:.2f}")
assert tool_acc == 1.0 and exact == 1.0
```

👀 **Takeaway:** a tool-use system needs *layered* metrics — right tool, valid args, and correct final answer are distinct failure modes.

### Advanced 5 — A retry policy with a hard stop

When a call fails validation, retry with a repair, but cap retries so failures can't loop forever.

```python
def call_with_retry_a5(bad_first, max_retries=2):
    attempts = 0
    parsed = {"name": "calculator", "arguments": {"op": "add", "a": 1}}  # missing b
    while attempts <= max_retries:
        ok = all(k in parsed["arguments"] for k in ("op", "a", "b"))
        if ok:
            return "success", attempts
        # "repair": supply the missing argument, but only if we still have budget
        parsed["arguments"]["b"] = 41
        attempts += 1
        if bad_first and attempts == 1:
            del parsed["arguments"]["b"]   # simulate a repair that failed once
    return ("success" if all(k in parsed["arguments"] for k in ("op", "a", "b"))
            else "give_up"), attempts

print("repairs cleanly :", call_with_retry_a5(bad_first=False))
print("needs a retry   :", call_with_retry_a5(bad_first=True))
assert call_with_retry_a5(bad_first=False)[0] == "success"
assert call_with_retry_a5(bad_first=True)[1] <= 2
```

👀 **Takeaway:** retries make tool use robust, but only a hard retry cap turns "robust" into "guaranteed to terminate" — the boundary between an agent and an infinite loop.
