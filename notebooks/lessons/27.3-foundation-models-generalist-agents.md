# 27.3 — Foundation Models & Generalist Agents

Foundation models replace many narrow systems with one broad prior that can be prompted, adapted, retrieved into, and wrapped with tools. In this notebook, we build the core math from scratch: scaling laws, compute/data/parameter tradeoffs, transfer, in-context learning, routing, and agent loops. The code uses only NumPy, Matplotlib, and the Python standard library.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build foundation models and generalist agents one idea at a time. Run each cell in order and read the printed intermediate values — every piece of math, including power-law fitting, is spelled out so nothing is a black box. This walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

```python
import numpy as np  # arrays, linear algebra, random simulation, and log-space fitting.
import matplotlib.pyplot as plt  # all walkthrough and example visualizations.
np.random.seed(0)  # reproducibility for simulations.
```

### 1. One broad prior instead of many narrow models

A foundation model is the bet that one broad pretraining distribution can learn reusable structure for many tasks. Instead of training separate isolated systems for summarization, coding, retrieval, dialogue, and tool use, we first learn a shared representation and then specialize by prompting, fine-tuning, retrieval, or tools. The practical question is whether the shared prior transfers across tasks rather than helping only the task it saw most often.

```python
tasks_w = ["summarize", "code", "retrieve", "dialogue", "tool-use"]  # downstream tasks.
transfer_w = np.array([[0.90, 0.42, 0.50, 0.70, 0.45],
                       [0.40, 0.88, 0.44, 0.52, 0.66],
                       [0.52, 0.46, 0.86, 0.58, 0.72],
                       [0.68, 0.50, 0.56, 0.89, 0.60],
                       [0.46, 0.70, 0.75, 0.61, 0.87]])  # how much pretraining on row helps column.
shared_gain_w = transfer_w.mean(axis=0)  # average incoming help per task.
print("mean transfer into each task:", dict(zip(tasks_w, np.round(shared_gain_w, 3))))
assert transfer_w.shape == (5, 5)
plt.figure(figsize=(5.8, 4))
plt.imshow(transfer_w, cmap="viridis", vmin=0, vmax=1)
plt.colorbar(label="transfer score")
plt.xticks(range(len(tasks_w)), tasks_w, rotation=30, ha="right")
plt.yticks(range(len(tasks_w)), tasks_w)
plt.title("1: broad prior as multi-task transfer")
plt.tight_layout()
plt.show()
```
▶ What you'll see: a transfer heatmap where diagonal strengths are high, but useful off-diagonal transfer is the reason a foundation model can replace many narrow systems.

*Why it's done this way: a heatmap makes the shared-prior claim testable — broad models are valuable only when knowledge learned for one task improves other tasks too.*

### 2. Self-supervised learning turns raw sequences into labels

Self-supervised pretraining makes its own targets from raw sequences. In next-token prediction, the input is the prefix $x_{<t}$ and the label is the next token $x_t$, so every position in a document becomes a supervised example without human annotation. More data usually lowers validation loss, but a power law means the improvement is smooth and expensive, not magical.

```python
D_w = np.logspace(6, 10, 9)  # number of training tokens.
A_data_w, alpha_data_w = 2.4, 0.065  # synthetic data-scaling constant and exponent.
loss_data_w = A_data_w * D_w ** (-alpha_data_w) + 0.02  # validation loss with irreducible floor.
logD_w = np.log(D_w)
logy_w = np.log(loss_data_w - 0.02)  # subtract known floor before fitting a power law.
X_w = np.c_[np.ones_like(logD_w), -logD_w]  # log y = log A - alpha log D.
beta_w = np.linalg.solve(X_w.T @ X_w, X_w.T @ logy_w)  # normal equations from scratch.
A_hat_w, alpha_hat_w = float(np.exp(beta_w[0])), float(beta_w[1])
print("fit A:", round(A_hat_w, 3), "fit alpha:", round(alpha_hat_w, 3))
assert abs(alpha_hat_w - alpha_data_w) < 1e-10
plt.figure(figsize=(5, 3.2))
plt.loglog(D_w, loss_data_w, marker="o", label="observed")
plt.loglog(D_w, A_hat_w * D_w ** (-alpha_hat_w) + 0.02, linestyle="--", label="power-law fit")
plt.xlabel("tokens D")
plt.ylabel("validation loss")
plt.title("2: self-supervised loss vs data")
plt.legend()
plt.show()
```
▶ What you'll see: validation loss falls as tokens grow, and the log-log line recovers the exponent used to simulate the data.

*Why it's done this way: fitting in log space turns $L=A D^{-\alpha}$ into a straight-line regression, so the exponent is visible instead of hidden inside a black box.*

### 3. Transformers condition many predictions on one context

Transformers and attention let one context influence many next-token predictions and tool choices. The full architecture is large, but the scaling fact is simple: larger context and model capacity can improve in-context learning, where a model uses examples inside the prompt without changing its weights. We simulate accuracy as the number of shots increases.

```python
shots_w = np.arange(0, 9)  # examples placed in the prompt.
acc_small_w = 0.35 + 0.35 * (1 - np.exp(-shots_w / 3.2))  # smaller model learns slowly from context.
acc_large_w = 0.42 + 0.48 * (1 - np.exp(-shots_w / 2.0))  # larger model extracts the pattern faster.
print("0-shot vs 8-shot large:", round(acc_large_w[0], 3), "->", round(acc_large_w[-1], 3))
assert acc_large_w[-1] > acc_small_w[-1]
plt.figure(figsize=(5, 3.2))
plt.plot(shots_w, acc_small_w, marker="o", label="smaller model")
plt.plot(shots_w, acc_large_w, marker="o", label="larger foundation model")
plt.xlabel("number of in-context examples")
plt.ylabel("accuracy")
plt.ylim(0.3, 1.0)
plt.title("3: in-context learning improves with shots")
plt.legend()
plt.show()
```
▶ What you'll see: accuracy rises with more demonstrations, and the larger model benefits more from the same prompt evidence.

*Why it's done this way: an in-context curve separates parameter learning, which happened during pretraining, from fast prompt conditioning, which happens at inference time.*

### 4. Representation learning explains transfer

Representation learning means pretraining shapes features that downstream tasks reuse. A feature useful for language structure can also help retrieval, coding, or dialogue. Transfer is not uniform: some task pairs share structure, while others interfere. We model this as a source-by-target transfer matrix and inspect where reuse is strong.

```python
sources_w = ["syntax", "facts", "reason", "tools"]
targets_w = ["QA", "code", "search", "agent"]
reuse_w = np.array([[0.72, 0.80, 0.45, 0.50],
                    [0.88, 0.48, 0.82, 0.56],
                    [0.74, 0.70, 0.58, 0.76],
                    [0.40, 0.62, 0.66, 0.91]])
best_source_w = [sources_w[i] for i in np.argmax(reuse_w, axis=0)]
print("best source per target:", dict(zip(targets_w, best_source_w)))
assert reuse_w[3, 3] == reuse_w[:, 3].max()
plt.figure(figsize=(5, 3.6))
plt.imshow(reuse_w, cmap="magma", vmin=0, vmax=1)
plt.colorbar(label="feature reuse")
plt.xticks(range(len(targets_w)), targets_w)
plt.yticks(range(len(sources_w)), sources_w)
plt.title("4: representation transfer heatmap")
plt.show()
```
▶ What you'll see: tasks reuse different pretrained features; agent behavior depends especially on tool-related features.

*Why it's done this way: transfer matrices force us to ask which learned features move across tasks, instead of treating “general” as a single undifferentiated property.*

### 5. Scaling laws are smooth price curves

A scaling-law sketch writes validation loss as $L(C)=A C^{-\alpha}$, where $C$ is compute, $A$ is a model-family constant, and $\alpha>0$ is the scaling exponent. With $A=1.2$ and $\alpha=0.08$, increasing compute from $10^{20}$ to $10^{24}$ lowers loss, but each hundredfold increase multiplies loss by the fixed factor $100^{-0.08}$.

```python
C_w = np.array([1e20, 1e22, 1e24])
A_w, alpha_w = 1.2, 0.08
L_w = A_w * C_w ** (-alpha_w)
ratio_w = (100.0) ** (-alpha_w)
print("losses:", np.round(L_w, 6))
print("hundredfold compute loss factor:", round(ratio_w, 3), "relative reduction:", round(1 - ratio_w, 3))
assert np.allclose(np.round(L_w, 6), [0.030143, 0.020854, 0.014427])
plt.figure(figsize=(5, 3.2))
plt.loglog(C_w, L_w, marker="o", color="purple")
plt.xlabel("compute C (FLOPs)")
plt.ylabel("validation loss L(C)")
plt.title("5: scaling law loss vs compute")
plt.show()
```
▶ What you'll see: a straight line on log-log axes; the loss improves predictably but slowly.

*Why it's done this way: log-log plots make the exponent the slope, so scaling is a measurable economic tradeoff rather than a vague claim that “bigger is better.”*

### 6. Training compute is dominated by parameters and tokens

A rough transformer training rule is $C\approx 6ND$, where $N$ is parameter count and $D$ is training tokens. For $N=70$ billion and $D=300$ billion, the estimate is $1.26\times10^{23}$ FLOPs. Chinchilla-style reasoning says that for a fixed compute budget, parameters and tokens should be balanced instead of making one enormous and starving the other.

```python
N_w = np.array([7e9, 13e9, 34e9, 70e9, 130e9])  # candidate parameter counts.
budget_w = 1.26e23  # fixed compute budget.
D_frontier_w = budget_w / (6 * N_w)  # tokens allowed by C ≈ 6ND.
N_ref_w, D_ref_w = 70e9, 300e9
C_ref_w = 6 * N_ref_w * D_ref_w
print("70B × 300B FLOPs:", "%.2e" % C_ref_w)
assert abs(C_ref_w - 1.26e23) / 1.26e23 < 1e-12
plt.figure(figsize=(5, 3.2))
plt.loglog(N_w, D_frontier_w, marker="o", label="compute-optimal frontier")
plt.scatter([N_ref_w], [D_ref_w], color="red", label="70B, 300B")
plt.xlabel("parameters N")
plt.ylabel("tokens D under fixed compute")
plt.title("6: Chinchilla-style compute frontier")
plt.legend()
plt.show()
```
▶ What you'll see: under a fixed FLOP budget, using more parameters forces fewer tokens, and vice versa.

*Why it's done this way: the frontier turns “scale the model” into a resource allocation problem between parameters and data.*

### 7. Emergent abilities can look jumpy after a threshold

Average loss changes smoothly, but a downstream capability can appear abruptly when accuracy crosses a practical threshold. This does not require magic: if a task needs several subskills at once, the measured success rate may stay near zero until the weakest subskill improves enough. We simulate a thresholded ability as a smooth sigmoid over log compute.

```python
compute_w = np.logspace(19, 25, 80)
logc_w = np.log10(compute_w)
ability_w = 1 / (1 + np.exp(-3.0 * (logc_w - 22.4)))  # smooth latent competence.
pass_rate_w = (ability_w > 0.65).astype(float)  # benchmark appears discrete after thresholding.
first_pass_w = compute_w[np.argmax(pass_rate_w > 0)]
print("first threshold pass compute:", "%.2e" % first_pass_w)
assert first_pass_w > 1e22
plt.figure(figsize=(5, 3.2))
plt.semilogx(compute_w, ability_w, label="latent ability")
plt.semilogx(compute_w, pass_rate_w, linestyle="--", label="thresholded benchmark")
plt.xlabel("compute")
plt.ylabel("ability / pass rate")
plt.title("7: emergent-looking ability jump")
plt.legend()
plt.show()
```
▶ What you'll see: a smooth competence curve can create a sudden benchmark jump once a cutoff is crossed.

*Why it's done this way: the plot separates smooth scaling from discrete evaluation, preventing us from over-reading a jump as proof that average loss guaranteed reasoning.*

### 8. A generalist score is a mixture, so averages can hide weaknesses

Generalist systems are often evaluated by a weighted mixture of task losses. With task losses $0.20,0.40,0.60$ and weights $0.5,0.3,0.2$, the average is $0.340$. That number is useful, but it can hide a low-frequency tool weakness if the tool-use weight is small.

```python
losses_mix_w = np.array([0.20, 0.40, 0.60])
weights_mix_w = np.array([0.50, 0.30, 0.20])
mixture_w = float(np.sum(weights_mix_w * losses_mix_w))
print("mixture loss:", round(mixture_w, 3))
assert round(mixture_w, 3) == 0.340
plt.figure(figsize=(4.8, 3.2))
plt.imshow((weights_mix_w * losses_mix_w)[None, :], cmap="viridis", aspect="auto")
plt.colorbar(label="weighted loss contribution")
plt.xticks(range(3), ["common", "medium", "rare tool"])
plt.yticks([0], ["mixture"])
plt.title("8: mixture score can hide rare weakness")
plt.show()
```
▶ What you'll see: the rare tool task has the largest raw loss but a modest weighted contribution.

*Why it's done this way: visualizing weighted contributions shows why a respectable average does not guarantee reliability on every important subtask.*

### 9. Agents route among parameters, retrieval, and tools

The design decision people gloss over is where knowledge should live. Parameters are fast but stale, retrieval is fresh but search-dependent, and tools are precise but require planning and verification. A generalist agent routes among these stores by scoring actions such as answer, retrieve, and calculate; a softmax converts logits into route probabilities.

```python
routes_w = ["answer", "retrieve", "calculate"]
logits_w = np.array([2.0, 1.0, -0.5])
probs_w = np.exp(logits_w - np.max(logits_w))
probs_w = probs_w / probs_w.sum()
costs_w = np.array([0.2, 0.5, 0.8])
expected_cost_w = float(np.sum(probs_w * costs_w))
print("route probabilities:", dict(zip(routes_w, np.round(probs_w, 3))))
print("expected cost:", round(expected_cost_w, 3))
assert np.allclose(np.round(probs_w, 3), [0.690, 0.254, 0.057])
plt.figure(figsize=(4.8, 3.2))
plt.imshow((probs_w * costs_w)[None, :], cmap="plasma", aspect="auto")
plt.colorbar(label="probability × cost")
plt.xticks(range(3), routes_w)
plt.yticks([0], ["agent route"])
plt.title("9: route-cost heatmap")
plt.show()
```
▶ What you'll see: most probability goes to answering directly, but retrieval and calculation still contribute to expected cost.

*Why it's done this way: routing is a probability model under uncertainty; calibrated route probabilities matter because confident wrong tool choices can be expensive.*

### 10. Acting, observing, and revising creates an agent loop

A model becomes an agent when it repeatedly observes state, chooses an action or tool, reads the result, and revises the plan. Reinforcement learning reappears because actions have delayed consequences: a cheap direct answer can fail, while a retrieval or calculator call can improve final reward at extra cost. We simulate success as a function of the number of observe-act-revise steps.

```python
steps_w = np.arange(1, 8)
success_plain_w = 0.30 + 0.35 * (1 - np.exp(-steps_w / 4.0))
success_tool_w = 0.38 + 0.50 * (1 - np.exp(-steps_w / 2.2))
net_tool_w = success_tool_w - 0.02 * steps_w  # simple reward after per-step cost.
print("best net tool step:", int(steps_w[np.argmax(net_tool_w)]))
assert net_tool_w.max() > success_plain_w.max()
plt.figure(figsize=(5, 3.2))
plt.plot(steps_w, success_plain_w, marker="o", label="no tools")
plt.plot(steps_w, net_tool_w, marker="o", label="tool loop, cost-adjusted")
plt.xlabel("observe-act-revise steps")
plt.ylabel("success / reward")
plt.title("10: agent loop improves with verified tool use")
plt.legend()
plt.show()
```
▶ What you'll see: tool-using loops can outperform direct answering, but extra steps eventually face a cost tradeoff.

*Why it's done this way: an agent is not just a larger model — it is a control loop whose reliability depends on when it gathers evidence, invokes tools, and stops.*

## 🛠️ Setup

```python
import numpy as np  # numerical arrays, random simulation, power laws, and from-scratch linear algebra.
import matplotlib.pyplot as plt  # visualizations for scaling laws, transfer heatmaps, frontiers, and ICL curves.
np.random.seed(0)  # reproducible stochastic examples.

def power_loss(x, A, alpha, floor=0.0):  # compute A*x^-alpha plus an optional irreducible floor.
    x = np.asarray(x, dtype=float)
    return A * x ** (-alpha) + floor

def fit_power_law(x, y, floor=0.0):  # fit y - floor = A*x^-alpha by linear regression in log space.
    x = np.asarray(x, dtype=float)
    y = np.asarray(y, dtype=float) - floor
    assert np.all(x > 0) and np.all(y > 0)
    X = np.c_[np.ones_like(x), -np.log(x)]
    beta = np.linalg.solve(X.T @ X, X.T @ np.log(y))
    return float(np.exp(beta[0])), float(beta[1])

def softmax(z):  # convert action logits into route probabilities.
    z = np.asarray(z, dtype=float)
    ez = np.exp(z - np.max(z))
    return ez / ez.sum()

def weighted_mixture(losses, weights):  # compute a weighted multitask objective.
    losses = np.asarray(losses, dtype=float)
    weights = np.asarray(weights, dtype=float)
    assert np.isclose(weights.sum(), 1.0)
    return float(np.sum(losses * weights))

def tiny_icl_accuracy(shots, capacity=1.0):  # smooth toy model of in-context learning accuracy.
    shots = np.asarray(shots, dtype=float)
    return 0.35 + 0.55 * (1 - np.exp(-capacity * shots / 4.0))
```

## 🟢 Basics

### Basic 1 — Compute validation loss from a scaling law

**Goal.** Evaluate $L(C)=A C^{-\alpha}$ at several compute budgets, because foundation-model scaling is usually discussed as a power law rather than a linear improvement. We build it in 1 step.

```python
C_b1 = np.array([1e20, 1e22, 1e24])
L_b1 = power_loss(C_b1, A=1.2, alpha=0.08)
print("losses:", np.round(L_b1, 6))
assert np.allclose(np.round(L_b1, 6), [0.030143, 0.020854, 0.014427])
plt.figure(figsize=(5, 3))
plt.loglog(C_b1, L_b1, marker="o", color="navy")
plt.title("Basic 1: loss vs compute")
plt.xlabel("compute C")
plt.ylabel("validation loss")
plt.show()
```
▶ What you'll see: loss falls with compute, but the tiny exponent makes progress gradual.

👀 Takeaway: scaling laws are smooth price curves, not guarantees of perfect reasoning.

### Basic 2 — Measure the hundredfold-compute factor

**Goal.** Compute $L(100C)/L(C)=100^{-\alpha}$, because the exponent tells us the fixed gain from multiplying compute. We build it in 1 step.

```python
alpha_b2 = 0.08
factor_b2 = 100 ** (-alpha_b2)
reduction_b2 = 1 - factor_b2
print("factor:", round(factor_b2, 3), "reduction:", round(reduction_b2, 3))
assert round(factor_b2, 3) == 0.692
C_b2 = np.logspace(20, 24, 50)
plt.figure(figsize=(5, 3))
plt.loglog(C_b2, power_loss(C_b2, 1.2, alpha_b2), label="L(C)")
plt.loglog(100 * C_b2, factor_b2 * power_loss(C_b2, 1.2, alpha_b2), linestyle="--", label="L(100C)")
plt.title("Basic 2: fixed gain from 100× compute")
plt.xlabel("compute")
plt.ylabel("loss")
plt.legend()
plt.show()
```
▶ What you'll see: the shifted curve stays a constant multiplicative factor below the original.

👀 Takeaway: the exponent converts a resource multiplier into a predictable loss multiplier.

### Basic 3 — Estimate transformer training FLOPs

**Goal.** Use $C\approx6ND$ for parameters $N$ and tokens $D$, because training compute is dominated by multiplying these two scales. We build it in 1 step.

```python
N_b3, D_b3 = 70e9, 300e9
C_b3 = 6 * N_b3 * D_b3
print("estimated FLOPs:", "%.2e" % C_b3)
assert C_b3 == 1.26e23
Ns_b3 = np.logspace(9, 12, 50)
Ds_b3 = C_b3 / (6 * Ns_b3)
plt.figure(figsize=(5, 3))
plt.loglog(Ns_b3, Ds_b3, color="teal")
plt.scatter([N_b3], [D_b3], color="red")
plt.title("Basic 3: C ≈ 6ND frontier")
plt.xlabel("parameters N")
plt.ylabel("tokens D")
plt.show()
```
▶ What you'll see: the 70B-parameter, 300B-token point lies on a fixed-compute frontier.

👀 Takeaway: parameter count and token count trade off under a fixed training budget.

### Basic 4 — Fit a power-law exponent from scratch

**Goal.** Recover $\alpha$ using log-space linear regression, because power-law fitting is just least squares after taking logarithms. We build it in 1 step.

```python
C_b4 = np.logspace(18, 24, 7)
L_b4 = power_loss(C_b4, A=1.5, alpha=0.06, floor=0.01)
A_b4, alpha_b4 = fit_power_law(C_b4, L_b4, floor=0.01)
print("A_hat:", round(A_b4, 3), "alpha_hat:", round(alpha_b4, 3))
assert abs(alpha_b4 - 0.06) < 1e-10
plt.figure(figsize=(5, 3))
plt.loglog(C_b4, L_b4, marker="o", label="data")
plt.loglog(C_b4, power_loss(C_b4, A_b4, alpha_b4, floor=0.01), linestyle="--", label="fit")
plt.title("Basic 4: fitting L=A C^-α")
plt.xlabel("compute")
plt.ylabel("loss")
plt.legend()
plt.show()
```
▶ What you'll see: the fitted line overlays the simulated observations.

👀 Takeaway: the scaling exponent is the negative slope in log-log coordinates.

**Goal.** Combine task losses with task weights, because aggregate benchmarks are weighted mixtures. We build it in 1 step.

losses_b7 = np.array([0.20, 0.40, 0.60])

### Basic 9 — Show an emergent-looking threshold

**Goal.** Threshold a smooth competence curve, because benchmark pass rates can jump even when underlying loss improves smoothly. We build it in 1 step.
