# 25.4 — Program Synthesis

Program synthesis turns examples, constraints, and a restricted language into executable code. In this lesson we build a tiny synthesizer from scratch: enumerate programs in a small DSL, score them on input-output examples, prune inconsistent candidates, and test whether the discovered rule generalizes beyond the examples that selected it.

## 📖 Concept walkthrough — build each idea from scratch

Before the worked examples, we build program synthesis one idea at a time. Run each cell in order and read the printed intermediate values. The walkthrough is self-contained and uses a `_w` suffix so it never clashes with later examples.

```python
import numpy as np  # arrays for examples, losses, and candidate tables.
import matplotlib.pyplot as plt  # visual diagnostics for every synthesis step.
np.random.seed(0)  # reproducible ordering whenever ties are broken.
```

### 1. A tiny DSL is the search space

Program synthesis cannot search "all code." We first choose a **domain-specific language** (DSL): the finite set of program templates the synthesizer is allowed to try. Here the grammar contains `x+c`, `c*x`, and `x^2+c` for a few constants. This is the bias-complexity tradeoff: if the true program is inside the DSL, search can find it; if not, exact synthesis is impossible.

```python
constants_w = np.array([-2, -1, 0, 1, 2])  # small constant set keeps enumeration finite.
programs_w = []  # each candidate stores a name, size, and callable behavior.
for c_w in constants_w:  # enumerate linear shifts.
    programs_w.append((f"x+{c_w}", 1, lambda x, c=c_w: x + c))
for c_w in constants_w:  # enumerate linear scales.
    programs_w.append((f"{c_w}*x", 1, lambda x, c=c_w: c * x))
for c_w in constants_w:  # enumerate quadratic shifts.
    programs_w.append((f"x^2+{c_w}", 2, lambda x, c=c_w: x**2 + c))
print("candidate programs:", len(programs_w))
print([name for name, size, fn in programs_w])
```
▶ What you'll see: 15 candidate programs, grouped by the three templates in the DSL.

```python
sizes_w = np.array([size for name, size, fn in programs_w])  # extract DSL sizes.
labels_w, counts_w = np.unique(sizes_w, return_counts=True)  # count candidates by size.
plt.figure(figsize=(4.6, 3))
plt.bar([f"size {s}" for s in labels_w], counts_w, color="steelblue")
plt.title("1: candidates by DSL program size")
plt.ylabel("number of programs")
plt.show()
```
▶ What you'll see: most candidates are tiny, and only the quadratic family has size 2.

*Why it's done this way:* restricting the grammar turns an impossible search over arbitrary code into a finite list whose members can be executed and compared.

### 2. Input-output examples become a specification

A synthesis task is defined by examples such as $0\mapsto1$, $-2\mapsto5$, and $2\mapsto5$. These are not training labels for a predictor; they are behavioral requirements for code. A candidate program is good only if running it on the inputs produces the requested outputs.

```python
x_w = np.array([0, -2, -1, 1, 2])  # specification inputs.
y_w = x_w**2 + 1  # intended behavior: x^2 + 1.
print("examples:", list(zip(x_w, y_w)))
print("target outputs:", y_w)
```
▶ What you'll see: five input-output examples that describe the intended rule.

```python
plt.figure(figsize=(4.6, 3))
plt.scatter(x_w, y_w, s=80, color="black", label="examples")
plt.plot(np.sort(x_w), np.sort(x_w)**2 + 1, color="seagreen", label="x^2+1")
plt.title("2: examples specify behavior")
plt.xlabel("input x")
plt.ylabel("output y")
plt.legend()
plt.show()
```
▶ What you'll see: the examples lie on the curve $x^2+1$.

*Why it's done this way:* examples are executable tests; the synthesizer can score any program by running it on exactly these inputs.

### 3. Enumerative synthesis scores every candidate

The simplest synthesizer tries every DSL program, evaluates it on the examples, and computes a loss. We use mean squared error, so exact matches receive loss 0 and near misses receive small positive loss. The winner is the candidate with minimum loss.

```python
losses_w = []  # store one MSE per candidate.
satisfied_w = []  # store how many examples each candidate matches exactly.
for name_w, size_w, fn_w in programs_w:
    pred_w = fn_w(x_w)  # execute candidate on all inputs.
    losses_w.append(float(np.mean((pred_w - y_w) ** 2)))
    satisfied_w.append(int(np.sum(pred_w == y_w)))
losses_w = np.array(losses_w)
satisfied_w = np.array(satisfied_w)
best_w = int(np.argmin(losses_w))
print("best program:", programs_w[best_w][0], "loss:", losses_w[best_w])
assert programs_w[best_w][0] == "x^2+1" and losses_w[best_w] == 0.0
```
▶ What you'll see: `x^2+1` is the unique zero-loss program.

```python
order_w = np.argsort(losses_w)[:6]  # show the best few candidates.
plt.figure(figsize=(6, 3))
plt.bar([programs_w[i][0] for i in order_w], losses_w[order_w], color="darkorange")
plt.title("3: lowest candidate losses")
plt.ylabel("MSE on examples")
plt.xticks(rotation=25)
plt.show()
```
▶ What you'll see: the exact program has loss 0; nearby quadratic shifts have small loss.

*Why it's done this way:* scoring converts symbolic search into an optimization view, even though the candidate set is discrete.

### 4. Version-space pruning removes inconsistent programs

The **version space** is the set of programs still consistent with the examples seen so far. After one example, multiple programs can fit. After more examples, inconsistent candidates are pruned away. In this tiny DSL, the second example distinguishes the alias `x+1` from the intended quadratic rule.

```python
remaining_counts_w = []  # number of exact-fit programs after the first m examples.
remaining_names_w = []  # names of candidates remaining after each prefix.
for m_w in range(1, len(x_w) + 1):
    keep_w = []
    for name_w, size_w, fn_w in programs_w:
        if np.all(fn_w(x_w[:m_w]) == y_w[:m_w]):
            keep_w.append(name_w)
    remaining_counts_w.append(len(keep_w))
    remaining_names_w.append(keep_w)
print("remaining names after each prefix:", remaining_names_w)
assert remaining_counts_w == [2, 1, 1, 1, 1]
```
▶ What you'll see: two programs fit the first example, but only one remains after two examples.

```python
plt.figure(figsize=(5, 3))
plt.plot(np.arange(1, len(x_w) + 1), remaining_counts_w, marker="o", color="crimson")
plt.title("4: version-space pruning")
plt.xlabel("number of examples used")
plt.ylabel("exact-fit programs remaining")
plt.xticks(np.arange(1, len(x_w) + 1))
plt.show()
```
▶ What you'll see: the candidate set collapses as examples add constraints.

*Why it's done this way:* pruning avoids treating every later candidate as equally plausible once an earlier example has already falsified it.

### 5. Ambiguity means exact fit is not enough

With too few examples, a wrong program can be perfectly consistent with the specification. On the single example $0\mapsto1$, both `x+1` and `x^2+1` have zero loss. They only disagree when tested away from the weak specification.

```python
amb_x_w = np.array([0])  # intentionally underspecified behavior.
amb_y_w = np.array([1])
fits_w = []
for name_w, size_w, fn_w in programs_w:
    if np.all(fn_w(amb_x_w) == amb_y_w):
        fits_w.append((name_w, fn_w))
print("zero-loss programs on one example:", [name for name, fn in fits_w])
assert set(name for name, fn in fits_w) == {"x+1", "x^2+1"}
```
▶ What you'll see: two distinct programs satisfy the weak one-point spec.

```python
grid_w = np.arange(-3, 4)
plt.figure(figsize=(5, 3))
for name_w, fn_w in fits_w:
    plt.plot(grid_w, fn_w(grid_w), marker="o", label=name_w)
plt.scatter(amb_x_w, amb_y_w, s=90, color="black", zorder=5, label="given example")
plt.title("5: identical on the spec, different elsewhere")
plt.xlabel("x")
plt.ylabel("program output")
plt.legend()
plt.show()
```
▶ What you'll see: the two programs meet at the given example but diverge on other inputs.

*Why it's done this way:* a synthesizer must be judged with additional tests or constraints, because training examples alone may underspecify the intended code.

### 6. Held-out checks reward the right structure

If the selected program has the right structure, it should also match held-out behavior such as $3\mapsto10$ and $4\mapsto17$. This is not magic generalization from a neural model; it is the consequence of recovering an executable rule rather than memorizing a lookup table.

```python
best_name_w, best_size_w, best_fn_w = programs_w[best_w]
held_x_w = np.array([3, 4])
held_y_w = held_x_w**2 + 1
held_pred_w = best_fn_w(held_x_w)
print("selected:", best_name_w)
print("held-out predictions:", held_pred_w)
assert np.all(held_pred_w == held_y_w)
```
▶ What you'll see: the synthesized program returns 10 and 17 on new inputs.

```python
all_x_w = np.arange(-3, 5)
plt.figure(figsize=(5, 3))
plt.plot(all_x_w, best_fn_w(all_x_w), color="seagreen", label="synthesized")
plt.scatter(x_w, y_w, color="black", label="synthesis examples")
plt.scatter(held_x_w, held_y_w, color="red", marker="x", s=90, label="held-out checks")
plt.title("6: synthesized program vs spec checks")
plt.xlabel("x")
plt.ylabel("output")
plt.legend()
plt.show()
```
▶ What you'll see: training examples and held-out checks lie on the same synthesized curve.

*Why it's done this way:* held-out checks expose overfit or ambiguous programs that merely passed the original examples.

## 🛠️ Setup

```python
import numpy as np  # arrays, vectorized evaluation, losses, and deterministic toy data.
import matplotlib.pyplot as plt  # all examples include a relevant visualization.
np.random.seed(0)  # keep example ordering reproducible.

def make_tiny_dsl(constants=(-2, -1, 0, 1, 2)):  # build the lesson DSL from scratch.
    programs = []  # store dictionaries so names, sizes, and functions travel together.
    for c in constants:  # x+c family.
        programs.append({"name": f"x+{c}", "size": 1, "fn": lambda x, c=c: x + c})
    for c in constants:  # c*x family.
        programs.append({"name": f"{c}*x", "size": 1, "fn": lambda x, c=c: c * x})
    for c in constants:  # x^2+c family.
        programs.append({"name": f"x^2+{c}", "size": 2, "fn": lambda x, c=c: x**2 + c})
    return programs  # return finite candidate list.

def score_program(program, x, y):  # compute numeric fit and exact-match count.
    pred = program["fn"](x)  # execute candidate on the specification inputs.
    mse = float(np.mean((pred - y) ** 2))  # mean squared error ranks near misses.
    matched = int(np.sum(pred == y))  # exact satisfied examples support pruning views.
    return pred, mse, matched  # return all useful diagnostics.

def synthesize(programs, x, y):  # exhaustive enumerative synthesizer.
    rows = []  # collect scores for every candidate.
    for program in programs:
        pred, mse, matched = score_program(program, x, y)
        rows.append((program["name"], program["size"], mse, matched, pred, program))
    rows.sort(key=lambda r: (r[2], r[1], r[0]))  # prefer low loss, then smaller programs, then stable names.
    return rows  # best candidate is rows[0].

def plot_spec(x, y, title):  # small helper to draw input-output examples.
    plt.figure(figsize=(4.5, 3))
    plt.scatter(x, y, s=80, color="black")
    plt.title(title)
    plt.xlabel("input x")
    plt.ylabel("output y")
    plt.show()
```

#### B2. Enumerate a tiny DSL

**Goal.** Build candidate programs from three templates, because enumeration only works after the language is finite. We build it in 2 steps.

```python
programs_b2 = make_tiny_dsl()  # create x+c, c*x, and x^2+c candidates.
names_b2 = [p["name"] for p in programs_b2]  # extract names for inspection.
```

#### A5. Use counterexamples to refine the specification
