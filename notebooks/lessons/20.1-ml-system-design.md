# 20.1 — ML System Design

A production ML system is not just a trained model; it is a promise that predictions arrive accurately, quickly, reliably, and affordably under real traffic. In this lesson, we turn system-design words like latency budget, capacity headroom, SLO, error budget, and queueing into small NumPy calculations so model choice becomes an inspectable engineering tradeoff instead of a leaderboard reflex.

### 1. Turn design goals into a weighted utility score

The first design move is to write down what the system must optimize before choosing a model. A useful toy score is

$$S=\sum_j w_j m_j,$$

where each $m_j$ is a normalized metric such as quality, latency score, or reliability score, and the weights $w_j$ sum to 1. This does not make the score magically objective; it makes the tradeoff explicit enough to debate. If latency matters, it must have a weight. If reliability matters, it must appear before the model consumes the whole budget.

```python
metrics_w = np.array([0.82, 0.73, 0.90])  # normalized quality, latency, and reliability scores.
weights_w = np.array([0.50, 0.30, 0.20])  # business choice: quality matters most, but not alone.
print("weights sum:", weights_w.sum())  # a convex combination needs weights that sum to 1.
print("metrics:", metrics_w)  # inspect the comparable, normalized scores.
assert abs(weights_w.sum() - 1.0) < 1e-12
```
▶ What you'll see: the three weights sum to 1, so the final score stays on the same 0–1 scale as the normalized metrics.

```python
score_w = float(np.sum(weights_w * metrics_w))  # weighted utility S = Σ w_j m_j.
parts_w = weights_w * metrics_w  # contribution from each production metric.
print("contributions:", np.round(parts_w, 3))  # [0.410, 0.219, 0.180].
print("design score S:", round(score_w, 3))  # 0.809.
assert round(score_w, 3) == 0.809
```
▶ What you'll see: the design score is 0.809, with quality contributing the largest share but not the only share.

```python
plt.figure(figsize=(4.6, 3))
plt.bar(["quality", "latency", "reliability"], parts_w, color=["teal", "orange", "seagreen"])
plt.ylabel("w × metric")
plt.title("1: utility score contributions")
plt.show()
```
▶ What you'll see: a bar chart showing which requirement is driving the final score.

*Why it's done this way:* a weighted sum is the simplest convex tradeoff model: because $\sum w_j=1$, each term is a share of the decision rather than an unbounded bonus. The math forces hidden preferences into visible numbers, so a slower model can win only if its quality gain is large enough to pay for the latency and reliability cost.

### 2. Split traffic before changing the serving path

A new ML candidate should rarely receive all production traffic at once. If the system serves 10,000 requests per day and we route 30% to the candidate, then 3,000 calls exercise the risky path while 7,000 stay on the safe path. This turns rollout risk into arithmetic and gives monitoring enough volume to compare behavior without betting the entire product.

```python
daily_requests_w = 10_000  # total product requests per day.
candidate_fraction_w = 0.30  # canary or experiment traffic share.
candidate_calls_w = daily_requests_w * candidate_fraction_w  # requests through the new model path.
safe_calls_w = daily_requests_w - candidate_calls_w  # requests kept on the champion path.
print("candidate calls/day:", int(candidate_calls_w))
print("safe-path calls/day:", int(safe_calls_w))
assert int(candidate_calls_w) == 3000 and int(safe_calls_w) == 7000
```
▶ What you'll see: 3,000 candidate calls and 7,000 safe-path calls, matching the rollout calculation.

```python
arms_w = np.array([safe_calls_w, candidate_calls_w])
plt.figure(figsize=(4.4, 3))
plt.bar(["safe path", "candidate"], arms_w, color=["gray", "purple"])
plt.ylabel("requests/day")
plt.title("2: traffic split controls rollout exposure")
plt.show()
```
▶ What you'll see: the safe path still carries most traffic while the candidate gets enough examples to inspect.

*Why it's done this way:* traffic splitting separates model evaluation from global blast radius. The fraction is a probability gate: each request has a 0.30 chance of taking the candidate path, so expected candidate load is $10{,}000\times0.30=3{,}000$. That expectation is the capacity and monitoring input for the new path.

### 3. Budget latency as components, then inspect tails

Latency budgets are additive along a sequential request path. If feature lookup costs 35 ms, model inference costs 55 ms, and postprocessing costs 20 ms, then the median-ish path budget is 110 ms. But user promises are usually about high percentiles, not averages. A mean under 150 ms can still violate a p99 target if a small fraction of requests queue or hit slow dependencies.

```python
feature_ms_w = 35.0
model_ms_w = 55.0
post_ms_w = 20.0
target_ms_w = 150.0
budget_parts_w = np.array([feature_ms_w, model_ms_w, post_ms_w])
total_ms_w = float(budget_parts_w.sum())
slack_ms_w = target_ms_w - total_ms_w
print("component latency ms:", budget_parts_w)
print("total latency:", total_ms_w, "slack:", slack_ms_w)
assert total_ms_w == 110.0 and slack_ms_w == 40.0
```
▶ What you'll see: the deterministic component budget totals 110 ms, leaving 40 ms of slack under a 150 ms target.

```python
rng_w = np.random.default_rng(0)
latencies_w = rng_w.lognormal(mean=np.log(85), sigma=0.32, size=5000) + 20  # synthetic request latency in ms.
p50_w, p95_w, p99_w = np.percentile(latencies_w, [50, 95, 99])
print("p50/p95/p99 ms:", np.round([p50_w, p95_w, p99_w], 1))
print("p99 meets 150ms target?", bool(p99_w <= target_ms_w))
assert p50_w < target_ms_w and p99_w > target_ms_w
```
▶ What you'll see: p50 is comfortably below 150 ms, but p99 is above the target — averages hide user pain.

```python
plt.figure(figsize=(5, 3))
plt.hist(latencies_w, bins=45, color="steelblue", alpha=0.8)
plt.axvline(p50_w, color="black", linestyle="--", label=f"p50={p50_w:.0f}ms")
plt.axvline(p99_w, color="red", linestyle="--", label=f"p99={p99_w:.0f}ms")
plt.axvline(target_ms_w, color="green", linestyle=":", label="150ms SLO")
plt.xlabel("latency (ms)")
plt.ylabel("request count")
plt.title("3: latency histogram with p50 and p99")
plt.legend()
plt.show()
```
▶ What you'll see: most requests cluster near the middle, but the right tail crosses the SLO line.

*Why it's done this way:* sequential latency adds because the user waits for each stage in order. Percentiles are order statistics: p99 is the value only 1% of requests exceed. Designing for p99 protects the unlucky tail users, while designing for the mean protects a request that almost nobody exactly experiences.

### 4. Multiply required dependencies and spend an error budget

When two required services are both needed for a prediction, availability multiplies. If feature serving is available 99.5% of the time and model serving is available 99.0% of the time, the chain availability is $0.995\times0.990=0.98505$. That is less than either component because every required dependency is another way to fail.

```python
feature_avail_w = 0.995
model_avail_w = 0.990
chain_avail_w = feature_avail_w * model_avail_w
chain_error_w = 1 - chain_avail_w
print("chain availability:", round(chain_avail_w, 5))
print("chain error rate:", round(chain_error_w, 5))
assert round(chain_avail_w, 5) == 0.98505
```
▶ What you'll see: the two-service chain is 98.505% available, not 99%+.

```python
slo_w = 0.99
allowed_error_w = 1 - slo_w
spent_error_w = chain_error_w / allowed_error_w
print("allowed error budget:", round(allowed_error_w, 3))
print("budget spent:", round(spent_error_w, 3), "x")
assert spent_error_w > 1.0
```
▶ What you'll see: the chain spends more than one full 99% SLO error budget.

```python
services_w = ["feature", "model", "chain"]
avails_w = [feature_avail_w, model_avail_w, chain_avail_w]
plt.figure(figsize=(4.8, 3))
plt.bar(services_w, avails_w, color=["teal", "orange", "crimson"])
plt.axhline(slo_w, color="black", linestyle="--", label="99% SLO")
plt.ylim(0.97, 1.0)
plt.ylabel("availability")
plt.title("4: required dependencies multiply")
plt.legend()
plt.show()
```
▶ What you'll see: the chain bar falls below the 99% SLO line even though individual components look close.

*Why it's done this way:* for required independent-ish services, success means service A succeeds AND service B succeeds, so probabilities multiply. Error budget is just the complement: a 99% SLO allows 1% failures, so any design with failure probability above 0.01 is mathematically over budget before launch.

### 5. Use Little's law to connect throughput, latency, and concurrency

Capacity planning needs units. Throughput is requests per second, latency is seconds per request, and concurrency is requests in flight. Little's law says

$$L=\lambda W,$$

where $L$ is average in-flight work, $\lambda$ is arrival rate, and $W$ is average time in system. If a service receives 85 qps and spends 110 ms per request, it carries about 9.35 concurrent requests on average.

```python
load_qps_w = 85.0
service_time_s_w = total_ms_w / 1000.0
inflight_w = load_qps_w * service_time_s_w
capacity_qps_w = 120.0
headroom_qps_w = capacity_qps_w - load_qps_w
headroom_frac_w = headroom_qps_w / capacity_qps_w
print("average in-flight requests:", round(inflight_w, 2))
print("headroom qps:", headroom_qps_w, "headroom fraction:", round(headroom_frac_w, 3))
assert round(inflight_w, 2) == 9.35 and round(headroom_frac_w, 3) == 0.292
```
▶ What you'll see: the service averages 9.35 in-flight requests and has 35 qps, or 29.2%, capacity headroom.

```python
loads_w = np.linspace(10, 118, 80)
service_time_fixed_s_w = 1 / capacity_qps_w  # one worker-equivalent service rate for a queueing sketch.
util_w = loads_w / capacity_qps_w
little_inflight_w = loads_w * service_time_s_w
plt.figure(figsize=(5, 3))
plt.plot(loads_w, little_inflight_w, color="purple")
plt.axvline(load_qps_w, color="black", linestyle="--", label="current load")
plt.xlabel("load (qps)")
plt.ylabel("average in-flight L")
plt.title("5: Little's law scales load into concurrency")
plt.legend()
plt.show()
```
▶ What you'll see: average concurrency rises linearly with load when average latency is fixed.

*Why it's done this way:* Little's law is a conservation law for stable systems: arrivals times residence time equals work present. It lets you translate a latency target into thread pools, connection pools, and queue depths without guessing from CPU charts alone.

### 6. Queueing explains why high utilization hurts tail latency

The dangerous part of capacity is not the linear region; it is the queue. In an M/M/1 approximation, one server handles Poisson arrivals at rate $\lambda$ and exponential service at rate $\mu$. Average response time is

$$W=\frac{1}{\mu-\lambda}=\frac{1/\mu}{1-\rho}, \quad \rho=\lambda/\mu.$$

As utilization $\rho$ approaches 1, the denominator approaches 0 and latency explodes. This is why 90% utilization is not just 10% worse than 80% — it can be roughly twice the queueing delay.

```python
mu_w = 120.0  # service capacity in requests per second.
rhos_w = np.array([0.50, 0.70, 0.85, 0.90, 0.95])
arrival_w = rhos_w * mu_w
response_ms_w = 1000.0 / (mu_w - arrival_w)  # M/M/1 mean response time.
print("utilization:", rhos_w)
print("M/M/1 mean response ms:", np.round(response_ms_w, 1))
assert response_ms_w[-1] > 2.9 * response_ms_w[2]
```
▶ What you'll see: response time climbs gently at first, then jumps sharply near 95% utilization.

```python
rho_grid_w = np.linspace(0.05, 0.98, 160)
mean_ms_w = 1000.0 / (mu_w * (1 - rho_grid_w))
p99_mm1_ms_w = -np.log(0.01) * mean_ms_w  # exponential response-time p99 for the M/M/1 sketch.
plt.figure(figsize=(5, 3))
plt.plot(rho_grid_w, mean_ms_w, label="mean", color="teal")
plt.plot(rho_grid_w, p99_mm1_ms_w, label="p99", color="crimson")
plt.axhline(150, color="black", linestyle="--", label="150ms target")
plt.xlabel("utilization ρ")
plt.ylabel("latency (ms)")
plt.title("6: utilization-vs-latency curve")
plt.legend()
plt.show()
```
▶ What you'll see: the p99 curve crosses the target at much lower utilization than the mean curve.

*Why it's done this way:* queueing delay is nonlinear because arrivals during busy periods must wait for all work ahead of them. The $1/(1-\rho)$ term is the warning: once utilization is high, tiny load increases produce large tail-latency increases, so capacity planning needs headroom, not just average CPU below 100%.

### ✍️ Toy 1 · Weighted utility turns goals into one score

A weighted utility score makes quality, latency, and reliability tradeoffs explicit. Multiply each
metric by its weight, then add the contributions.

```python
import numpy as np
import matplotlib.pyplot as plt

t1_rng = np.random.default_rng(0)               # seeded generator for reproducibility.
t1_metrics = np.array([0.90, 0.70, 0.80])       # quality, latency, reliability  # -> [0.9 0.7 0.8]
t1_weights = np.array([0.50, 0.30, 0.20])       # decision weights               # -> [0.5 0.3 0.2]
t1_weight_sum = t1_weights.sum()                # convex weights must sum to 1   # -> 1.0
print("weight sum:", round(float(t1_weight_sum), 2))          # -> 1.0
t1_contributions = t1_weights * t1_metrics      # w_j × m_j per goal             # -> [0.45 0.21 0.16]
print("contributions:", np.round(t1_contributions, 2).tolist())   # -> [0.45, 0.21, 0.16]
t1_score = t1_contributions.sum()               # total utility                  # -> 0.82
print("utility score:", round(float(t1_score), 2))               # -> 0.82
assert abs(t1_score - 0.82) < 1e-12

plt.figure(figsize=(4.6, 2.8))
plt.bar(["quality", "latency", "reliability"], t1_contributions, color=["teal", "orange", "seagreen"])
plt.ylabel("weight × metric")
plt.title("Toy 1 · weighted utility pieces")
plt.show()
plt.close()
```
▶ What you'll see: the score `0.82` is the sum of three visible contribution bars.

### ✍️ Toy 3 · Latency budgets add, but tails decide the SLO

Sequential components add to a deterministic budget. A tiny latency sample then shows why the tail
can exceed the target even when the component sum has slack.

```python
import numpy as np

t3_rng = np.random.default_rng(0)                # seeded generator for reproducibility.
t3_parts_ms = np.array([20.0, 35.0, 15.0])       # feature, model, postprocess ms  # -> [20. 35. 15.]
t3_target_ms = 90.0                              # user-facing latency target      # -> 90.0
t3_total_ms = t3_parts_ms.sum()                  # sequential latency sum          # -> 70.0

t3_slack_ms = t3_target_ms - t3_total_ms         # remaining budget                # -> 20.0
```

### ✍️ Toy 5 · Little's law maps qps and latency to in-flight work

Little's law says average in-flight requests equal arrival rate times average time in system. The same
calculation also exposes capacity headroom.

```python
import numpy as np

t5_rng = np.random.default_rng(0)                # seeded generator for reproducibility.
t5_load_qps = 40.0                               # arrivals per second             # -> 40.0
t5_latency_s = 0.20                              # average seconds per request     # -> 0.2

print("average in-flight:", round(float(t5_inflight), 1))      # -> 8.0

t5_headroom_qps = t5_capacity_qps - t5_load_qps  # spare qps                       # -> 10.0

print("headroom fraction:", round(float(t5_headroom_fraction), 2)) # -> 0.2
assert t5_inflight == 8.0 and t5_headroom_fraction == 0.2

t5_load_grid = np.array([10.0, 20.0, 30.0, 40.0, 50.0])         # candidate loads       # -> [10. 20. 30. 40. 50.]
t5_inflight_grid = t5_load_grid * t5_latency_s                 # Little's-law curve    # -> [ 2.  4.  6.  8. 10.]
plt.figure(figsize=(4.8, 2.8))
plt.plot(t5_load_grid, t5_inflight_grid, marker="o", color="purple")

```
▶ What you'll see: in-flight work rises linearly with load, and the current point is 8 requests.

### ✍️ Toy 6 · M/M/1 utilization bends latency nonlinearly

In the M/M/1 sketch, response time is `1 / (μ - λ)`. Near saturation, small utilization increases
produce large latency jumps.

```python
import numpy as np

t6_rng = np.random.default_rng(0)                # seeded generator for reproducibility.
t6_mu_qps = 100.0                                # service capacity μ              # -> 100.0
t6_utilization = np.array([0.50, 0.80, 0.90])    # utilization values ρ             # -> [0.5 0.8 0.9]
t6_arrival_qps = t6_mu_qps * t6_utilization      # λ = ρμ                           # -> [50. 80. 90.]
print("arrival qps:", t6_arrival_qps.tolist())                 # -> [50.0, 80.0, 90.0]
t6_mean_ms = 1000.0 / (t6_mu_qps - t6_arrival_qps)              # mean response ms      # -> [ 20.  50. 100.]
print("mean response ms:", np.round(t6_mean_ms, 1).tolist())   # -> [20.0, 50.0, 100.0]
t6_p99_ms = -np.log(0.01) * t6_mean_ms          # exponential p99 sketch           # -> [ 92.1034 230.2585 460.517 ]
print("p99 response ms:", np.round(t6_p99_ms, 1).tolist())     # -> [92.1, 230.3, 460.5]
assert round(float(t6_mean_ms[-1]), 1) == 100.0 and t6_p99_ms[-1] > 4 * t6_p99_ms[0]

plt.figure(figsize=(4.8, 2.8))
plt.plot(t6_utilization, t6_mean_ms, marker="o", label="mean", color="teal")
plt.plot(t6_utilization, t6_p99_ms, marker="o", label="p99", color="crimson")
plt.xlabel("utilization ρ")
plt.ylabel("latency ms")
plt.title("Toy 6 · queueing curve")
plt.legend()
plt.show()
plt.close()
```
▶ What you'll see: mean and p99 latency bend upward sharply as utilization moves from 0.8 to 0.9.

## 🛠️ Setup

```python
import numpy as np  # NumPy handles arrays, random simulation, percentiles, and vectorized arithmetic.
import matplotlib.pyplot as plt  # Matplotlib makes latency, capacity, and tradeoff plots inspectable.
from collections import deque  # Standard-library queue container for small discrete-event simulations.
np.random.seed(0)  # Keep all random examples reproducible.

def percentile_summary(x):  # Summarize latency arrays with common service percentiles.
    x = np.asarray(x, dtype=float)  # Convert inputs to numeric arrays.
    return np.percentile(x, [50, 95, 99])  # Return p50, p95, and p99.

def mm1_mean_ms(arrival_qps, service_qps):  # Compute M/M/1 mean response time in milliseconds.
    arrival_qps = np.asarray(arrival_qps, dtype=float)  # Allow scalars or arrays.
    return 1000.0 / (service_qps - arrival_qps)  # W = 1 / (μ - λ), converted to ms.

def show_latency_hist(latencies, title, target=150):  # Draw a reusable latency histogram.
    p50, p95, p99 = percentile_summary(latencies)  # Compute percentiles for annotation.
    plt.figure(figsize=(5, 3))  # Create a compact notebook figure.
    plt.hist(latencies, bins=40, color="steelblue", alpha=0.8)  # Plot the latency distribution.
    plt.axvline(p50, color="black", linestyle="--", label=f"p50={p50:.0f}ms")  # Mark median latency.
    plt.axvline(p99, color="red", linestyle="--", label=f"p99={p99:.0f}ms")  # Mark tail latency.
    plt.axvline(target, color="green", linestyle=":", label=f"target={target}ms")  # Mark SLO target.
    plt.title(title)  # Label the plot.
    plt.xlabel("latency (ms)")  # Label the x-axis.
    plt.ylabel("count")  # Label the y-axis.
    plt.legend()  # Show percentile labels.
    plt.show()  # Display the figure.
```
