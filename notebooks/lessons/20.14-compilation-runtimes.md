# 20.14 — Compilation & Runtimes

Compilation turns a friendly tensor program into an execution plan: a graph of operations, shape assumptions, optimizer rewrites, scheduled kernels, and hardware-aware tradeoffs. In this lesson, we build a tiny NumPy-only compiler/runtime from scratch so the usual production claims — fewer kernels, less memory traffic, valid numerical tolerance, and faster steady-state latency — become inspectable numbers instead of magic.

The walkthrough is self-contained and uses a `_w` suffix on its variables so it never clashes with the examples below.

### 1. Represent a tensor computation as a graph IR

A compiler needs a representation it can inspect. Instead of immediately running `((x + 3) * 4) + ((x + 3) * 4)`, we store each operation as a small record: its name, operator, inputs, and optional constant value. That graph IR is the boundary between user code and optimizer code.

```python
def node_w(name, op, inputs=(), value=None):
    return {"name": name, "op": op, "inputs": list(inputs), "value": value}

graph_w = [
    node_w("x", "input"),
    node_w("c3", "const", value=3.0),
    node_w("c4", "const", value=4.0),
    node_w("add1", "add", ["x", "c3"]),
    node_w("mul1", "mul", ["add1", "c4"]),
    node_w("add2", "add", ["x", "c3"]),
    node_w("mul2", "mul", ["add2", "c4"]),
    node_w("out", "add", ["mul1", "mul2"]),
]
print("graph nodes:", [n["name"] + ":" + n["op"] for n in graph_w])
print("output depends on:", graph_w[-1]["inputs"])
```
▶ What you'll see: an eight-node graph where `add1/mul1` and `add2/mul2` repeat the same computation.

```python
def draw_graph_w(graph, title):
    levels = {"input": 0, "const": 0, "add": 1, "mul": 2, "fused": 2}
    xs, ys, labels = [], [], []
    for i, n in enumerate(graph):
        xs.append(levels.get(n["op"], 3))
        ys.append(-i)
        labels.append(n["name"])
    plt.figure(figsize=(6, 3.5))
    for n, x0, y0 in zip(graph, xs, ys):
        for src in n["inputs"]:
            j = labels.index(src)
            plt.plot([xs[j], x0], [ys[j], y0], color="gray", linewidth=1)
    plt.scatter(xs, ys, s=500, color="lightsteelblue", edgecolor="black")
    for x0, y0, lab in zip(xs, ys, labels):
        plt.text(x0, y0, lab, ha="center", va="center", fontsize=8)
    plt.axis("off"); plt.title(title); plt.show()

draw_graph_w(graph_w, "1: raw computation graph IR")
```
▶ What you'll see: inputs/constants on the left, arithmetic nodes in the middle, and an output depending on two duplicate branches.

*Why it's done this way:* a runtime can execute Python statements, but a compiler needs a data structure it can reason about. Naming every intermediate exposes dependencies, duplicate work, and places where later passes can safely rewrite the program without changing the mathematical result.

### 2. Interpret the graph in topological order

A graph is only executable if every node runs after the nodes it reads. A **topological schedule** is that dependency-respecting order. Our tiny graph is already listed mostly in order, but we still compute the schedule from edges because real compiler IRs should not trust input order.

```python
def topo_sort_w(graph):
    names = {n["name"] for n in graph}
    deps = {n["name"]: set(n["inputs"]) & names for n in graph}
    ready = sorted([name for name, ds in deps.items() if not ds])
    order = []
    while ready:
        cur = ready.pop(0)
        order.append(cur)
        for name in sorted(deps):
            if cur in deps[name]:
                deps[name].remove(cur)
                if not deps[name] and name not in order and name not in ready:
                    ready.append(name)
    return order

schedule_w = topo_sort_w(graph_w)
print("topological schedule:", schedule_w)
assert schedule_w.index("add1") > schedule_w.index("x")
assert schedule_w.index("out") > schedule_w.index("mul2")
```
▶ What you'll see: constants and input appear before arithmetic, and `out` appears last.

```python
def run_graph_w(graph, feeds):
    by_name = {n["name"]: n for n in graph}
    values = {}
    for name in topo_sort_w(graph):
        n = by_name[name]
        if n["op"] == "input":
            values[name] = feeds[name]
        elif n["op"] == "const":
            values[name] = n["value"]
        elif n["op"] == "add":
            values[name] = values[n["inputs"][0]] + values[n["inputs"][1]]
        elif n["op"] == "mul":
            values[name] = values[n["inputs"][0]] * values[n["inputs"][1]]
        elif n["op"] == "fused":
            a, b, c = n["inputs"]
            values[name] = (values[a] + values[b]) * values[c]
    return values

x_w = np.array([1.0, 2.0, 3.0])
vals_w = run_graph_w(graph_w, {"x": x_w})
print("compiled-IR output:", vals_w["out"])
print("eager output:", ((x_w + 3.0) * 4.0) + ((x_w + 3.0) * 4.0))
assert np.allclose(vals_w["out"], np.array([32., 40., 48.]))
```
▶ What you'll see: the graph interpreter matches the eager NumPy expression exactly on this input.

```python
order_index_w = {name: i for i, name in enumerate(schedule_w)}
plt.figure(figsize=(6, 2.8))
plt.scatter(range(len(schedule_w)), np.zeros(len(schedule_w)), s=520, color="lightblue", edgecolor="black")
for i_w, name_w in enumerate(schedule_w):
    plt.text(i_w, 0, name_w, ha="center", va="center", fontsize=8)
for n_w in graph_w:
    for src_w in n_w["inputs"]:
        if src_w in order_index_w and n_w["name"] in order_index_w:
            a_w, b_w = order_index_w[src_w], order_index_w[n_w["name"]]
            plt.annotate("", xy=(b_w - 0.25, 0.08), xytext=(a_w + 0.25, 0.08),
                         arrowprops={"arrowstyle": "->", "color": "gray", "lw": 0.8})
plt.yticks([]); plt.xlabel("execution step"); plt.title("2: topological runtime schedule")
plt.show()
```
▶ What you'll see: every dependency arrow points forward in the execution order, so no node runs before its inputs exist.

*Why it's done this way:* topological scheduling separates correctness from textual order. The runtime can now execute any acyclic graph safely, and optimizer passes can reorder nodes as long as dependencies are preserved.

### 3. Fold constants before runtime

**Constant folding** evaluates any subgraph made only of constants during compilation. If a request repeatedly computes `3*4 + 2`, the answer `14` should be baked into the graph once instead of recomputed for every inference.

```python
const_graph_w = [
    node_w("x", "input"), node_w("c3", "const", value=3.0), node_w("c4", "const", value=4.0),
    node_w("c2", "const", value=2.0), node_w("scale", "mul", ["c3", "c4"]),
    node_w("bias", "add", ["scale", "c2"]), node_w("out", "mul", ["x", "bias"]),
]
print("before folding:", [(n["name"], n["op"], n["inputs"]) for n in const_graph_w])
```
▶ What you'll see: `scale` and `bias` are arithmetic nodes even though their inputs are all constants.

```python
def constant_fold_w(graph):
    values, new_graph = {}, []
    by_name = {n["name"]: n for n in graph}
    for name in topo_sort_w(graph):
        n = by_name[name]
        if n["op"] == "const":
            values[name] = n["value"]
            new_graph.append(n)
        elif n["op"] in ("add", "mul") and all(inp in values for inp in n["inputs"]):
            a, b = (values[i] for i in n["inputs"])
            values[name] = a + b if n["op"] == "add" else a * b
            new_graph.append(node_w(name, "const", value=values[name]))
        else:
            new_graph.append(n)
    return new_graph

folded_w = constant_fold_w(const_graph_w)
print("after folding:", [(n["name"], n["op"], n["value"]) for n in folded_w if n["op"] == "const"])
assert [n for n in folded_w if n["name"] == "bias"][0]["value"] == 14.0
```
▶ What you'll see: the `bias` node becomes a constant with value `14.0`.

```python
runtime_arith_before_w = sum(n["op"] in {"add", "mul"} for n in const_graph_w)
runtime_arith_after_w = sum(n["op"] in {"add", "mul"} for n in folded_w)
plt.figure(figsize=(5, 3))
plt.bar(["before folding", "after folding"], [runtime_arith_before_w, runtime_arith_after_w],
        color=["gray", "seagreen"])
plt.ylabel("runtime arithmetic nodes"); plt.title("3: constant folding removes runtime ops")
plt.show()
```
▶ What you'll see: compile-time folding removes the constant-only arithmetic from the runtime graph.

*Why it's done this way:* constants are request-independent. Moving that arithmetic to compile time shortens the runtime schedule and removes work from every future inference without changing outputs.

### 4. Eliminate common subexpressions

**Common-subexpression elimination (CSE)** notices that two nodes compute the same operator on the same inputs. In our raw graph, `add1` and `add2` are both `x + c3`, and `mul1` and `mul2` are both `(x + c3) * c4`. The compiler can reuse one branch.

```python
def cse_w(graph):
    alias, seen, new_graph = {}, {}, []
    for n in graph:
        mapped_inputs = tuple(alias.get(i, i) for i in n["inputs"])
        if n["op"] in ("input", "const"):
            key = (n["op"], n["value"] if n["op"] == "const" else n["name"])
        else:
            key = (n["op"], mapped_inputs)
        if key in seen:
            alias[n["name"]] = seen[key]
        else:
            alias[n["name"]] = n["name"]
            seen[key] = n["name"]
            new_graph.append(node_w(n["name"], n["op"], mapped_inputs, n["value"]))
    for n in new_graph:
        n["inputs"] = [alias.get(i, i) for i in n["inputs"]]
    return new_graph, alias

cse_graph_w, alias_w = cse_w(graph_w)
print("aliases:", alias_w)
print("node count before/after:", len(graph_w), len(cse_graph_w))
assert alias_w["add2"] == "add1" and alias_w["mul2"] == "mul1"
assert len(cse_graph_w) == 6
```
▶ What you'll see: `add2 → add1` and `mul2 → mul1`, reducing the graph from 8 nodes to 6.

```python
vals_cse_w = run_graph_w(cse_graph_w, {"x": x_w})
print("CSE output:", vals_cse_w["out"])
assert np.allclose(vals_cse_w["out"], vals_w["out"])
draw_graph_w(cse_graph_w, "4: graph after common-subexpression elimination")
```
▶ What you'll see: one branch feeds both sides of `out`; the output is unchanged while duplicate work is gone.

*Why it's done this way:* CSE is safe only when the operator is deterministic and inputs are identical. That logical condition matters: reusing `x+c3` is valid, but reusing random-number generation or stateful I/O would be wrong.

### 5. Remove dead code that cannot affect outputs

**Dead-code elimination (DCE)** starts from requested outputs and walks backward through dependencies. Any node not reached cannot affect the answer and should not run. This is common after other rewrites leave unused nodes behind.

```python
dead_graph_w = cse_graph_w + [
    node_w("unused_const", "const", value=99.0),
    node_w("unused_mul", "mul", ["unused_const", "c4"]),
]
print("before DCE names:", [n["name"] for n in dead_graph_w])
```
▶ What you'll see: `unused_const` and `unused_mul` sit in the graph even though `out` never reads them.

```python
def dce_w(graph, outputs):
    by_name = {n["name"]: n for n in graph}
    live = set(outputs)
    stack = list(outputs)
    while stack:
        cur = stack.pop()
        for inp in by_name[cur]["inputs"]:
            if inp not in live:
                live.add(inp)
                stack.append(inp)
    return [n for n in graph if n["name"] in live]

live_graph_w = dce_w(dead_graph_w, ["out"])
print("after DCE names:", [n["name"] for n in live_graph_w])
assert "unused_mul" not in [n["name"] for n in live_graph_w]
assert np.allclose(run_graph_w(live_graph_w, {"x": x_w})["out"], vals_w["out"])
```
▶ What you'll see: unused nodes disappear, and the output still matches the original graph.

```python
plt.figure(figsize=(5, 3))
plt.bar(["before DCE", "after DCE"], [len(dead_graph_w), len(live_graph_w)], color=["crimson", "seagreen"])
plt.ylabel("nodes kept"); plt.title("5: dead-code elimination shrinks the graph")
plt.show()
```
▶ What you'll see: the graph keeps only nodes reachable from `out`, dropping the unused branch.

*Why it's done this way:* DCE is a reachability proof. If there is no path from a node to the requested output, executing it wastes latency and possibly memory, so the compiler removes it.

### 6. Fuse elementwise operators into one kernel

**Operator fusion** combines adjacent elementwise operations into a single runtime kernel. The math is the same, but the memory behavior changes: instead of materializing `tmp = x + 3` and then reading `tmp` for multiplication, a fused kernel streams `x` once and writes the final result.

```python
fusion_graph_w = [
    node_w("x", "input"), node_w("c3", "const", value=3.0), node_w("c4", "const", value=4.0),
    node_w("add1", "add", ["x", "c3"]), node_w("mul1", "mul", ["add1", "c4"]),
]
print("unfused ops:", [n["op"] for n in fusion_graph_w])
```
▶ What you'll see: the graph has separate `add` and `mul` nodes.

```python
def fuse_add_mul_w(graph):
    by_name = {n["name"]: n for n in graph}
    consumed_adds = set()
    for n in graph:
        if n["op"] == "mul" and by_name[n["inputs"][0]]["op"] == "add":
            consumed_adds.add(n["inputs"][0])
    fused = []
    for n in graph:
        if n["name"] in consumed_adds:
            continue
        if n["op"] == "mul":
            left = by_name[n["inputs"][0]]
            if left["name"] in consumed_adds:
                fused.append(node_w(n["name"] + "_fused", "fused", left["inputs"] + [n["inputs"][1]]))
                continue
        fused.append(n)
    return fused

fused_graph_w = fuse_add_mul_w(fusion_graph_w)
print("fused ops:", [n["op"] for n in fused_graph_w])
unfused_out_w = run_graph_w(fusion_graph_w, {"x": x_w})["mul1"]
fused_out_w = run_graph_w(fused_graph_w, {"x": x_w})["mul1_fused"]
assert np.allclose(unfused_out_w, fused_out_w)
assert sum(n["op"] in ("add", "mul", "fused") for n in fused_graph_w) == 1
```
▶ What you'll see: two elementwise ops become one fused op, with the same numeric result.

```python
bytes_per_array_w = 4.0  # MB for one toy tensor.
traffic_unfused_w = 4 * bytes_per_array_w  # read x, write tmp, read tmp, write y.
traffic_fused_w = 2 * bytes_per_array_w  # read x, write y.
plt.figure(figsize=(5, 3))
plt.bar(["unfused", "fused"], [traffic_unfused_w, traffic_fused_w], color=["crimson", "seagreen"])
plt.ylabel("memory traffic (MB)"); plt.title("6: fusion saves intermediate traffic"); plt.show()
print("traffic saved MB:", traffic_unfused_w - traffic_fused_w)
assert traffic_unfused_w - traffic_fused_w == 8.0
```
▶ What you'll see: the fused plan uses half the memory traffic in this tiny model, saving 8 MB.

*Why it's done this way:* small elementwise kernels are often memory-bound. Fusion does not reduce the arithmetic much; it reduces trips to memory and launch overhead, which is exactly where many eager tensor programs lose time.

### 7. Use a roofline model to decide compute-bound versus memory-bound

A runtime targets hardware kernels, so it needs a crude performance model. The **roofline model** says throughput is limited by the smaller of peak compute and `memory_bandwidth × arithmetic_intensity`. Low intensity means memory-bound; high intensity means compute-bound.

```python
peak_w = 100.0  # GFLOP/s toy peak compute.
bandwidth_w = 25.0  # GB/s toy memory bandwidth.
intensity_w = np.logspace(-2, 2, 80)  # FLOPs per byte.
roof_w = np.minimum(peak_w, bandwidth_w * intensity_w)
print("ridge intensity FLOP/byte:", peak_w / bandwidth_w)
assert peak_w / bandwidth_w == 4.0
```
▶ What you'll see: the ridge point is 4 FLOP/byte; below it memory dominates, above it compute dominates.

```python
eltwise_intensity_w = 1 / 8  # roughly one FLOP for reading/writing two float32 values.
matmul_intensity_w = 16.0  # a toy high-reuse matrix multiply.
eltwise_perf_w = min(peak_w, bandwidth_w * eltwise_intensity_w)
matmul_perf_w = min(peak_w, bandwidth_w * matmul_intensity_w)
print("elementwise predicted GFLOP/s:", round(eltwise_perf_w, 2))
print("matmul predicted GFLOP/s:", round(matmul_perf_w, 2))
```
▶ What you'll see: elementwise work is far below peak because memory limits it; matmul reaches peak compute.

```python
plt.figure(figsize=(5, 3.4))
plt.loglog(intensity_w, roof_w, color="navy")
plt.scatter([eltwise_intensity_w, matmul_intensity_w], [eltwise_perf_w, matmul_perf_w], color=["crimson", "seagreen"])
plt.text(eltwise_intensity_w, eltwise_perf_w * 1.4, "elementwise")
plt.text(matmul_intensity_w, matmul_perf_w * 0.7, "matmul")
plt.xlabel("arithmetic intensity (FLOP/byte)"); plt.ylabel("attainable GFLOP/s")
plt.title("7: roofline view of runtime bottlenecks"); plt.show()
```
▶ What you'll see: the elementwise point lies on the bandwidth slope, while matmul sits on the compute ceiling.

*Why it's done this way:* a compiler should not optimize only FLOP count. Fusion helps low-intensity code by reducing bytes moved; kernel selection and tiling help high-intensity code by approaching peak compute.
