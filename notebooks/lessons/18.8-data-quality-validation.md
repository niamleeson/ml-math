# 18.8 — Data Quality & Validation

Data quality validation turns the assumptions discovered during EDA into executable checks that can stop a bad dataset before it reaches a model. In this lesson, we build a tiny validation system from scratch with NumPy and pure Python: schema checks, constraint checks, missingness budgets, duplicate detection, train-serving skew checks, and distribution drift tests.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build data validation one idea at a time. Run each cell in order and read the printed intermediate values — every rule is visible, numeric, and inspectable. The walkthrough uses a `_w` suffix so it never clashes with the examples below.

```python
import numpy as np  # arrays, masks, summaries, and simulation.
import matplotlib.pyplot as plt  # all walkthrough visualizations.
np.random.seed(0)  # reproducibility for toy data.
```

### 1. A data contract is a schema plus expectations

Validation starts by naming what the table is supposed to contain. A schema says which columns exist and what kind of value each column should hold; expectations add semantic promises such as "age is nonnegative" or "score is in [0,1]." The point is not bureaucracy: the schema turns assumptions into code that can fail before a learner silently treats broken inputs as data.

```python
rows_w = [
    {"user_id": 101, "age": 24.0, "score": 0.82, "country": "US"},
    {"user_id": 102, "age": 39.0, "score": 0.34, "country": "CA"},
    {"user_id": 103, "age": 51.0, "score": 0.91, "country": "US"},
]
schema_w = {"user_id": int, "age": float, "score": float, "country": str}
print("columns in first row:", list(rows_w[0].keys()))
print("expected columns:", list(schema_w.keys()))
```
▶ What you'll see: the observed and expected column names match exactly.

```python
def check_schema_w(rows, schema):
    problems = []
    expected = set(schema)
    for i, row in enumerate(rows):
        missing = expected - set(row)
        extra = set(row) - expected
        if missing:
            problems.append((i, "missing", sorted(missing)))
        if extra:
            problems.append((i, "extra", sorted(extra)))
        for col, typ in schema.items():
            if col in row and not isinstance(row[col], typ):
                problems.append((i, "type", col, type(row[col]).__name__))
    return problems

schema_problems_w = check_schema_w(rows_w, schema_w)
print("schema problems:", schema_problems_w)
assert schema_problems_w == []
```
▶ What you'll see: no schema problems, so the table shape and primitive types satisfy the contract.

```python
bad_rows_w = rows_w + [{"user_id": "104", "age": 28.0, "score": 0.77}]
bad_schema_problems_w = check_schema_w(bad_rows_w, schema_w)
print("bad-row problems:", bad_schema_problems_w)
assert len(bad_schema_problems_w) == 2
```
▶ What you'll see: the added row is missing `country` and has `user_id` as a string rather than an integer.

*Why it's done this way:* schema validation is the cheapest possible boundary check. If the feature matrix is supposed to be $X\in\mathbb{R}^{m\times d}$, then missing columns, extra columns, and type changes mean the downstream model is no longer seeing the same mathematical object it was trained on. Catching that before numerical code runs prevents silent column shifts and unit mistakes from masquerading as legitimate observations.

### 2. Range, category, and row-level constraints are boolean predicates

Once columns exist, each value still needs to satisfy domain rules. A score may be a float but still be impossible if it is 1.7 when the model expects probabilities in $[0,1]$. A category may be a string but still be invalid if it is outside the known vocabulary. Mathematically, a constraint is just a predicate that maps each row or value to pass/fail.

```python
scores_w = np.array([0.5, 0.6, 1.7, 0.8])
in_range_w = (0 <= scores_w) & (scores_w <= 1)
violations_w = ~in_range_w
print("scores:", scores_w)
print("range violations:", violations_w.astype(int), "count:", int(violations_w.sum()))
assert int(violations_w.sum()) == 1
```
▶ What you'll see: only the impossible score 1.7 violates the expected probability range.

```python
countries_w = np.array(["US", "CA", "FR", "US"])
allowed_w = np.array(["US", "CA", "MX"])
known_country_w = np.array([c in set(allowed_w) for c in countries_w])
print("known-country mask:", known_country_w.astype(int))
print("invalid countries:", countries_w[~known_country_w])
assert countries_w[~known_country_w].tolist() == ["FR"]
```
▶ What you'll see: `FR` is a valid string but fails the allowed-vocabulary expectation.

```python
ages_w = np.array([24.0, 39.0, 51.0, 16.0])
adult_high_score_w = ~((ages_w < 18) & (scores_w > 0.7))
print("row-level pass mask:", adult_high_score_w.astype(int))
assert adult_high_score_w.tolist() == [True, True, True, False]
```
▶ What you'll see: the last row fails a cross-field rule because a minor has a high adult-only score.

```python
plt.figure(figsize=(4.4, 3))
plt.scatter(ages_w, scores_w, c=np.where(adult_high_score_w, "seagreen", "crimson"), s=80)
plt.axhline(0.7, color="gray", linestyle="--")
plt.axvline(18, color="gray", linestyle="--")
plt.title("1: row-level constraint failures")
plt.xlabel("age")
plt.ylabel("score")
plt.show()
```
▶ What you'll see: the red point sits in the forbidden region: age below 18 and score above 0.7.

*Why it's done this way:* constraints are boolean masks because masks are composable. A range check is $0\le x\le1$, a vocabulary check is $x\in\mathcal{C}$, and a row-level rule is a logical expression over features. Counting failures with $\sum_i \mathbf{1}[\text{fail}_i]$ gives an auditable number and the exact offending rows.

### 3. Missingness budgets separate normal absence from broken pipelines

Real datasets often allow some missing values, but the allowed amount should be explicit. A missingness rate is the fraction $\frac{1}{m}\sum_i \mathbf{1}[x_i\text{ missing}]$ for one feature. A budget says how much absence is tolerable before a pipeline should fail or alert.

```python
X_w = np.array([
    [1.0, np.nan, 0.2],
    [2.0, np.nan, np.nan],
    [3.0, 0.7, np.nan],
    [np.nan, 0.9, 0.4],
])
missing_mask_w = np.isnan(X_w)
missing_rates_w = missing_mask_w.mean(axis=0)
print("missing mask:\n", missing_mask_w.astype(int))
print("missing rates:", missing_rates_w)
assert np.allclose(missing_rates_w, [0.25, 0.50, 0.50])
```
▶ What you'll see: the three feature missingness rates are 0.25, 0.50, and 0.50.

```python
budget_w = 0.40
fails_budget_w = missing_rates_w > budget_w
print("budget:", budget_w)
print("features failing budget:", np.where(fails_budget_w)[0])
assert np.where(fails_budget_w)[0].tolist() == [1, 2]
```
▶ What you'll see: features 1 and 2 fail because 0.50 is greater than the 0.40 budget.

```python
plt.figure(figsize=(4.4, 3))
plt.bar(["f0", "f1", "f2"], missing_rates_w, color=np.where(fails_budget_w, "crimson", "seagreen"))
plt.axhline(budget_w, color="black", linestyle="--", label="budget")
plt.ylim(0, 0.65)
plt.title("2: missingness budget check")
plt.ylabel("missing rate")
plt.legend()
plt.show()
```
▶ What you'll see: bars above the dashed line are failures that should stop or quarantine the snapshot.

*Why it's done this way:* missingness is measured as a rate, not a count, because row counts change across batches. A budget encodes an operational assumption: if a feature was trained with roughly 5% absence, a 50% absence serving batch is probably a pipeline issue rather than ordinary data variation. The strict inequality $rate>budget$ makes pass/fail deterministic and reproducible.

### 4. Duplicate and join checks protect the meaning of one row

Many data failures are not strange values; they are strange row counts. A bad join can duplicate users, creating repeated labels and biased training examples. A uniqueness constraint says a key should appear once, and a join cardinality check compares actual row counts to the expected one-to-one or many-to-one relationship.

```python
user_ids_w = np.array([101, 102, 103, 103, 104])
unique_ids_w, counts_w = np.unique(user_ids_w, return_counts=True)
duplicate_ids_w = unique_ids_w[counts_w > 1]
print("ids:", user_ids_w)
print("duplicate ids:", duplicate_ids_w)
assert duplicate_ids_w.tolist() == [103]
```
▶ What you'll see: user 103 appears twice, violating uniqueness.

```python
left_ids_w = np.array([101, 102, 103, 104])
right_ids_w = np.array([101, 102, 102, 103, 104])
joined_rows_w = sum(int(np.sum(right_ids_w == key)) for key in left_ids_w)
print("left rows:", len(left_ids_w), "joined rows:", joined_rows_w)
print("join expansion factor:", round(joined_rows_w / len(left_ids_w), 2))
assert joined_rows_w == 5
```
▶ What you'll see: a supposed one-to-one enrichment expands 4 rows into 5 because key 102 has two matches.

```python
right_unique_w, right_counts_w = np.unique(right_ids_w, return_counts=True)
right_bad_keys_w = right_unique_w[right_counts_w > 1]
plt.figure(figsize=(4.4, 3))
plt.bar(right_unique_w.astype(str), right_counts_w, color=np.where(right_counts_w > 1, "crimson", "seagreen"))
plt.axhline(1, color="black", linestyle="--")
plt.title("3: right-table key multiplicity")
plt.xlabel("join key")
plt.ylabel("matches in right table")
plt.show()
print("bad join keys:", right_bad_keys_w)
```
▶ What you'll see: key 102 has two right-table matches, explaining the row expansion.

*Why it's done this way:* supervised learning usually assumes each row contributes one unit of evidence. Duplicate keys secretly reweight examples, and join expansion changes the empirical distribution without changing feature names. Counting key multiplicities is a direct check on the relational assumption behind the feature table.

### 5. Distribution drift tests compare train and serving populations

A batch can pass schema and constraints while still coming from a different population. Distribution drift tests compare the training proportions $p_b$ in bins with serving proportions $q_b$. Population Stability Index uses $PSI=\sum_b(q_b-p_b)\log(q_b/p_b)$, which is zero when proportions match and grows as the populations separate.

```python
train_counts_w = np.array([50, 30, 20], dtype=float)
serving_counts_w = np.array([30, 40, 30], dtype=float)
p_w = train_counts_w / train_counts_w.sum()
q_w = serving_counts_w / serving_counts_w.sum()
print("train proportions:", p_w)
print("serving proportions:", q_w)
assert np.allclose(p_w, [0.5, 0.3, 0.2])
assert np.allclose(q_w, [0.3, 0.4, 0.3])
```
▶ What you'll see: serving has fewer low-bin examples and more mid/high-bin examples than training.

```python
eps_w = 1e-12
psi_terms_w = (q_w - p_w) * np.log((q_w + eps_w) / (p_w + eps_w))
psi_w = float(np.sum(psi_terms_w))
print("PSI terms:", np.round(psi_terms_w, 3))
print("PSI total:", round(psi_w, 3))
assert np.allclose(np.round(psi_terms_w, 3), [0.102, 0.029, 0.041])
assert round(psi_w, 3) == 0.171
```
▶ What you'll see: each bin contributes a nonnegative amount, for total PSI 0.171.

```python
x_w = np.arange(3)
plt.figure(figsize=(5, 3))
plt.bar(x_w - 0.18, p_w, width=0.36, label="train", color="steelblue")
plt.bar(x_w + 0.18, q_w, width=0.36, label="serving", color="orange")
plt.xticks(x_w, ["low", "mid", "high"])
plt.title(f"4: distribution drift, PSI={psi_w:.3f}")
plt.ylabel("bin proportion")
plt.legend()
plt.show()
```
▶ What you'll see: the serving bars shift mass from low to mid/high, matching the positive PSI.

*Why it's done this way:* PSI is a population check, not a model metric. The logarithm compares relative change $q_b/p_b$, while multiplication by $q_b-p_b$ weights the change by how much mass moved. Small epsilons avoid division by zero without changing nonzero-bin examples. The result is an early warning that the model may now be extrapolating from a different input distribution.

### 6. Train-serving skew is a row-level difference test

Sometimes the same feature name is computed differently offline and online. A train-serving skew check aligns rows by key and compares feature values. It is a mechanism test: distribution drift says the population moved; row-level diffs say the pipeline is computing a value differently for the same entity.

```python
offline_w = {101: 0.82, 102: 0.34, 103: 0.91, 104: 0.44}
online_w = {101: 0.82, 102: 0.35, 103: 0.10, 104: 0.44}
keys_w = sorted(set(offline_w) & set(online_w))
diffs_w = np.array([abs(offline_w[k] - online_w[k]) for k in keys_w])
print("keys:", keys_w)
print("absolute diffs:", np.round(diffs_w, 3))
assert np.allclose(diffs_w, [0.0, 0.01, 0.81, 0.0])
```
▶ What you'll see: key 103 has a much larger offline/online discrepancy than the others.

```python
tolerance_w = 0.05
skew_fail_w = diffs_w > tolerance_w
print("skew failures:", np.array(keys_w)[skew_fail_w])
assert np.array(keys_w)[skew_fail_w].tolist() == [103]
```
▶ What you'll see: only user 103 fails the row-level tolerance.

```python
plt.figure(figsize=(4.6, 3))
plt.bar([str(k) for k in keys_w], diffs_w, color=np.where(skew_fail_w, "crimson", "seagreen"))
plt.axhline(tolerance_w, color="black", linestyle="--", label="tolerance")
plt.title("5: train-serving skew diff")
plt.xlabel("user_id")
plt.ylabel("|offline - online|")
plt.legend()
plt.show()
```
▶ What you'll see: one red bar crosses the tolerance line, identifying the broken entity and feature.

*Why it's done this way:* row-level diffs hold the entity fixed, so differences cannot be explained by a changing population. The tolerance turns floating-point noise into pass/fail logic: small differences are acceptable numerical variation, while large differences indicate inconsistent feature computation.

## 🟢 Basics (warm-up)

### Basic 1 — Check required columns

**Goal.** Verify that every expected feature is present, because a model trained on one set of columns should not receive a different table.

```python
row_b1 = {"age": 24.0, "score": 0.82, "country": "US"}
required_b1 = ["age", "score", "country"]
missing_b1 = [col for col in required_b1 if col not in row_b1]
print("missing columns:", missing_b1)
assert missing_b1 == []
```
▶ What you'll see: the row contains every required column.

👀 Takeaway: column presence is the first executable version of a data contract.

### Basic 2 — Detect a missing column

**Goal.** Fail loudly when a required feature disappears, because downstream arrays can otherwise shift silently.

```python
row_b2 = {"age": 31.0, "country": "CA"}
required_b2 = ["age", "score", "country"]
missing_b2 = [col for col in required_b2 if col not in row_b2]
print("missing columns:", missing_b2)
assert missing_b2 == ["score"]
```
▶ What you'll see: `score` is reported as missing.

👀 Takeaway: a missing feature should be a validation failure, not a model input.

### Basic 3 — Check one numeric range

**Goal.** Catch impossible values in a probability-like score, because type correctness does not guarantee semantic correctness.

```python
score_b3 = 1.7
in_range_b3 = 0.0 <= score_b3 <= 1.0
print("score:", score_b3, "in [0,1]?", in_range_b3)
assert in_range_b3 is False
```
▶ What you'll see: 1.7 fails the probability range check.

👀 Takeaway: range predicates turn feature meaning into runnable code.

### Basic 4 — Count range violations

**Goal.** Count invalid values in a batch, because validation reports should quantify failure size.

```python
scores_b4 = np.array([0.2, 0.5, -0.1, 1.1, 0.7])
violations_b4 = (scores_b4 < 0) | (scores_b4 > 1)
print("violation mask:", violations_b4.astype(int))
print("violation count:", int(violations_b4.sum()))
assert int(violations_b4.sum()) == 2
```
▶ What you'll see: two scores sit outside [0,1].

👀 Takeaway: masks make constraint failures easy to locate and count.

### Basic 5 — Validate categorical values

**Goal.** Check that strings belong to an allowed vocabulary, because unknown categories often mean upstream mapping changed.

```python
countries_b5 = np.array(["US", "CA", "FR", "MX"])
allowed_b5 = {"US", "CA", "MX"}
valid_b5 = np.array([c in allowed_b5 for c in countries_b5])
print("valid mask:", valid_b5.astype(int))
print("bad categories:", countries_b5[~valid_b5])
assert countries_b5[~valid_b5].tolist() == ["FR"]
```
▶ What you'll see: `FR` is the only category outside the contract.

👀 Takeaway: category validation protects one-hot or embedding tables from unseen tokens.

### Basic 6 — Compute feature missingness

**Goal.** Measure the missingness rate of one feature, because a few missing values may be normal while a spike may indicate breakage.

```python
feature_b6 = np.array([1.2, np.nan, 0.7, np.nan, 0.4])
missing_rate_b6 = float(np.isnan(feature_b6).mean())
print("missing rate:", round(missing_rate_b6, 2))
assert round(missing_rate_b6, 2) == 0.40
```
▶ What you'll see: two of five values are missing, so the rate is 0.40.

👀 Takeaway: missingness is best monitored as a rate so batches of different sizes compare fairly.

### Basic 7 — Apply a missingness budget

**Goal.** Compare a missingness rate against a maximum allowed budget, because validation needs deterministic pass/fail rules.

```python
rates_b7 = np.array([0.05, 0.12, 0.45])
budget_b7 = 0.20
fails_b7 = rates_b7 > budget_b7
print("failing features:", np.where(fails_b7)[0])
assert np.where(fails_b7)[0].tolist() == [2]
```
▶ What you'll see: only feature 2 exceeds the 20% missingness budget.

👀 Takeaway: a threshold converts a quality statistic into an operational decision.

### Basic 8 — Find duplicate keys

**Goal.** Detect repeated primary keys, because duplicate rows can accidentally reweight training examples.

```python
ids_b8 = np.array([7, 8, 9, 9, 10, 10, 10])
unique_b8, counts_b8 = np.unique(ids_b8, return_counts=True)
dups_b8 = unique_b8[counts_b8 > 1]
print("duplicate ids:", dups_b8)
assert dups_b8.tolist() == [9, 10]
```
▶ What you'll see: ids 9 and 10 appear more than once.

👀 Takeaway: uniqueness checks protect the assumption that each entity contributes once.

### Basic 9 — Compare two distributions by bin proportions

**Goal.** Convert raw counts into comparable proportions, because drift tests should not depend on batch size.

```python
train_counts_b9 = np.array([80, 15, 5], dtype=float)
serve_counts_b9 = np.array([60, 30, 10], dtype=float)
p_b9 = train_counts_b9 / train_counts_b9.sum()
q_b9 = serve_counts_b9 / serve_counts_b9.sum()
print("train proportions:", p_b9)
print("serve proportions:", q_b9)
assert np.allclose(p_b9, [0.80, 0.15, 0.05])
```
▶ What you'll see: serving has shifted mass toward the middle and high bins.

👀 Takeaway: proportions put train and serving snapshots on the same probability scale.

### Basic 10 — Compute one row-level skew diff

**Goal.** Compare offline and online feature values for the same key, because train-serving skew is easiest to diagnose row by row.

```python
offline_b10 = 0.91
online_b10 = 0.10
diff_b10 = abs(offline_b10 - online_b10)
tolerance_b10 = 0.05
print("absolute diff:", diff_b10, "fails?", diff_b10 > tolerance_b10)
assert round(diff_b10, 2) == 0.81
```
▶ What you'll see: the row-level difference is much larger than the tolerance.

👀 Takeaway: row-aligned comparisons catch feature computation mismatches directly.

## 🟡 Easy

### Easy 1 — Build a tiny schema validator

**Goal.** Validate columns and primitive types for a small batch, because schema failures are usually the fastest data bugs to catch.

```python
rows_e1 = [
    {"age": 24.0, "score": 0.82, "country": "US"},
    {"age": "old", "score": 0.34, "country": "CA"},
]
schema_e1 = {"age": float, "score": float, "country": str}
problems_e1 = []
for i_e1, row_e1 in enumerate(rows_e1):
    for col_e1, typ_e1 in schema_e1.items():
        if col_e1 not in row_e1:
            problems_e1.append((i_e1, col_e1, "missing"))
        elif not isinstance(row_e1[col_e1], typ_e1):
            problems_e1.append((i_e1, col_e1, "type"))
print("schema problems:", problems_e1)
assert problems_e1 == [(1, "age", "type")]
```
▶ What you'll see: row 1 fails because `age` is a string.

👀 Takeaway: a schema validator is just repeated column-presence and type predicates.

### Easy 2 — Validate multiple constraints at once

**Goal.** Combine range and vocabulary checks into one report, because real validation suites run many expectations per batch.

```python
scores_e2 = np.array([0.3, 1.2, 0.8, -0.1])
countries_e2 = np.array(["US", "CA", "ZZ", "US"])
allowed_e2 = {"US", "CA", "MX"}
range_fail_e2 = (scores_e2 < 0) | (scores_e2 > 1)
cat_fail_e2 = np.array([c not in allowed_e2 for c in countries_e2])
report_e2 = {"score_range_failures": int(range_fail_e2.sum()), "country_failures": int(cat_fail_e2.sum())}
print("report:", report_e2)
assert report_e2 == {"score_range_failures": 2, "country_failures": 1}
```
▶ What you'll see: the score range has two failures and the country vocabulary has one.

👀 Takeaway: validation reports should separate failure types so owners know what broke.

### Easy 4 — Compute PSI from scratch

**Goal.** Implement Population Stability Index directly, because it is just a bin-wise comparison of train and serving proportions.

```python
p_e4 = np.array([0.5, 0.3, 0.2])
q_e4 = np.array([0.3, 0.4, 0.3])
psi_terms_e4 = (q_e4 - p_e4) * np.log(q_e4 / p_e4)
psi_e4 = float(np.sum(psi_terms_e4))
print("PSI terms:", np.round(psi_terms_e4, 3))
print("PSI:", round(psi_e4, 3))
assert round(psi_e4, 3) == 0.171
```
▶ What you'll see: the three bin terms sum to PSI 0.171.

👀 Takeaway: PSI is an early-warning input-drift statistic, not an accuracy score.

### Easy 5 — Produce a pass/fail validation summary

**Goal.** Aggregate checks into one validation decision, because pipelines need one clear status plus detailed reasons.

```python
checks_e5 = {
    "schema": True,
    "score_range": False,
    "missingness": True,
    "psi": False,
}
failed_e5 = [name_e5 for name_e5, passed_e5 in checks_e5.items() if not passed_e5]
status_e5 = "PASS" if len(failed_e5) == 0 else "FAIL"
print("status:", status_e5)
print("failed checks:", failed_e5)
assert status_e5 == "FAIL" and failed_e5 == ["score_range", "psi"]
```
▶ What you'll see: the batch fails with two named reasons.

👀 Takeaway: validation is useful operationally only when failures are explicit and attributable.

## 🔴 Advanced

### Advanced 1 — Build an expectation runner

**Goal.** Represent expectations as small functions and run them over one batch, because executable checks should be easy to version and extend.

```python
data_a1 = {
    "score": np.array([0.2, 0.9, 1.4, 0.7]),
    "age": np.array([25, 17, 31, 45]),
}

def expect_between_a1(values_a1, low_a1, high_a1):
    return (values_a1 >= low_a1) & (values_a1 <= high_a1)

def expect_at_least_a1(values_a1, low_a1):
    return values_a1 >= low_a1

results_a1 = {
    "score_between_0_1": expect_between_a1(data_a1["score"], 0, 1),
```

### Advanced 5 — Simulate a validation gate over snapshots

**Goal.** Gate dataset snapshots with multiple checks, because validation should fail before models do and record which version passed.

```python
snapshots_a5 = [
    {"version": "v1", "missing": 0.08, "psi": 0.04, "range_failures": 0},
    {"version": "v2", "missing": 0.35, "psi": 0.06, "range_failures": 0},
    {"version": "v3", "missing": 0.10, "psi": 0.18, "range_failures": 1},
]
missing_budget_a5 = 0.20
psi_budget_a5 = 0.10
reports_a5 = []

    failed_a5 = []
    if snap_a5["missing"] > missing_budget_a5:
        failed_a5.append("missingness")
    if snap_a5["psi"] > psi_budget_a5:
        failed_a5.append("drift")
    if snap_a5["range_failures"] > 0:
        failed_a5.append("range")
    reports_a5.append((snap_a5["version"], "PASS" if not failed_a5 else "FAIL", failed_a5))
print("reports:", reports_a5)
assert reports_a5[0][1] == "PASS" and reports_a5[1][2] == ["missingness"] and reports_a5[2][2] == ["drift", "range"]
```
▶ What you'll see: v1 passes, v2 fails missingness, and v3 fails drift plus range checks.

