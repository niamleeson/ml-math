# 20.6 — Batch vs Online Inference

Batch inference computes predictions before a request arrives; online inference computes while the user waits. The production question is not which one is universally better, but which one gives enough freshness under the latency, throughput, and cost budgets; in practice, hybrid designs often win by caching stable work and reserving online compute for volatile signals.

## 📖 Concept walkthrough — build each idea from scratch

Before the terse worked examples, we build batch-vs-online inference one idea at a time. Run each cell in order and inspect the small arrays, queues, and plots — the arithmetic is deliberately visible because production ML decisions are usually made from budgets, ratios, and tail behavior before they are made from bigger models. This walkthrough is self-contained (it imports what it needs) and uses a `_w` suffix on its variables so it never clashes with the examples below.

```python
import numpy as np  # arrays, random arrivals, percentiles, and vectorized arithmetic.
import matplotlib.pyplot as plt  # all walkthrough visualizations.
np.random.seed(0)  # reproducibility for simulated request streams.
```
▶ What you'll see: the two allowed libraries are loaded and the random stream is fixed.

### 1. Batch inference: compute first, serve later

Batch inference precomputes predictions on a schedule, stores them, and serves a cheap lookup when the user arrives. The price is **staleness**: if the batch refresh interval is $T$, the worst-case age is $T$ and, for uniformly arriving requests, the average age is $T/2$. That age matters only if the world changes enough between refreshes to damage the prediction.

```python
refresh_hours_w = 6.0  # one batch job refreshes predictions every 6 hours.
request_hours_w = np.array([0.2, 1.5, 2.9, 4.1, 5.8])  # request times since the latest refresh.
age_hours_w = request_hours_w % refresh_hours_w  # age of the cached prediction at each request.
print("cached prediction ages (hours):", age_hours_w)
print("average age:", round(float(age_hours_w.mean()), 2), "hours")
assert refresh_hours_w / 2 == 3.0  # uniformly random arrivals average half the refresh window.
```
▶ What you'll see: requests later in the refresh window receive older predictions; a 6-hour interval has a 3-hour average-age rule of thumb.

```python
plt.figure(figsize=(4.6, 3))
plt.scatter(request_hours_w, age_hours_w, color="teal")
plt.plot([0, refresh_hours_w], [0, refresh_hours_w], color="gray", linestyle="--")
plt.xlabel("hours since batch refresh")
plt.ylabel("prediction age (hours)")
plt.title("1: batch staleness grows until refresh")
plt.show()
```
▶ What you'll see: age rises linearly between refreshes and resets when the next batch job runs.

*Why it's done this way:* precomputing removes model work from the user path, so latency can be a tiny key-value lookup. The refresh window is the explicit trade: longer windows amortize more work and lower operational pressure, but they increase stale decisions. The $T/2$ average is useful because it lets us compare freshness against cost with one inspectable number instead of hand-waving.

### 2. Online inference: fresh predictions on the critical path

Online inference computes at request time. Freshness improves, but every dependency now sits on the latency path: feature lookup, model execution, network hops, serialization, and retries. The simplest latency model is a sum of components, and the user pays the sum.

```python
latency_parts_ms_w = {"feature_lookup": 25, "model": 40, "network": 15}  # component budget.
online_latency_ms_w = sum(latency_parts_ms_w.values())  # end-to-end online latency.
print("online latency parts:", latency_parts_ms_w)
print("total online latency:", online_latency_ms_w, "ms")
assert online_latency_ms_w == 80  # 25 + 40 + 15 from the lesson block.
```
▶ What you'll see: the online path totals 80 ms before any queueing or retry overhead.

```python
names_w = list(latency_parts_ms_w.keys())
vals_w = np.array(list(latency_parts_ms_w.values()))
plt.figure(figsize=(4.8, 3))
plt.bar(names_w, vals_w, color=["steelblue", "darkorange", "seagreen"])
plt.axhline(80, color="black", linestyle="--", label="total shown separately")
plt.ylabel("milliseconds")
plt.title("2: online latency is additive")
plt.xticks(rotation=15)
plt.show()
```
▶ What you'll see: the model is not the whole latency budget; feature lookup and network time are visible contributors.

*Why it's done this way:* online serving is attractive because it uses the newest features, but a real user request cannot finish until every required component finishes. Summing components forces us to name the budget and prevents the common mistake of optimizing model runtime while ignoring feature-store or network latency.

### 3. Hybrid inference: expected latency from cache hits

A hybrid system serves cached batch predictions when they are good enough and falls back to online inference for misses or volatile cases. If $h$ is the cache hit rate, $L_{cache}$ the lookup latency, and $L_{online}$ the online latency, then

$$E[L]=hL_{cache}+(1-h)L_{online}.$$

This is a weighted average: with probability $h$ the user sees the fast path; otherwise they pay the slow path.

```python
h_w = 0.70  # 70% of requests hit the batch cache.
L_cache_w = 5.0  # ms for a cached lookup.
L_online_w = 80.0  # ms for real-time inference.
expected_latency_w = h_w * L_cache_w + (1 - h_w) * L_online_w
print("expected hybrid latency:", round(expected_latency_w, 1), "ms")
assert round(expected_latency_w, 1) == 27.5  # 0.7*5 + 0.3*80.
```
▶ What you'll see: a 70% hit rate cuts expected latency from 80 ms to 27.5 ms.

```python
hit_grid_w = np.linspace(0, 1, 11)
lat_grid_w = hit_grid_w * L_cache_w + (1 - hit_grid_w) * L_online_w
plt.figure(figsize=(4.8, 3))
plt.plot(hit_grid_w, lat_grid_w, marker="o", color="purple")
plt.axhline(50, color="crimson", linestyle="--", label="50 ms budget")
plt.xlabel("cache hit rate h")
plt.ylabel("expected latency (ms)")
plt.title("3: hit rate moves hybrid latency")
plt.legend()
plt.show()
```
▶ What you'll see: expected latency falls linearly as more requests hit the cached batch path.

*Why it's done this way:* hybrid inference separates stable and volatile work. If most predictions are acceptable from cache, the system buys online freshness only where it matters. The weighted-average formula makes the design inspectable: improving hit rate, cache latency, or online latency all have measurable effects.

### 4. Throughput and amortized compute

Batching can improve throughput because some compute has a fixed overhead. If one model call costs `fixed + per_item × batch_size`, then the per-request cost is `fixed / batch_size + per_item`. Larger batches amortize the fixed overhead, but they may wait longer before running.

```python
fixed_ms_w = 10.0  # fixed model-launch overhead per batch.
per_item_ms_w = 2.0  # incremental compute per request in the batch.
batch_sizes_w = np.array([1, 2, 4, 8, 16, 32])
batch_compute_ms_w = fixed_ms_w + per_item_ms_w * batch_sizes_w
per_request_ms_w = batch_compute_ms_w / batch_sizes_w
print("per-request compute (ms):", np.round(per_request_ms_w, 2))
assert round(float(per_request_ms_w[0]), 1) == 12.0
assert round(float(per_request_ms_w[-1]), 3) == 2.312
```
▶ What you'll see: per-request compute falls quickly because the 10 ms fixed cost is shared across more requests.

```python
throughput_per_s_w = 1000 * batch_sizes_w / batch_compute_ms_w
plt.figure(figsize=(5, 3))
plt.plot(batch_sizes_w, throughput_per_s_w, marker="o", color="seagreen")
plt.xlabel("batch size")
plt.ylabel("max throughput (requests/s)")
plt.title("4: amortized compute raises throughput")
plt.show()
```
▶ What you'll see: throughput rises with batch size, then starts to flatten as per-item cost dominates.

*Why it's done this way:* accelerators and vectorized kernels often have launch overhead. Batching improves hardware utilization by paying that overhead once for many requests. The reason this is a tradeoff is that real users arrive over time; waiting to form a bigger batch may increase latency even as it improves throughput.

### 5. Little's law: qps × latency = in-flight load

Capacity planning needs concurrency, not only average qps. Little's law says that, for a stable system,

$$L=\lambda W,$$

where $L$ is the average number of in-flight requests, $\lambda$ is arrival rate, and $W$ is average time in the system. If 500 qps each spend 80 ms in service, roughly 40 requests are in flight at once.

```python
qps_w = 500.0  # peak arrivals per second.
latency_s_w = 0.080  # 80 ms online path expressed in seconds.
inflight_w = qps_w * latency_s_w
print("in-flight requests:", round(inflight_w, 1))
assert round(inflight_w, 1) == 40.0  # 500 * 0.080.
```
▶ What you'll see: even an 80 ms path needs capacity for about 40 simultaneous requests at 500 qps.

```python
latencies_ms_w = np.array([20, 40, 80, 160])
inflight_grid_w = qps_w * (latencies_ms_w / 1000)
plt.figure(figsize=(4.8, 3))
plt.bar([str(x) for x in latencies_ms_w], inflight_grid_w, color="darkorange")
plt.xlabel("average latency (ms)")
plt.ylabel("average in-flight requests")
plt.title("5: Little's law capacity intuition")
plt.show()
```
▶ What you'll see: doubling latency doubles the concurrency required for the same qps.

*Why it's done this way:* queues form when arrivals exceed the capacity implied by service time. Little's law gives a fast sanity check: latency budgets are also capacity budgets. Optimizing 80 ms to 40 ms does not only help users; it halves in-flight work at the same traffic level.

### 6. Dynamic micro-batching, tail latency, and SLO windows

Micro-batching waits briefly for nearby requests, runs them together, and returns all results. It is dynamic because batch size depends on arrivals and a maximum wait window. The SLO question is whether the extra waiting plus compute keeps the **tail latency** (for example p95) under budget. Averages can look fine while p95 violates the user promise.

```python
rng_w = np.random.default_rng(0)
arrivals_ms_w = np.cumsum(rng_w.exponential(scale=4.0, size=80))  # synthetic arrivals about every 4 ms.
window_ms_w = 6.0  # max time to wait before closing a micro-batch.
max_batch_w = 8  # cap batch size so no one batch grows without bound.
print("first arrivals (ms):", np.round(arrivals_ms_w[:8], 2))
print("arrival span:", round(float(arrivals_ms_w[-1] - arrivals_ms_w[0]), 1), "ms")
```
▶ What you'll see: requests arrive irregularly, so dynamic batches will have uneven sizes.

```python
finish_ms_w = np.zeros_like(arrivals_ms_w)
batch_ids_w = []
i_w = 0
while i_w < len(arrivals_ms_w):
    start_w = arrivals_ms_w[i_w]
    j_w = i_w
    while j_w < len(arrivals_ms_w) and arrivals_ms_w[j_w] <= start_w + window_ms_w and (j_w - i_w) < max_batch_w:
        j_w += 1
    size_w = j_w - i_w
    run_ms_w = 8.0 + 1.5 * size_w  # fixed overhead plus per-item compute.
    done_w = max(arrivals_ms_w[j_w - 1], start_w + window_ms_w) + run_ms_w
    finish_ms_w[i_w:j_w] = done_w
    batch_ids_w.append(size_w)
    i_w = j_w
latency_ms_w = finish_ms_w - arrivals_ms_w
print("batch sizes:", batch_ids_w[:10])
print("mean / p95 latency:", round(float(latency_ms_w.mean()), 2), round(float(np.percentile(latency_ms_w, 95)), 2))
assert len(batch_ids_w) > 0
```
▶ What you'll see: batches are not uniform; p95 latency is higher than the mean because early requests wait for the window.

```python
plt.figure(figsize=(5, 3))
plt.hist(latency_ms_w, bins=14, color="steelblue", edgecolor="white")
plt.axvline(np.percentile(latency_ms_w, 95), color="crimson", linestyle="--", label="p95")
plt.xlabel("latency (ms)")
plt.ylabel("request count")
plt.title("6: micro-batching creates a latency tail")
plt.legend()
plt.show()
```
▶ What you'll see: the right edge of the histogram, not the center, decides whether a p95 SLO is safe.

*Why it's done this way:* micro-batching buys throughput by waiting for neighbors, but that waiting is added to user latency. Tail latency matters because users and SLOs experience the slow requests, not only the average. The batch-window decision is therefore a Pareto problem: larger windows improve amortization but can push p95 past the latency budget.

### ✍️ Toy 1 · Batch staleness is age since the last refresh

A cached prediction gets older between batch jobs. The modulo operation turns request times into
prediction ages inside the refresh window.

```python
import numpy as np
import matplotlib.pyplot as plt

t1_rng = np.random.default_rng(0)
t1_refresh_hours = 4.0
print("refresh interval hours:", t1_refresh_hours)  # -> 4.0

t1_request_hours = np.array([0.5, 1.0, 3.5, 4.2, 7.9])
print("request hours:", t1_request_hours.tolist())  # -> [0.5, 1.0, 3.5, 4.2, 7.9]

t1_age_hours = t1_request_hours % t1_refresh_hours
print("prediction ages:", np.round(t1_age_hours, 2).tolist())  # -> [0.5, 1.0, 3.5, 0.2, 3.9]

t1_average_age = float(t1_age_hours.mean())
print("average age:", round(t1_average_age, 2))  # -> 1.82

t1_worst_age = float(t1_age_hours.max())
print("worst age:", round(t1_worst_age, 2))  # -> 3.9
assert round(t1_average_age, 2) == 1.82

plt.figure(figsize=(4.8, 3.0))
plt.scatter(t1_request_hours, t1_age_hours, color="teal", s=70)
plt.axhline(t1_refresh_hours, color="gray", linestyle="--", label="refresh window")
plt.xlabel("request time (hours)")
plt.ylabel("cached prediction age")
plt.title("Toy 1 · batch age resets every refresh")
plt.legend()
plt.show()
```
▶ What you'll see: requests just after a refresh have tiny ages; requests near 8 hours are almost 4 hours stale.

### ✍️ Toy 2 · Online latency is an additive critical path

Online inference waits for every dependency on the request path. Summing components also gives a
single-worker throughput sanity check.

```python
import numpy as np

t2_rng = np.random.default_rng(0)
t2_component_names = np.array(["features", "model", "network", "retry"])
print("components:", t2_component_names.tolist())  # -> ['features', 'model', 'network', 'retry']

t2_component_ms = np.array([12.0, 25.0, 8.0, 5.0])
print("component ms:", t2_component_ms.tolist())  # -> [12.0, 25.0, 8.0, 5.0]

t2_cumulative_ms = np.cumsum(t2_component_ms)
print("cumulative ms:", t2_cumulative_ms.tolist())  # -> [12.0, 37.0, 45.0, 50.0]

t2_total_ms = float(t2_component_ms.sum())
print("total latency ms:", round(t2_total_ms, 1))  # -> 50.0

t2_single_worker_qps = 1000.0 / t2_total_ms
print("single-worker qps:", round(t2_single_worker_qps, 1))  # -> 20.0
assert round(t2_single_worker_qps, 1) == 20.0

plt.figure(figsize=(5.0, 3.0))
plt.bar(t2_component_names, t2_component_ms, color=["steelblue", "darkorange", "seagreen", "purple"])
plt.plot(t2_component_names, t2_cumulative_ms, marker="o", color="black", label="cumulative")
plt.ylabel("milliseconds")
plt.title("Toy 2 · online path adds components")
plt.legend()
plt.show()
```
▶ What you'll see: the path totals 50 ms, so one worker can handle about 20 serial requests per second.

### ✍️ Toy 3 · Hybrid latency is a cache-hit weighted average

A hybrid system pays the cache latency on hits and the online latency on misses. The expected value
is just the weighted sum of those two paths.

```python
import numpy as np

t3_rng = np.random.default_rng(0)
t3_hit_rate = 0.80
print("cache hit rate:", t3_hit_rate)  # -> 0.8

t3_miss_rate = 1.0 - t3_hit_rate
print("cache miss rate:", round(float(t3_miss_rate), 2))  # -> 0.2

t3_cache_latency_ms = 4.0
print("cache latency ms:", t3_cache_latency_ms)  # -> 4.0

t3_online_latency_ms = 50.0
print("online latency ms:", t3_online_latency_ms)  # -> 50.0

t3_cache_contribution = t3_hit_rate * t3_cache_latency_ms
print("cache contribution:", round(float(t3_cache_contribution), 1))  # -> 3.2

t3_online_contribution = t3_miss_rate * t3_online_latency_ms
print("online contribution:", round(float(t3_online_contribution), 1))  # -> 10.0

t3_expected_latency = t3_cache_contribution + t3_online_contribution
print("expected latency ms:", round(float(t3_expected_latency), 1))  # -> 13.2

t3_hit_grid = np.array([0.0, 0.5, 0.8, 1.0])
print("hit-rate grid:", t3_hit_grid.tolist())  # -> [0.0, 0.5, 0.8, 1.0]

t3_latency_grid = t3_hit_grid * t3_cache_latency_ms + (1.0 - t3_hit_grid) * t3_online_latency_ms
print("latency grid:", np.round(t3_latency_grid, 1).tolist())  # -> [50.0, 27.0, 13.2, 4.0]
assert round(float(t3_expected_latency), 1) == 13.2

plt.figure(figsize=(4.8, 3.0))
plt.plot(t3_hit_grid, t3_latency_grid, marker="o", color="purple")
plt.scatter([t3_hit_rate], [t3_expected_latency], color="crimson", s=80, label="current")
plt.xlabel("cache hit rate")
plt.ylabel("expected latency ms")
plt.title("Toy 3 · hit rate buys latency")
plt.legend()
plt.show()
```
▶ What you'll see: moving from no cache to an 80% hit rate cuts expected latency from 50 ms to 13.2 ms.

### ✍️ Toy 4 · Batching amortizes fixed compute and raises throughput

If each batch pays a launch overhead once, larger batches reduce per-request compute until per-item
work dominates.

```python
import numpy as np

t4_rng = np.random.default_rng(0)
t4_fixed_ms = 8.0
print("fixed ms per batch:", t4_fixed_ms)  # -> 8.0

t4_per_item_ms = 2.0
print("per-item ms:", t4_per_item_ms)  # -> 2.0

t4_batch_sizes = np.array([1, 2, 4, 8])
print("batch sizes:", t4_batch_sizes.tolist())  # -> [1, 2, 4, 8]

t4_batch_compute_ms = t4_fixed_ms + t4_per_item_ms * t4_batch_sizes
print("batch compute ms:", t4_batch_compute_ms.tolist())  # -> [10.0, 12.0, 16.0, 24.0]

t4_per_request_ms = t4_batch_compute_ms / t4_batch_sizes
print("per-request ms:", t4_per_request_ms.tolist())  # -> [10.0, 6.0, 4.0, 3.0]

t4_throughput_qps = 1000.0 * t4_batch_sizes / t4_batch_compute_ms
print("throughput qps:", np.round(t4_throughput_qps, 1).tolist())  # -> [100.0, 166.7, 250.0, 333.3]
assert round(float(t4_per_request_ms[-1]), 1) == 3.0

plt.figure(figsize=(4.8, 3.0))
plt.plot(t4_batch_sizes, t4_throughput_qps, marker="o", color="seagreen")
plt.xlabel("batch size")
plt.ylabel("throughput qps")
plt.title("Toy 4 · bigger batches share overhead")
plt.show()
```
▶ What you'll see: per-request compute falls from 10 ms to 3 ms, and throughput rises toward the per-item limit.

### ✍️ Toy 5 · Little's law turns qps and latency into capacity

Concurrency is arrival rate times time in system. Replica sizing then divides peak qps by safe
per-replica capacity.

```python
import numpy as np

t5_rng = np.random.default_rng(0)
t5_qps = np.array([120.0, 240.0, 360.0])
print("qps:", t5_qps.tolist())  # -> [120.0, 240.0, 360.0]

t5_latency_s = 0.05
print("latency seconds:", t5_latency_s)  # -> 0.05

t5_inflight = t5_qps * t5_latency_s

t5_replica_capacity_qps = 100.0

t5_target_util = 0.70

t5_safe_capacity_qps = t5_replica_capacity_qps * t5_target_util

t5_needed_replicas = np.ceil(t5_qps / t5_safe_capacity_qps).astype(int)

assert t5_needed_replicas[-1] == 6

plt.figure(figsize=(4.8, 3.0))

```
▶ What you'll see: at 360 qps, the system needs 6 replicas to keep each one near 70% utilization.

### ✍️ Toy 6 · Micro-batching trades wait time for tail latency

A dynamic micro-batcher waits a short window, runs the batch, and returns every request together.
The early requests in each batch pay the most waiting.

```python
import numpy as np

t6_rng = np.random.default_rng(0)
t6_arrivals_ms = np.array([0.0, 1.0, 3.0, 10.0, 11.0, 20.0])
print("arrivals ms:", t6_arrivals_ms.tolist())  # -> [0.0, 1.0, 3.0, 10.0, 11.0, 20.0]

t6_window_ms = 4.0
print("batch window ms:", t6_window_ms)  # -> 4.0

t6_max_batch = 3
print("max batch size:", t6_max_batch)  # -> 3

t6_finish_ms = np.zeros_like(t6_arrivals_ms)
t6_batch_sizes = []
t6_i = 0
while t6_i < len(t6_arrivals_ms):
    t6_start_ms = t6_arrivals_ms[t6_i]
    t6_j = t6_i
    while t6_j < len(t6_arrivals_ms) and t6_arrivals_ms[t6_j] <= t6_start_ms + t6_window_ms and (t6_j - t6_i) < t6_max_batch:
        t6_j += 1
    t6_size = t6_j - t6_i
    t6_run_ms = 5.0 + t6_size
    t6_done_ms = max(t6_arrivals_ms[t6_j - 1], t6_start_ms + t6_window_ms) + t6_run_ms
    t6_finish_ms[t6_i:t6_j] = t6_done_ms
    t6_batch_sizes.append(t6_size)
    t6_i = t6_j
print("batch sizes:", t6_batch_sizes)  # -> [3, 2, 1]
print("finish ms:", t6_finish_ms.tolist())  # -> [12.0, 12.0, 12.0, 21.0, 21.0, 30.0]

t6_latency_ms = t6_finish_ms - t6_arrivals_ms
print("latency ms:", t6_latency_ms.tolist())  # -> [12.0, 11.0, 9.0, 11.0, 10.0, 10.0]

t6_mean_ms = float(t6_latency_ms.mean())
print("mean latency ms:", round(t6_mean_ms, 2))  # -> 10.5

t6_p95_ms = float(np.percentile(t6_latency_ms, 95))
print("p95 latency ms:", round(t6_p95_ms, 2))  # -> 11.75

t6_slo_ms = 12.0
print("p95 SLO ms:", t6_slo_ms)  # -> 12.0

t6_meets_slo = bool(t6_p95_ms <= t6_slo_ms)
print("meets SLO:", t6_meets_slo)  # -> True
assert t6_meets_slo is True

plt.figure(figsize=(4.8, 3.0))
plt.hist(t6_latency_ms, bins=np.arange(8.5, 12.6, 0.5), color="steelblue", edgecolor="white")
plt.axvline(t6_p95_ms, color="crimson", linestyle="--", label="p95")
plt.xlabel("latency ms")
plt.ylabel("requests")
plt.title("Toy 6 · batch window creates a tail")
plt.legend()
plt.show()
```
▶ What you'll see: the first request in the first batch waits longest, but p95 still stays under the 12 ms SLO.

### ✍️ Toy 7 · Pareto frontier keeps non-dominated serving designs

A design is dominated if another design has no worse latency, cost, and staleness, with at least one
strictly better metric.

```python
import numpy as np

t7_rng = np.random.default_rng(0)
t7_names = np.array(["batch", "online", "hybrid", "slow_hybrid"])
print("designs:", t7_names.tolist())  # -> ['batch', 'online', 'hybrid', 'slow_hybrid']

t7_metrics = np.array([[5.0, 1.0, 6.0],
                       [50.0, 5.0, 0.0],
                       [18.0, 3.0, 1.0],
                       [25.0, 4.0, 2.0]])
```

### Advanced 2 — Sweep batch-window versus SLO

**Goal.** Vary the micro-batch wait window and compare throughput with p95 latency, because the largest safe window is bounded by the SLO. We build it in 4 steps.

```python

print("windows:", windows_a2)  # Inspect sweep values.
```
▶ What you'll see: the sweep includes no batching wait and increasingly larger windows.

```python
p95s_a2 = []
throughputs_a2 = []
for window_a2 in windows_a2:
    finish_a2 = np.zeros_like(arrivals_a2)
    sizes_a2 = []
    i_a2 = 0
    while i_a2 < len(arrivals_a2):
        start_a2 = arrivals_a2[i_a2]
        j_a2 = i_a2
        while j_a2 < len(arrivals_a2) and arrivals_a2[j_a2] <= start_a2 + window_a2 and (j_a2 - i_a2) < 16:

        size_a2 = j_a2 - i_a2
        run_a2 = 7.0 + 1.0 * size_a2
        done_a2 = max(arrivals_a2[j_a2 - 1], start_a2 + window_a2) + run_a2
```

```python

    finish = np.zeros_like(arrivals, dtype=float)
    for i in range(len(arrivals)):
        start = arrivals[i] if i == 0 else max(arrivals[i], finish[i - 1])
```

### Advanced 5 — Extract a Pareto frontier of serving designs

**Goal.** Identify non-dominated designs, because a serving option is only interesting if no other option is both faster and cheaper at equal or better freshness. We build it in 4 steps.
