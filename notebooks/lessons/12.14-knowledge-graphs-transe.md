# 12.14 — Knowledge Graphs & TransE

Knowledge graphs store typed facts such as `(Ada, works_at, OpenAI)`, and TransE turns those symbolic facts into geometry: the head embedding plus the relation embedding should land near the tail embedding. In this lesson, you will build a tiny knowledge graph, implement TransE scoring, margin ranking loss, negative sampling, SGD, and link-prediction metrics from scratch with NumPy so every number is inspectable.

### 1. Knowledge graphs as typed triples

A knowledge graph is not just a graph of connected nodes; every edge has a **type**. The triple `(head, relation, tail)` says that a particular relation holds from one entity to another. This typing matters because the same pair of entities can participate in different relationships, and reversing a relationship usually changes its meaning.

```python
entities_w = np.array(["Ada", "Ben", "Cy", "DataLab", "GraphCo", "Paris"])  # nodes in the toy KG.
relations_w = np.array(["works_at", "lives_in", "collaborates_with"])  # typed edge labels.
triples_w = np.array([[0, 0, 3], [1, 0, 4], [0, 1, 5], [1, 1, 5], [0, 2, 1], [1, 2, 2]])  # h, r, t ids.
for h_w, r_w, t_w in triples_w:
    print(f"({entities_w[h_w]}, {relations_w[r_w]}, {entities_w[t_w]})")
```
▶ What you'll see: six typed facts, including people working at companies, living in Paris, and collaborating.

```python
plt.figure(figsize=(5, 3))
counts_w = np.array([np.sum(triples_w[:, 1] == r_w) for r_w in range(len(relations_w))])
plt.bar(relations_w, counts_w, color=["teal", "orange", "purple"])
plt.title("1: relation types in the toy KG")
plt.ylabel("number of triples")
plt.xticks(rotation=15)
plt.show()
```
▶ What you'll see: a small bar chart showing that each edge type supplies its own training signal.

*Why it's done this way:* storing triples as integer ids makes the symbolic graph easy to index into embedding matrices. The relation id is not decoration: it selects a relation-specific vector, so `(Ada, works_at, DataLab)` can mean something different from `(Ada, lives_in, DataLab)` even though the head and tail slots look the same.

### 2. TransE scoring: the translation `h + r ≈ t`

TransE gives every entity an embedding vector `e_h` and every relation a vector `e_r`. A true triple should satisfy `e_h + e_r ≈ e_t`, so the score is a distance: lower means more plausible. The canonical distance is $f(h,r,t)=\lVert e_h+e_r-e_t\rVert_2$.

```python
h_w = np.array([1.0, 1.0])  # head embedding.
r_w = np.array([2.0, 0.0])  # relation translation.
t_w = np.array([3.0, 1.0])  # tail embedding.
translated_w = h_w + r_w
score_w = float(np.linalg.norm(translated_w - t_w))
print("h + r:", translated_w, "tail:", t_w)
print("TransE distance:", round(score_w, 3))
assert round(score_w, 3) == 0.000
```
▶ What you'll see: `h + r` lands exactly on the tail, so the distance is 0.

```python
bad_tail_w = np.array([2.0, 2.0])
bad_score_w = float(np.linalg.norm(translated_w - bad_tail_w))
print("corrupted tail distance:", round(bad_score_w, 3))
assert round(bad_score_w, 3) == 1.414
plt.figure(figsize=(4, 3))
plt.scatter([h_w[0], translated_w[0], t_w[0], bad_tail_w[0]], [h_w[1], translated_w[1], t_w[1], bad_tail_w[1]], color=["teal", "black", "green", "red"])
plt.arrow(h_w[0], h_w[1], r_w[0], r_w[1], head_width=0.08, length_includes_head=True, color="black")
for p_w, label_w in [(h_w, "h"), (translated_w, "h+r"), (t_w, "true t"), (bad_tail_w, "bad t")]:
    plt.text(p_w[0] + 0.04, p_w[1] + 0.04, label_w)
plt.xlim(0.5, 3.5); plt.ylim(0.5, 2.4); plt.title("2: TransE translation geometry"); plt.show()
```
▶ What you'll see: the relation arrow moves the head onto the true tail and away from the corrupted tail.

*Why it's done this way:* a distance score turns relation meaning into geometry. If `works_at` is a consistent offset from people to companies, then many facts can share the same relation vector instead of memorizing separate edges. Low distance is good because the model is asked to make true translations land closer than false ones.

### 3. Inverse relations and direction

Relations are directional. If `Ada works_at DataLab`, the reverse fact is not represented by the same vector; it needs an inverse relation whose translation points back from tail to head. For pure translations, the ideal inverse vector is approximately `-r`.

```python
forward_r_w = np.array([2.0, 0.0])
inverse_r_w = -forward_r_w
data_lab_w = np.array([3.0, 1.0])
ada_w = np.array([1.0, 1.0])
back_distance_w = float(np.linalg.norm(data_lab_w + inverse_r_w - ada_w))
print("inverse relation vector:", inverse_r_w)
print("reverse distance:", round(back_distance_w, 3))
assert round(back_distance_w, 3) == 0.000
```
▶ What you'll see: negating the relation vector makes the reversed triple geometrically consistent.

```python
same_r_reverse_w = float(np.linalg.norm(data_lab_w + forward_r_w - ada_w))
print("using the same relation backward gives distance:", round(same_r_reverse_w, 3))
assert round(same_r_reverse_w, 3) == 4.000
```
▶ What you'll see: the wrong direction pushes even farther away, giving a distance of 4.


```python
plt.figure(figsize=(4.5, 3))
plt.scatter([ada_w[0], data_lab_w[0]], [ada_w[1], data_lab_w[1]], color=["teal", "green"])
plt.arrow(ada_w[0], ada_w[1], forward_r_w[0], forward_r_w[1], head_width=0.08, length_includes_head=True, color="black", label="forward")
plt.arrow(data_lab_w[0], data_lab_w[1], inverse_r_w[0], inverse_r_w[1], head_width=0.08, length_includes_head=True, color="crimson", label="inverse")
plt.text(ada_w[0] - 0.15, ada_w[1] + 0.12, "Ada")
plt.text(data_lab_w[0] - 0.35, data_lab_w[1] + 0.12, "DataLab")
plt.xlim(0.5, 3.5); plt.ylim(0.5, 1.6); plt.legend(); plt.title("3: inverse relation reverses direction")
plt.show()
```
▶ What you'll see: the inverse relation arrow points from the tail embedding back to the head embedding.

*Why it's done this way:* TransE is asymmetric only through relation direction. The entity embeddings are shared, so the model needs separate relation parameters for forward and inverse facts; otherwise it would imply that moving from person to company and company to person are the same operation.

### 4. Negative sampling: make false triples to compare against positives

A KG usually lists positives but not explicit negatives. TransE therefore trains by corrupting a known fact: replace the head or tail with a different entity and treat the result as a likely false triple. These negatives define task difficulty; easy corruptions teach little once the model already separates them.

```python
pos_w = np.array([0, 0, 3])  # (Ada, works_at, DataLab).
rng_w = np.random.default_rng(0)
negatives_w = []
for _ in range(5):
    corrupted_w = pos_w.copy()
    if rng_w.random() < 0.5:
        corrupted_w[0] = rng_w.integers(len(entities_w))
    else:
        corrupted_w[2] = rng_w.integers(len(entities_w))
    negatives_w.append(corrupted_w)
print("positive:", tuple(pos_w))
print("sample negatives:", [tuple(x) for x in negatives_w])
```
▶ What you'll see: several triples that share the relation but replace one entity slot.

```python
known_w = {tuple(x) for x in triples_w}
filtered_w = [x for x in negatives_w if tuple(x) not in known_w and x[0] != x[2]]
print("filtered negatives:", [tuple(x) for x in filtered_w])
print("kept count:", len(filtered_w))
assert len(filtered_w) >= 2
```
▶ What you'll see: filtering avoids accidentally labeling a known positive as negative.


```python
plt.figure(figsize=(5, 3))
labels_w = ["sampled", "kept", "discarded"]
values_w = [len(negatives_w), len(filtered_w), len(negatives_w) - len(filtered_w)]
plt.bar(labels_w, values_w, color=["steelblue", "seagreen", "crimson"])
plt.title("4: filtering sampled corruptions")
plt.ylabel("negative triples")
plt.show()
```
▶ What you'll see: sampled corruptions are split into usable negatives and discarded known/self triples.

*Why it's done this way:* the margin loss needs a contrast: “this positive should score better than that negative.” Corrupting one entity creates a near-miss with the same relation, so the model learns relation-specific compatibility rather than merely learning which entities are common.

### 5. Margin ranking loss

TransE does not need calibrated probabilities. It only needs positives to be closer than negatives by at least a margin $\gamma$. For one pair, the loss is $\max(0, \gamma + f(h,r,t) - f(h',r,t'))$. If the negative is already far enough away, the hinge is zero.

```python
pos_dist_w = 0.0
neg_dist_w = np.sqrt(2.0)
gamma_w = 1.0
loss_w = max(0.0, gamma_w + pos_dist_w - neg_dist_w)
print("margin loss:", round(loss_w, 3))
assert round(loss_w, 3) == 0.000
```
▶ What you'll see: the loss is zero because the negative is more than margin 1 farther than the positive.

```python
hard_neg_dist_w = 0.4
hard_loss_w = max(0.0, gamma_w + pos_dist_w - hard_neg_dist_w)
print("hard negative loss:", round(hard_loss_w, 3))
assert round(hard_loss_w, 3) == 0.600
plt.figure(figsize=(4, 3))
plt.bar(["easy neg", "hard neg"], [loss_w, hard_loss_w], color=["seagreen", "crimson"])
plt.title("5: hinge loss activates only inside the margin")
plt.ylabel("loss")
plt.show()
```
▶ What you'll see: the easy negative has no penalty, while the hard negative produces positive loss.

*Why it's done this way:* ranking is the real link-prediction goal: the true tail should outrank alternatives. The margin prevents wasting updates on negatives that are already safely worse, focusing learning pressure on confusing false triples near the positive.

### 6. Training TransE from scratch

Training repeatedly samples a positive triple, corrupts it, and nudges embeddings so the positive distance shrinks while the negative distance grows. We normalize entity vectors after updates to keep distances well behaved; otherwise embeddings can grow just to satisfy margins.

```python
def score_w(E_w, R_w, triple_w):
    h_i_w, r_i_w, t_i_w = triple_w
    return float(np.linalg.norm(E_w[h_i_w] + R_w[r_i_w] - E_w[t_i_w]))

rng_w = np.random.default_rng(1)
E_w = 0.1 * rng_w.normal(size=(len(entities_w), 2))
Rrel_w = 0.1 * rng_w.normal(size=(len(relations_w), 2))
print("initial score for first positive:", round(score_w(E_w, Rrel_w, triples_w[0]), 3))
```
▶ What you'll see: random embeddings give an arbitrary starting distance.

```python
losses_w = []
for epoch_w in range(250):
    total_w = 0.0
    for pos_triple_w in triples_w:
        neg_w = pos_triple_w.copy()
        if rng_w.random() < 0.5:
            neg_w[0] = rng_w.integers(len(entities_w))
        else:
            neg_w[2] = rng_w.integers(len(entities_w))
        sp_w = score_w(E_w, Rrel_w, pos_triple_w)
        sn_w = score_w(E_w, Rrel_w, neg_w)
        loss_pair_w = max(0.0, 1.0 + sp_w - sn_w)
        total_w += loss_pair_w
        if loss_pair_w > 0:
            hp_w, rp_w, tp_w = pos_triple_w
            hn_w, rn_w, tn_w = neg_w
            gp_w = (E_w[hp_w] + Rrel_w[rp_w] - E_w[tp_w]) / (sp_w + 1e-9)
            gn_w = (E_w[hn_w] + Rrel_w[rn_w] - E_w[tn_w]) / (sn_w + 1e-9)
            eta_w = 0.04
            E_w[hp_w] -= eta_w * gp_w; Rrel_w[rp_w] -= eta_w * gp_w; E_w[tp_w] += eta_w * gp_w
            E_w[hn_w] += eta_w * gn_w; Rrel_w[rn_w] += eta_w * gn_w; E_w[tn_w] -= eta_w * gn_w
            E_w = E_w / np.maximum(1.0, np.linalg.norm(E_w, axis=1, keepdims=True))
    losses_w.append(total_w)
print("loss start -> end:", round(losses_w[0], 3), "->", round(losses_w[-1], 3))
assert losses_w[-1] < losses_w[0]
```
▶ What you'll see: the total hinge loss drops as positive translations become easier to separate from negatives.

```python
plt.figure(figsize=(5, 3))
plt.plot(losses_w, color="purple")
plt.title("6: TransE margin loss during SGD")
plt.xlabel("epoch")
plt.ylabel("total hinge loss")
plt.show()
```
▶ What you'll see: a noisy but downward learning curve, because each epoch uses fresh corrupted triples.

*Why it's done this way:* the gradient of a distance points along the vector `h + r - t`. Decreasing the positive distance moves head and relation toward the tail; increasing the negative distance moves the corrupted triple apart. Normalization keeps the solution from satisfying the margin by inflating all vectors.

### 7. Link prediction metrics: rank, MRR, and Hits@k

After training, link prediction asks: if we hide the tail of `(h, r, ?)`, where does the true tail rank among all candidates? Mean reciprocal rank (MRR) averages `1/rank`, so rank 1 contributes 1.0 and rank 10 contributes 0.1. Hits@k measures the fraction of queries whose true answer appears in the top k.

```python
def tail_ranks_w(E_w, R_w, triples_eval_w):
    ranks_w = []
    for h_i_w, r_i_w, t_i_w in triples_eval_w:
        distances_w = np.array([score_w(E_w, R_w, [h_i_w, r_i_w, cand_w]) for cand_w in range(E_w.shape[0])])
        order_w = np.argsort(distances_w)
        rank_w = int(np.where(order_w == t_i_w)[0][0]) + 1
        ranks_w.append(rank_w)
    return np.array(ranks_w)

ranks_w = tail_ranks_w(E_w, Rrel_w, triples_w)
print("tail ranks:", ranks_w)
print("MRR:", round(float(np.mean(1 / ranks_w)), 3), "Hits@3:", round(float(np.mean(ranks_w <= 3)), 3))
assert np.all(ranks_w >= 1)
```
▶ What you'll see: each positive fact receives a tail rank, then MRR and Hits@3 summarize ranking quality.

```python
plt.figure(figsize=(5, 3))
plt.hist(ranks_w, bins=np.arange(1, len(entities_w) + 2) - 0.5, color="steelblue", edgecolor="white")
plt.xticks(range(1, len(entities_w) + 1))
plt.title("7: distribution of true-tail ranks")
plt.xlabel("rank of true tail")
plt.ylabel("count")
plt.show()
```
▶ What you'll see: more mass near rank 1 means better link prediction.

*Why it's done this way:* KG completion is a retrieval problem, so absolute distances matter less than ordering. MRR rewards moving the true entity from rank 5 to rank 1 much more than from rank 50 to rank 46, while Hits@k matches product behavior such as “is the answer in the first page?”

### 8. A one-to-many pitfall

Pure translation struggles with one-to-many relations. If one head and relation point to several far-apart tails, the single vector `h + r` cannot land close to all of them at once; it must compromise.

```python
center_w = np.array([0.0, 0.0])
children_w = np.array([[2.0, 0.0], [-2.0, 0.0], [0.0, 2.0]])
best_translation_w = children_w.mean(axis=0) - center_w
compromise_point_w = center_w + best_translation_w
dists_w = np.linalg.norm(compromise_point_w - children_w, axis=1)
print("best compromise h+r:", np.round(compromise_point_w, 3))
print("distances to three tails:", np.round(dists_w, 3))
assert round(float(dists_w.mean()), 3) == 1.850
```
▶ What you'll see: the compromise translation is not exactly on any tail.

```python
plt.figure(figsize=(4, 3))
plt.scatter(children_w[:, 0], children_w[:, 1], color="crimson", label="true tails")
plt.scatter([center_w[0]], [center_w[1]], color="teal", label="head")
plt.scatter([compromise_point_w[0]], [compromise_point_w[1]], color="black", label="h+r compromise")
plt.legend(); plt.title("8: one-to-many strains one translation"); plt.axis("equal"); plt.show()
```
▶ What you'll see: the black compromise point sits between multiple tails rather than matching all of them.

*Why it's done this way:* the example exposes TransE's capacity limit. A single relation vector is elegant and scalable, but if the same `(h, r)` should map to many distant tails, distance minimization has no perfect solution; later KG models add relation-specific projections or richer scoring functions to handle this.

## 🛠️ Setup

```python
import numpy as np # load NumPy for arrays, vector arithmetic, random sampling, and metrics.
import matplotlib.pyplot as plt # load Matplotlib so every concept can be inspected visually.
np.random.seed(0) # make all stochastic examples reproducible across notebook runs.

def transe_score(E, R, triple): # compute the TransE distance f(h,r,t)=||e_h+e_r-e_t||_2.
    h, r, t = triple # unpack integer ids for head, relation, and tail.
    return float(np.linalg.norm(E[h] + R[r] - E[t])) # lower distance means a more plausible triple.

def margin_loss(pos_score, neg_score, gamma=1.0): # compute the pairwise hinge ranking loss.
    return max(0.0, gamma + pos_score - neg_score) # zero when the negative is at least gamma farther away.

def normalize_rows(X): # keep embeddings inside the unit ball for stable TransE demos.
    return X / np.maximum(1.0, np.linalg.norm(X, axis=1, keepdims=True)) # shrink only rows with norm above 1.

def rank_true_tail(E, R, triple): # rank the true tail against every candidate entity.
    h, r, t = triple # unpack the query.
    distances = np.array([transe_score(E, R, [h, r, cand]) for cand in range(E.shape[0])]) # score all candidate tails.
    order = np.argsort(distances) # lower TransE distance ranks first.
    return int(np.where(order == t)[0][0]) + 1, distances # convert zero-based position to one-based rank.
```

### Easy 2 — Run a tiny TransE training loop

**Goal.** Train embeddings on the toy KG, because repeated margin updates should reduce average hinge loss. We build it in 4 steps.

```python
triples_e2 = np.array([[0, 0, 3], [1, 0, 4], [0, 1, 5], [1, 1, 5], [0, 2, 1], [1, 2, 2]]) # toy KG triples.
n_entities_e2, n_relations_e2 = 6, 3 # define table sizes.
rng_e2 = np.random.default_rng(2) # local reproducible generator.
E_e2 = 0.1 * rng_e2.normal(size=(n_entities_e2, 2)); R_e2 = 0.1 * rng_e2.normal(size=(n_relations_e2, 2)) # initialize embeddings.
print("initial first score:", round(transe_score(E_e2, R_e2, triples_e2[0]), 3)) # inspect random start.
```
▶ What you'll see: the first positive starts with an arbitrary distance.

```python
losses_e2 = [] # store per-epoch hinge loss.
for epoch_e2 in range(180): # train for a small number of epochs.
    total_e2 = 0.0 # reset epoch loss.
    for pos_e2 in triples_e2: # loop through positives.
        neg_e2 = pos_e2.copy(); neg_e2[2] = rng_e2.integers(n_entities_e2) # corrupt the tail.
        sp_e2 = transe_score(E_e2, R_e2, pos_e2); sn_e2 = transe_score(E_e2, R_e2, neg_e2) # score pair.
        loss_e2 = margin_loss(sp_e2, sn_e2, 1.0); total_e2 += loss_e2 # accumulate hinge.
        if loss_e2 > 0: # update only active pairs.
            gp_e2 = (E_e2[pos_e2[0]] + R_e2[pos_e2[1]] - E_e2[pos_e2[2]]) / (sp_e2 + 1e-9) # positive direction.
            gn_e2 = (E_e2[neg_e2[0]] + R_e2[neg_e2[1]] - E_e2[neg_e2[2]]) / (sn_e2 + 1e-9) # negative direction.
            old_head_e2 = E_e2[pos_e2[0]].copy() # save old head for stability.
            E_e2[pos_e2[0]] = old_head_e2 - 0.03 * gp_e2 + 0.03 * gn_e2 # combine head effects when same head.
            R_e2[pos_e2[1]] -= 0.03 * gp_e2; E_e2[pos_e2[2]] += 0.03 * gp_e2; E_e2[neg_e2[2]] -= 0.03 * gn_e2 # update relation and tails.
            E_e2 = normalize_rows(E_e2) # constrain entity norms.
    losses_e2.append(total_e2) # record epoch loss.
print("loss start -> end:", round(losses_e2[0], 3), "->", round(losses_e2[-1], 3)) # inspect convergence.
assert losses_e2[-1] < losses_e2[0] # verify training improved.
```
▶ What you'll see: total hinge loss decreases over training.

```python

plt.plot(losses_e2, color="purple") # draw epoch loss.
plt.title("Easy 2: tiny TransE training") # title chart.
plt.xlabel("epoch"); plt.ylabel("total hinge loss") # label axes.
plt.show() # display.
```
▶ What you'll see: a noisy downward curve from stochastic corruptions.

```python
scores_a2 = np.array([transe_score(E_a2, R_a2, [0, 0, cand_a2]) for cand_a2 in range(E_a2.shape[0])]) # score all candidates.

```
▶ What you'll see: entity 1 and entity 2 are both close for the same query.

```python
raw_order_a2 = np.argsort(scores_a2) # raw ranking includes all candidates.
```

### Advanced 3 — Demonstrate a one-to-many limitation

**Goal.** Fit one translation to multiple tails, because pure TransE must compromise on one-to-many relations. We build it in 3 steps.

```python
head_a3 = np.array([0., 0.]) # one shared head.
tails_a3 = np.array([[2., 0.], [-2., 0.], [0., 2.]]) # three valid tails for the same relation.
r_best_a3 = tails_a3.mean(axis=0) - head_a3 # least-squares translation to the tail centroid.
point_a3 = head_a3 + r_best_a3 # translated head.
dists_a3 = np.linalg.norm(point_a3 - tails_a3, axis=1) # distances to all true tails.
print("best r:", np.round(r_best_a3, 3), "distances:", np.round(dists_a3, 3)) # inspect compromise.
assert round(float(np.mean(dists_a3)), 3) == 1.850 # verify worked number.
```
▶ What you'll see: no single translation lands on all three tails.

```python
plt.figure(figsize=(4, 3)) # create geometry plot.
```

▶ What you'll see: the translation sits between the true tails.

### Advanced 4 — Sweep embedding dimension

**Goal.** Train the same toy KG with different embedding dimensions, because dimension is a capacity knob for TransE. We build it in 4 steps.

```python
triples_a4 = np.array([[0, 0, 3], [1, 0, 4], [0, 1, 5], [1, 1, 5], [0, 2, 1], [1, 2, 2]]) # toy facts.
dims_a4 = np.array([1, 2, 4]) # test capacities.
final_losses_a4 = [] # store one final loss per dimension.
print("dimensions:", dims_a4) # inspect sweep.
```
▶ What you'll see: the sweep compares 1-D, 2-D, and 4-D embeddings.

```python
for dim_a4 in dims_a4: # train one tiny model per dimension.
    rng_a4 = np.random.default_rng(int(dim_a4)) # reset seed per dimension.
    E_a4 = 0.1 * rng_a4.normal(size=(6, dim_a4)); R_a4 = 0.1 * rng_a4.normal(size=(3, dim_a4)) # initialize.
    losses_dim_a4 = [] # track this model.
    for epoch_a4 in range(120): # short training.
        total_a4 = 0.0 # epoch loss.
        for pos_a4 in triples_a4: # positives.
            neg_a4 = pos_a4.copy(); neg_a4[2] = rng_a4.integers(6) # corrupt tail.
            sp_a4 = transe_score(E_a4, R_a4, pos_a4); sn_a4 = transe_score(E_a4, R_a4, neg_a4) # scores.
            loss_a4 = margin_loss(sp_a4, sn_a4, 1.0); total_a4 += loss_a4 # hinge.
            if loss_a4 > 0: # update active pair.
                gp_a4 = (E_a4[pos_a4[0]] + R_a4[pos_a4[1]] - E_a4[pos_a4[2]]) / (sp_a4 + 1e-9) # pos direction.
                gn_a4 = (E_a4[neg_a4[0]] + R_a4[neg_a4[1]] - E_a4[neg_a4[2]]) / (sn_a4 + 1e-9) # neg direction.
                E_a4[pos_a4[0]] -= 0.02 * gp_a4; R_a4[pos_a4[1]] -= 0.02 * gp_a4; E_a4[pos_a4[2]] += 0.02 * gp_a4 # pull pos.
                E_a4[neg_a4[0]] += 0.02 * gn_a4; R_a4[neg_a4[1]] += 0.02 * gn_a4; E_a4[neg_a4[2]] -= 0.02 * gn_a4 # push neg.
                E_a4 = normalize_rows(E_a4) # constrain norms.
        losses_dim_a4.append(total_a4) # record.
    final_losses_a4.append(losses_dim_a4[-1]) # save final loss.
print("final losses:", np.round(final_losses_a4, 3)) # inspect capacity effect.
```
▶ What you'll see: different dimensions end with different losses because capacity and optimization changed.

```python
plt.figure(figsize=(4, 3)) # create sweep plot.
plt.plot(dims_a4, final_losses_a4, marker="o", color="purple") # plot final loss vs dimension.
plt.title("Advanced 4: embedding dimension sweep") # title.
plt.xlabel("embedding dimension"); plt.ylabel("final hinge loss") # labels.
plt.xticks(dims_a4); plt.show() # display.
```
▶ What you'll see: dimension changes how much geometry the model can represent.

```python

print("best dimension in this tiny run:", best_dim_a4) # inspect selected capacity.
assert best_dim_a4 in [1, 2, 4] # verify valid choice.
```
▶ What you'll see: the selected dimension is simply the best on this toy criterion.

👀 Takeaway: embedding dimension is a validation-tuned capacity parameter, not a universal constant.
