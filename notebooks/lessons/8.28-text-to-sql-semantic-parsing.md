# 8.28 — Text-to-SQL & Semantic Parsing

Semantic parsing turns a natural-language question into an executable program, so the model is right only when words, schema items, SQL grammar, and database execution all agree. In text-to-SQL, "highest sales" is not a phrase to paraphrase; it is evidence for linking *sales* to the right column, choosing a maximum aggregation, emitting only grammar-valid SQL actions, and checking the answer by running the query.

### 1. Schema linking: grounding words in columns

A semantic parser cannot choose SQL actions safely until it knows which question words refer to which schema items. We start with two question cues, `highest` and `sales`, and two candidate columns, `revenue` and `region`. The scores are deliberately tiny and inspectable: a high score means the word and column are semantically compatible.

```python
words_w = ["highest", "sales"]
columns_w = ["revenue", "region"]
link_scores_w = np.array([[0.8, 0.1],
                          [0.9, 0.2]])
print("rows = words:", words_w)
print("cols = schema:", columns_w)
print(link_scores_w)
```
▶ What you'll see: `sales` scores 0.9 with `revenue` and only 0.2 with `region`.

```python
best_col_w = np.argmax(link_scores_w, axis=1)
margin_sales_w = link_scores_w[1, best_col_w[1]] - np.partition(link_scores_w[1], -2)[-2]
for i_w, word_w in enumerate(words_w):
    print(word_w, "→", columns_w[best_col_w[i_w]], "score", link_scores_w[i_w, best_col_w[i_w]])
print("sales margin:", round(float(margin_sales_w), 3))
assert round(float(margin_sales_w), 3) == 0.7
```
▶ What you'll see: `sales → revenue` with a margin of 0.7, matching the lesson block.

```python
plt.figure(figsize=(4.4, 3.1))
plt.imshow(link_scores_w, cmap="Blues", vmin=0, vmax=1)
plt.colorbar(label="link score")
plt.xticks(range(len(columns_w)), columns_w)
plt.yticks(range(len(words_w)), words_w)
plt.title("1: word-to-schema links")
plt.show()
```
▶ What you'll see: the brightest cell for `sales` is under `revenue`; that is the grounding signal the parser should trust.

*Why it's done this way:* SQL columns are not generated from language alone; they are selected from a database schema. The margin matters because a parser should be more confident when the best schema item is separated from alternatives. Here, the difference $0.9-0.2=0.7$ says `sales` strongly points to `revenue`, so aggregating `region` would be valid SQL but wrong semantics.

### 2. Slot filling: turning cues into a query sketch

Once words are linked to schema items, a parser fills a small program sketch: aggregation, selected column, table, and optional filter. This is the simplest form of semantic parsing: rather than emitting arbitrary text, we map language cues into typed slots that can later be rendered as SQL.

```python
question_w = "Which region had the highest sales?"
schema_w = {"table": "sales", "columns": ["region", "revenue", "quarter"]}
slots_w = {"select": None, "agg": None, "table": schema_w["table"], "where": None}
print("question:", question_w)
print("initial slots:", slots_w)
```
▶ What you'll see: the parser starts with an empty typed sketch, not a SQL string.

```python
if "highest" in question_w.lower() or "most" in question_w.lower():
    slots_w["agg"] = "MAX"
slots_w["select"] = "revenue" if columns_w[best_col_w[1]] == "revenue" else columns_w[best_col_w[1]]
print("filled slots:", slots_w)
assert slots_w["agg"] == "MAX" and slots_w["select"] == "revenue"
```
▶ What you'll see: `highest` becomes `MAX`, and the schema link fills the selected column as `revenue`.

```python
actions_w = ["SELECT", "AGG_MAX", "COLUMN_revenue", "FROM_sales"]
for idx_w, action_w in enumerate(actions_w):
    print(idx_w, action_w)
assert len(actions_w) == 4 and actions_w[:2] == ["SELECT", "AGG_MAX"]
```
▶ What you'll see: four actions, indexed 0 through 3; the first two establish a maximum aggregation query.

*Why it's done this way:* Slot filling separates *what role a phrase plays* from *how SQL spells it*. `highest` is not a column; it is an operation. `sales` is not an operation; it is evidence for the numeric column. Keeping slots typed prevents category mistakes such as using a table name where an aggregation should go.

### 3. Grammar-constrained decoding: masking impossible next actions

A sequence model may assign a huge score to an invalid next token. Grammar-constrained decoding fixes that by multiplying the next-action distribution by a binary mask $m_k\in\{0,1\}$ before softmax. Invalid actions receive probability 0, so the decoder stays inside SQL's action language.

```python
logits_w = np.array([2.0, 5.0, 1.0, 4.0])
mask_w = np.array([1, 0, 1, 0], dtype=float)
action_names_w = ["COLUMN_revenue", "FROM_sales", "COLUMN_region", "WHERE"]
print("raw logits:", logits_w)
print("valid mask:", mask_w.astype(int))
```
▶ What you'll see: the largest raw logit is 5, but its mask value is 0.

```python
stable_logits_w = logits_w - np.max(logits_w[mask_w == 1])
exp_valid_w = np.exp(stable_logits_w) * mask_w
probs_w = exp_valid_w / exp_valid_w.sum()
print("masked probabilities:", np.round(probs_w, 3))
assert np.allclose(np.round(probs_w, 3), [0.731, 0.0, 0.269, 0.0])
```
▶ What you'll see: probabilities are `[0.731, 0, 0.269, 0]`; invalid actions are exactly zero.

```python
plt.figure(figsize=(5, 3))
plt.bar(action_names_w, probs_w, color=["seagreen" if m else "lightgray" for m in mask_w])
plt.xticks(rotation=25, ha="right")
plt.ylabel("probability")
plt.title("3: grammar mask changes decoding")
plt.show()
```
▶ What you'll see: only two valid actions have nonzero bars, and the invalid high-logit action disappears.

*Why it's done this way:* Softmax alone normalizes every logit, even impossible ones. Multiplying by $m_k$ before normalization changes the denominator to include only grammar-valid actions, so an invalid but high-scoring token cannot win. This is mathematical control over the output language, not post-hoc string cleanup.

### 4. Execution: the program must return the right denotation

A text-to-SQL system ultimately produces a query that is run against data. We use an in-memory SQLite database so the whole example is executable without files. The query asks for the maximum revenue, and execution verifies the denotation — the returned answer.

```python
conn_w = sqlite3.connect(":memory:")
cur_w = conn_w.cursor()
cur_w.execute("CREATE TABLE sales(region TEXT, revenue INTEGER, quarter TEXT)")
rows_w = [("East", 10, "Q1"), ("West", 30, "Q1"), ("North", 20, "Q1")]
cur_w.executemany("INSERT INTO sales VALUES (?, ?, ?)", rows_w)
print("inserted rows:", rows_w)
```
▶ What you'll see: three inline rows with revenue values 10, 30, and 20.

```python
sql_w = "SELECT MAX(revenue) FROM sales"
answer_w = cur_w.execute(sql_w).fetchone()[0]
print("SQL:", sql_w)
print("answer:", answer_w)
assert answer_w == 30
```
▶ What you'll see: the executed answer is 30, the largest target-column value.

```python
values_w = np.array([row_w[1] for row_w in rows_w])
plt.figure(figsize=(4.4, 3))
plt.bar([row_w[0] for row_w in rows_w], values_w, color="steelblue")
plt.axhline(answer_w, color="crimson", linestyle="--", label="MAX=30")
plt.ylabel("revenue")
plt.title("4: execution grounds the SQL")
plt.legend()
plt.show()
```
▶ What you'll see: the West bar reaches 30 and the dashed line marks the executed maximum.

*Why it's done this way:* SQL meaning is denotational: two strings can be different yet return the same value, while a fluent-looking query can return the wrong value. Running the query catches mistakes in column choice, aggregation, and filters that syntax alone cannot see.

### 5. Exact match versus execution accuracy

Evaluation has two useful lenses. Exact match asks whether the predicted SQL string equals the reference string. Execution accuracy asks whether both queries return the same answer. They can diverge, so we compute both explicitly.

```python
exact_indicators_w = np.array([1, 0, 0])
exec_indicators_w = np.array([1, 1, 0])
exact_acc_w = exact_indicators_w.mean()
exec_acc_w = exec_indicators_w.mean()
print("exact indicators:", exact_indicators_w)
print("execution indicators:", exec_indicators_w)
print("exact acc:", round(float(exact_acc_w), 3), "exec acc:", round(float(exec_acc_w), 3))
assert round(float(exact_acc_w), 3) == 0.333 and round(float(exec_acc_w), 3) == 0.667
```
▶ What you'll see: execution accuracy is higher because one non-matching query still executes correctly.

```python
query_a_w = "SELECT MAX(revenue) FROM sales"
query_b_w = "SELECT revenue FROM sales ORDER BY revenue DESC LIMIT 1"
ans_a_w = cur_w.execute(query_a_w).fetchone()[0]
ans_b_w = cur_w.execute(query_b_w).fetchone()[0]
print("string match?", query_a_w == query_b_w)
print("same answer?", ans_a_w == ans_b_w, ans_a_w, ans_b_w)
assert query_a_w != query_b_w and ans_a_w == ans_b_w == 30
```
▶ What you'll see: two SQL strings differ, but both return 30.

```python
plt.figure(figsize=(4, 3))
plt.bar(["exact", "execution"], [exact_acc_w, exec_acc_w], color=["gray", "seagreen"])
plt.ylim(0, 1)
plt.ylabel("accuracy")
plt.title("5: evaluation metrics can diverge")
plt.show()
conn_w.close()
```
▶ What you'll see: execution accuracy has the taller bar on this tiny three-query set.

*Why it's done this way:* Exact match rewards canonical SQL form, which is useful for debugging decoders. Execution accuracy rewards semantic denotation, which is what users experience. Reporting both prevents us from mistaking surface similarity for meaning or dismissing a semantically correct alternative query.

A parser links question words to schema columns, then uses the margin between the best and runner-up
scores as a confidence signal.

```python
import numpy as np
import matplotlib.pyplot as plt

t1_rng = np.random.default_rng(0)
t1_words = np.array(["largest", "profit"])
t1_columns = np.array(["profit", "city", "date"])
t1_scores = np.array([[0.7, 0.2, 0.1], [0.95, 0.1, 0.05]])
print("words:", t1_words.tolist())  # -> ['largest', 'profit']
print("columns:", t1_columns.tolist())  # -> ['profit', 'city', 'date']
```

### ✍️ Toy 3 · Grammar masks zero invalid actions

A grammar mask removes impossible next actions before normalization, so even a high invalid logit gets
probability zero.

```python
import numpy as np

t3_rng = np.random.default_rng(0)
t3_action_names = np.array(["COLUMN_profit", "FROM_sales", "COLUMN_city", "WHERE"])
t3_logits = np.array([1.0, 3.0, 2.0, 0.0])
t3_mask = np.array([1.0, 0.0, 1.0, 0.0])
print("action names:", t3_action_names.tolist())  # -> ['COLUMN_profit', 'FROM_sales', 'COLUMN_city', 'WHERE']
print("raw logits:", t3_logits.tolist())  # -> [1.0, 3.0, 2.0, 0.0]
print("valid mask:", t3_mask.astype(int).tolist())  # -> [1, 0, 1, 0]
t3_valid_logits = t3_logits[t3_mask == 1]
print("valid logits:", t3_valid_logits.tolist())  # -> [1.0, 2.0]
t3_shifted = t3_logits - np.max(t3_valid_logits)
print("shifted logits:", np.round(t3_shifted, 3).tolist())  # -> [-1.0, 1.0, 0.0, -2.0]
t3_exp = np.exp(t3_shifted) * t3_mask
print("masked exp:", np.round(t3_exp, 3).tolist())  # -> [0.368, 0.0, 1.0, 0.0]
t3_probs = t3_exp / np.sum(t3_exp)
print("masked probabilities:", np.round(t3_probs, 3).tolist())  # -> [0.269, 0.0, 0.731, 0.0]
assert np.allclose(np.round(t3_probs, 3), [0.269, 0.0, 0.731, 0.0])

plt.figure(figsize=(5.0, 3))
plt.bar(t3_action_names, t3_probs, color=["seagreen" if m else "lightgray" for m in t3_mask])
plt.xticks(rotation=25, ha="right")
plt.ylabel("probability")
plt.title("Toy 3 · invalid actions get zero")
plt.show()
```
▶ What you'll see: the masked-out `FROM_sales` action has probability 0 despite its high raw logit.

```python
import numpy as np

t4_rng = np.random.default_rng(0)
```

### ✍️ Toy 5 · Exact match and execution accuracy can diverge

A predicted SQL string can differ from the reference while returning the same answer. Track exact-match

### Basic 4 — Compute a link margin

### Advanced 1 — Beam search with grammar masks

**Goal.** Keep multiple partial programs while applying grammar masks at every step, because text-to-SQL decoders often need search rather than one greedy path. We build it in 4 steps.

```python
logits_a1 = [np.array([3, 0, 0, 0, 0, 0], float), np.array([0, 2.0, 1.5, 0, 0, 0]), np.array([0, 0, 0, 2.5, 1.0, 0]), np.array([0, 0, 0, 0, 0, 3.0])]  # Step logits.

```
▶ What you'll see: the beam begins with a single empty program.

```python

    next_beam_a1 = []  # Store candidate continuations.
    mask_a1 = np.zeros(len(actions_a1))  # Create a grammar mask for this state.
    mask_a1[valid_a1] = 1  # Mark valid action indices.
```
